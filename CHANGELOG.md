# Changelog

## [Unreleased]

### Highlights

- **Tool names are bare on the wire.** A workspace tool is now `<source>__<tool>` — the `ws_<id>-` prefix is gone. It carried no information a session did not already have (a session is walled to one workspace), and at 39 opaque characters for a personal workspace it was a constant the model had to echo byte-exact on every call. Models on non-Anthropic providers dropped it, which failed every workspace tool call for that tenant. Personal connectors now carry a reserved `my_` marker (`my_gmail__send`) so they stay distinguishable from a workspace source of the same name — the two are different credentials. **Breaking for `/mcp` clients**, below; no data migration.

- **New visual identity.** NimbleBrain Blue (`#315EDB`) is now the single accent on pure white / pure black grounds, set in Hanken Grotesk with a screen-text serif (Newsreader) reserved for agent prose in chat. The terracotta `warm` accent is **removed** — blue carries every primary action, focus ring, and live state, so the brand hue means one thing. The web faces are served from Google Fonts (`fonts.googleapis.com` / `fonts.gstatic.com`) rather than Fontshare — self-hosted deployments behind an egress allowlist or a font-blocking CSP will fall back to `system-ui` unless those hosts are permitted. A contrast guard (`web/src/theme/__tests__/contrast.test.ts`) now derives WCAG ratios from the palette itself; it caught the outgoing palette's accessibility failures on the way in, including warning text at 2.15:1 and tertiary metadata at 2.40:1.

- **Files are workspace-owned storage.** An uploaded or agent-created file now lives under the workspace it was made in — `workspaces/<wsId>/files/<ownerId>/` — so the directory is the boundary: a file created in one workspace can't be read from another, and deleting a workspace archives its files with it. The `files://<id>` URI stays bare; the workspace comes from the request, and the browser serve endpoint is bare too — `GET /v1/files/:id` resolves the workspace from the globally-unique id (within the caller's own files), no `?ws=` needed. **Breaking** — run `bun run migrate:files-to-workspace` before deploying.
- **Conversations are workspace-owned storage.** Every conversation now lives under the workspace it runs in — `workspaces/<wsId>/conversations/<ownerId>/<convId>.jsonl` — so the directory *is* the boundary, not a soft `workspaceId` breadcrumb. Workspace-scoped conversation lists become directory listings, deleting a workspace archives its chats with it, and a chat cannot carry one workspace's context into another. **Breaking** — run `bun run migrate:conversations-to-workspace` before deploying.
- **Automations are workspace-owned, and a run produces a result — not a conversation.** Each automation now lives at `workspaces/<wsId>/automations/<ownerId>/<automationId>.json`, so the directory is the boundary and a workspace delete archives its automations with it. A scheduled run no longer creates a chat: it leaves a *run result* — the deliverable, the activity log, and refs to any files it wrote — under `…/automations/<ownerId>/runs/<automationId>/` (an `index.jsonl` of run summaries plus a per-run `<runId>.result.json`). `runtime.executeTask` returns a `runId` instead of a `conversationId`. **Breaking** — run `bun run migrate:automations-to-workspace` before deploying.
- **Composio-backed Gmail and Outlook connectors** (stopgap until our own restricted-scope verification at Google / Microsoft lands). New `auth: composio` discriminator in the catalog routes through `@composio/core` as a remote OAuth aggregator: install → adopt-or-create Composio session → user does vendor OAuth → tool calls flow through Composio's MCP endpoint. The platform persists only an opaque `connectedAccountId` per workspace; no vendor tokens ever land in `workspace.json`. Catalog entries carry a curated `composio.tools` allowlist so the agent's tool-search sees a working set instead of every tool the toolkit publishes (Outlook alone has 282). Operator setup is one secret — the broker API key — for the whole integration; adding a new Composio toolkit is one catalog entry + one line of config (no code change). See the [Composio operator guide](https://docs.nimblebrain.ai/deploy/composio/) for end-to-end setup.
- **Platform sources unified on MCP.** Every tool/resource provider — built-in platform capabilities and user-installed bundles alike — is now an MCP server. Built-ins run in-process over `InMemoryTransport`; bundles continue to run as subprocess or remote MCP. One contract, one shape, one set of capabilities.
- **Task-aware iframe tools** — widgets can now `callToolAsTask` for long-running tools (research runs, batch imports). The `/mcp` endpoint speaks the MCP 2025-11-25 tasks utility, and the iframe bridge always routes `tools/call` and `resources/read` through `/mcp` (legacy REST branches in the bridge are gone). The `/v1/tools/call` and `/v1/resources/read` REST endpoints stay for the web shell.
- **Bundle-side custom instructions.** Bundles publish `app://instructions`; the platform reads it on every prompt assembly and wraps non-empty bodies in `<app-custom-instructions>` containment in the system prompt. Zero opt-in flag, zero new platform-side infrastructure per bundle ([docs](https://docs.nimblebrain.ai/apps/custom-instructions/), [#98](https://github.com/NimbleBrainInc/nimblebrain/pull/98)).
- **Settings IA refactor.** Nav grouped by scope (This Workspace / Organization). Profile un-nested to top-level `/profile`. New shell `UserMenu` (avatar + popover) is the canonical path for identity actions; sidebar collapse moved to a half-overflow edge button. Old URLs redirect.
- **Connector registries unified on upstream MCP `ServerDetail`** — both the bundled curated catalog and mpak now flow through one wire shape and one client-side projection. mpak is consumed via `@nimblebrain/mpak-sdk@0.8.0`'s `searchServers` (native `/v1/servers/search`), so brand icons land in the Browse list, in installed-stdio-bundle rows, and on the Configure page through one `iconUrl` field — no more parallel stdio-catalog YAML lookup ([#195](https://github.com/NimbleBrainInc/nimblebrain/pull/195)).
- **`ConnectorDirectory` facade** — single read-side seam for the registry layer. Sources (`StaticSource`, `MpakSource`) implement just `fetch(): Promise<ServerDetail[]>`; the directory owns scope filtering, projection, error aggregation, dedup, and the lookup tables (`catalogByUrl`, `iconByPackage`, `catalogById`). Adding a new source type is a ~20-line `fetch()` body with everything else inherited. Replaces `DirectoryAggregator` + the four standalone helper functions that previously bypassed the registry instances.
- **`scopes[]` filter on `RegistryConfig`** — restrict a registry instance to one or more namespaces. Match is OR-of-prefixes against either the reverse-DNS prefix of `ServerDetail.name` (e.g. `ai.nimblebrain` matches `ai.nimblebrain/echo`) or the npm scope of `packages[].identifier` (e.g. `nimblebraininc` matches `@nimblebraininc/echo`). Operators can run multiple mpak rows with different scopes side-by-side. The seeded mpak row defaults to `scopes: ["nimblebraininc"]` — narrow-by-default for first installs; broaden by editing the row.
- **15 new DCR remote-OAuth connectors in the curated catalog** — Linear, Canva, Cloudflare, Intercom, Mercury, Neon, PayPal, Sentry, Stripe, Vercel, Webflow, Wix (workspace-scoped, all DCR — point-and-click installs, no operator setup). Granola moves from user to workspace scope so teams share one connection. Notion was already in the catalog. Brand icons sourced from `static.nimblebrain.ai/icons/<name>.png`.
- **Connector serverName slugified from canonical reverse-DNS form.** A new `slugifyServerName(canonicalName)` rule transforms `ServerDetail.name` (e.g. `com.canva/mcp`) into a URL-safe, filesystem-safe, collision-free single-segment slug (`com-canva-mcp`) at install time. Both source types use the same rule so a connector's `serverName` is uniform regardless of whether it came from the curated catalog or mpak. The whole-namespace preservation eliminates the rightmost-segment collision class (`com.acme.crm/mcp` and `com.foobar.crm/mcp` produce distinct slugs, where last-segment derivation would have collapsed both to `crm`).
- **Curated connector catalog is deployment config, not image code.** The catalog moves out of the compiled image into a mounted directory (`NB_CURATED_CATALOG_DIR`), so changing the connector set is a ConfigMap change rather than a code release, and production curation stays out of the OSS repo. `StaticSource` reads a single file or a directory of catalog files (split curation rolls up to one registry); the image ships a minimal DCR-only example as the locked fallback so fresh installs aren't empty. The DCR rot-detector (`scripts/check-catalog-dcr.ts`) becomes a path-argument CLI tool; its automated gate re-homes to the deploy repo alongside the real catalog.
- **Conversations moved to top-level user-owned storage** (Stage 1). Every conversation now lives at `{workDir}/conversations/{convId}.jsonl` instead of `{workDir}/workspaces/{wsId}/conversations/...`, with single-owner authorization (`Conversation.ownerId === access.userId`). Multi-participant / sharing semantics are deferred to a future stage with explicit policy gates. Operator deploy is **breaking** and requires two migration scripts (see Breaking).
- **Workspace-bounded tool reach (the wall).** A chat or task session reaches exactly one workspace's tools plus the caller's identity tools — never a cross-workspace union. The cross-workspace tool aggregator and its watcher cache are removed; `routeToolCall` denies any workspace other than the session's (`CrossWorkspaceReachDenied`). User-scope credentials live in the personal workspace; `oauthScope: "user"` is deleted. Header switcher → sidebar workspace+apps navigator. **Breaking** — run `bun run migrate:user-creds` before deploying; see Breaking for the `/mcp` impact.
- **Files and automations are now identity-owned** (Phase B / C). A file or automation belongs to the user, not a workspace: files live at `users/{userId}/files/`, automations owner-partitioned at `users/{userId}/automations/`, both surfacing as bare identity tools (`files__*`, `automations__*`) reachable from any workspace. A `files://` URI resolves from the owner's store regardless of which workspace created it; a scheduled automation **fires as its owner**, walled to its provenance workspace (the scheduler is now multi-owner). **Breaking** — run `bun run migrate:files-to-identity` and `bun run migrate:automations-to-identity` before deploying (see Breaking).
- **CLI slimmed to `bun run start` + `bun run dev`.** The Ink TUI, the operator subcommands, and the `nb` binary are gone; the runtime is launched via bun and its interfaces are the web UI and `/mcp`. See Removed.

### Added

- **`skills__history` and `skills__restore`** make a skill's saved versions reachable. Every `update`, `delete`, and `restore` already snapshotted the file to `_versions/` first, but nothing could list or read that directory, so the backup was unreachable from any path an agent or operator had. `skills__history` lists the snapshots, `skills__read` takes a `version` to show one, and `skills__restore` puts one back — snapshotting the current file first, so a restore is itself undoable. Partially addresses [#121](https://github.com/NimbleBrainInc/nimblebrain/issues/121) (`skills__diff` is still open).
- **Reasoning depth is a first-class setting, and it works on every provider.** A new `thinkingEffort` (`low` … `max`) says how hard to think, and the runtime translates it per provider: an effort tier to Anthropic's Opus 4.7/4.8 and 5-series and to OpenAI/Nebius-hosted models (Qwen, Kimi, GLM, gpt-oss) (on OpenAI, per-model — the GPT-5 `-pro` models accept only part of the ladder and `gpt-5-pro` takes `high` alone, while `o1-pro`/`o3-pro` take all three, so a tier it rejects steps down or is dropped rather than 400ing the call), a token budget sized from it to Anthropic up to 4.6 and to Gemini 2.5, `thinkingLevel` to Gemini 3 (per-model — support varies within a generation, and a Gemini model with no verified entry receives nothing rather than a guessed dialect), and an effort tier to xAI (per-model — two Grok models take no effort parameter at all, and `grok-4.3` accepts `none`, making it the only model in an effort dialect where `thinking: "off"` sends a suppressing value rather than nothing). OpenAI and Google reasoning were previously **ignored entirely** — the translation layer was Anthropic-only. The default depth is `medium`, which is deliberately cheaper than most provider defaults; on budget-shaped Anthropic models it also shrinks the derived thinking budget (Sonnet 4.6 at a 16,384 output ceiling: 12,288 → 4,300). Set `thinkingEffort` to restore a deeper default. `thinkingBudgetTokens` still works and takes precedence where a provider meters tokens ([docs](https://docs.nimblebrain.ai/config/nimblebrain-json/#reasoning-depth), [#774](https://github.com/NimbleBrainInc/nimblebrain/issues/774)).

  This replaces a derivation that ran the other way. Effort used to be inferred from a token budget, and with no budget configured the only number in scope was the model's own catalog ceiling — so an adaptive-only model got a "reason as hard as possible" directive on every call, derived from a figure nobody chose. Nothing in the resolver reads `maxOutputTokens` now. **Behavior change:** a `thinking` override is now honored only for models the catalog carries and flags reasoning-capable. Previously an explicit `enabled` bypassed that check, which was inert while non-Anthropic providers were dropped and became a live send of a parameter the model doesn't take once they weren't. If you pin a bespoke model id or point `providers.openai.baseURL` at a proxy with its own model names, add the model to the catalog to keep reasoning on it — the runtime logs a warning naming the model when it drops an override. Two further consequences: `xhigh` is reachable on Anthropic for the first time (no token band ever produced it; OpenAI and Gemini cap at their own `high`), and `thinking: "enabled"` no longer requires `thinkingBudgetTokens` — it falls back to the default tier, so that combination is now accepted where it used to be rejected.

- **The home briefing no longer breaks on most OpenAI models, or on Gemini 3.** It asked for the `minimal` reasoning tier on every OpenAI reasoning model, and 22 of the 25 reachable ones reject it outright; on Google it sent a `thinkingBudget`, which is the Gemini 2.5 dialect that Gemini 3 rejects. Either way the briefing 400'd on each home load for anyone whose fast slot pointed at an affected model. It now sends each model only a dialect that model accepts — the cheapest reasoning level a Gemini 3 model offers, and nothing where the model has no accepted way to ask for less ([#800](https://github.com/NimbleBrainInc/nimblebrain/pull/800), [#816](https://github.com/NimbleBrainInc/nimblebrain/pull/816)).

- **Claude Opus 5 is selectable** ($5/$25 per 1M, 1M context, 128K output). Pick it for any model slot in Settings → Model or in `nimblebrain.json`. No slot's default changes, so an install that doesn't choose it is unaffected. Like Opus 4.7/4.8 and Sonnet 5, Opus 5 rejects `thinking.type=enabled` and takes `thinking.type=adaptive` + `output_config.effort` instead; the engine translates on the fly. That translation derives an effort tier from a token budget and is lossy in ways worth knowing before you make Opus 5 a default — see [#774](https://github.com/NimbleBrainInc/nimblebrain/issues/774).
- **Managed-connector provider settings are declared in `nimblebrain.json`.** A new `connectors.providers.composio` block (`apiKey`, `baseUrl`, `monitorEnabled`) configures the provider on the config interface instead of ambient env, per-field: a field declared in the block wins, a field left out reads its `COMPOSIO_*` fallback, so nothing changes on upgrade. A connector's persisted transport credential now names a credential provider rather than a `${COMPOSIO_API_KEY}` env reference, which is what makes the broker credential declarable; connectors installed earlier are mapped forward when they start, with no operator action. **Forward-only** — a connector installed on this build does not start on an earlier image, so reinstall after a rollback ([#750](https://github.com/NimbleBrainInc/nimblebrain/pull/750), [docs](https://docs.nimblebrain.ai/config/nimblebrain-json/#connectors)).
- **Smithery is a second managed-connector provider.** `connectors.providers.smithery` (`apiKey`, `namespace`, `baseUrl`, `monitorEnabled`) registers Smithery through the same seam as Composio — a brokered provider that hosts a config-authed MCP session with no OAuth arm of its own, so it contributes just `createSession` and a liveness probe. Its vendor-returned session URL takes the full SSRF gate (no fleet-internal plain-HTTP exception), and its credential is a named credential provider from the start rather than a `${SMITHERY_API_KEY}` reference in workspace state. Registered only when both its broker credential and a namespace resolve — a namespace is account-owned at Smithery with no safe default, so half-configured means off — and a deploy without Smithery carries nothing ([#723](https://github.com/NimbleBrainInc/nimblebrain/pull/723), [docs](https://docs.nimblebrain.ai/config/connector-providers/)).
- **Context Ledger — skill activation is visible in the transcript.** Each assistant turn that loads skills shows a quiet line above its activity (`Following <skill> · matched <tool>`), expandable to each skill's scope, load reason, and token cost; a turn that loaded none shows nothing. Reports every loading mechanism — tool-affinity, trigger phrase, and always-on (workspace persona / house-rules), excluding the platform's own built-in core skills. The chat-header **In context** panel aggregates the current turn's skills (replacing the skills-only lightbulb), grouped by why each one loaded. The lines persist — reopening a conversation shows the same ledger ([docs](https://docs.nimblebrain.ai/using/chat/#the-context-ledger)).
- **Per-toolkit Composio auth-config ids are declared in `nimblebrain.json`.** `connectors.providers.composio.authConfigs` maps a toolkit slug to its `ac_…` id — keyed by the slug the catalog entry already carries, so adding a toolkit is one catalog entry plus one line of config instead of a hand-typed env-var name repeated across two repos and a Helm regex guarding its spelling. The id is an identifier, not a secret (inert without the broker key), so it belongs in config rather than your secret store. A boot audit reports any declared key matching no catalog toolkit — the one string still shared between the catalog and a deployment's config. The `COMPOSIO_<TOOLKIT>_AUTH_CONFIG_ID` env vars and the catalog's `composio.authConfigEnv` field are **removed**; every id is declared config ([#786](https://github.com/NimbleBrainInc/nimblebrain/pull/786), [docs](https://docs.nimblebrain.ai/config/nimblebrain-json/#per-toolkit-auth-configs)).
- **xAI (Grok) model provider (`xai:<model-id>`).** Configure via `providers.xai` or `XAI_API_KEY`; five models ship in the catalog (`grok-4.5`, `grok-4.3`, the two `grok-4.20-0309` variants, `grok-build-0.1`), all supporting tool calling, over Chat Completions. Effort support is per-model and measured: `grok-4.3` takes the full ladder plus `none`, `grok-4.5` everything but `none`, and two models take no effort parameter at all — a model with no measured ladder is sent nothing rather than a guessed tier. That `none` makes `grok-4.3` the only model in an effort dialect where `thinking: "off"` sends a suppressing value rather than nothing. See the [providers config docs](https://docs.nimblebrain.ai/config/nimblebrain-json/#xai-grok).
- **Nebius Token Factory model provider (`nebius:<model-id>`).** Optional OpenAI-compatible gateway for open-weight models — Qwen3, Kimi, GLM, gpt-oss, and more. Configure via `providers.nebius` or `NEBIUS_API_KEY`; a curated catalog surfaces flagship models in the picker with pricing while any other Nebius id still routes as free text. Requests use Chat Completions (Nebius has no Responses API) and rely on automatic prefix caching. See the [providers config docs](https://docs.nimblebrain.ai/config/nimblebrain-json/#providers).
- **Connector skill overlays.** Installing a connector binds a curated usage overlay (fetched by connector identity from a pinned public repo) and surfaces it into the conversation history exactly once — on the first call to a matching tool, never the system prompt — so the guidance is relevant (only when the connector's tools are used) and cache-friendly (rides the append-only history instead of re-varying the cached prefix). Always on and fail-soft: an overlay exists only if curated for that connector, and a missing overlay or fetch error is a no-op, never failing the install. Deduped against the bundle's own `skill://usage`, removed on uninstall, and listed via `manage_connectors list_bound_skills` ([docs](https://docs.nimblebrain.ai/using/skills/#connector-skill-overlays)).
- **Optional Sentry error reporting (`NB_SENTRY_ENABLED`, off by default).** Captures uncaught exceptions and unhandled promise rejections, initialized as an out-of-kernel Bun preload so the kernel stays vendor-neutral OTel (`check-no-sentry-in-kernel` still green) and Sentry does **not** take over tracing — additive to the OTLP→Tempo pipeline, not a replacement. Switched explicitly via `NB_SENTRY_ENABLED=true` (our own knobs, mirroring the web client; never inferred from DSN presence), and the SDK loads only when enabled. Per-tenant via the chart (`runtime.config.sentry.enabled`); events carry only the boot-time `tenant_id` and opaque ids, with headers/cookies/bodies/query strings scrubbed ([docs](https://docs.nimblebrain.ai/deploy/observability/#error-reporting-sentry-optional)).
- **"New version available — reload" prompt.** A long-lived browser tab keeps running the web build it loaded with; after a deploy it can sit on stale client code for hours. The shell now polls `/config.js` (already served `no-store`) every ~90s and on tab focus, and when the deployed web `release` differs from the one the tab booted with, shows a quiet, dismissible prompt at the foot of the sidebar (a refresh icon with a status dot when the sidebar is collapsed) with a Reload button. Never auto-reloads (you may be mid-turn). No effect in local dev / unconfigured builds.
- **Cache-hit rate in usage reports.** The usage aggregator now derives a `cacheHitRate` (0–1) — `cacheRead / (input + cacheRead + cacheWrite)` — on report totals, per model, and per breakdown row (including per-conversation), surfaced through the `usage` tool, the usage bundle, and the UI. It's the standing signal the prompt-cache work keeps high: a healthy long conversation reads its growing prefix back (high rate); a thrashing one re-writes it every turn (low rate). Makes the cache-cost win observable and catches regressions without a one-off forensic pass.
- **History compaction (opt-in, `features.compaction`).** Long conversations grow across runs until the prompt approaches the model's context window. The naive fix — windowing out the oldest messages every turn — busts the prompt cache every turn. Compaction instead folds the oldest turns into a single summary at run start as a deliberate, infrequent re-anchor: one cache re-write when it fires, then a smaller prefix that re-caches and stays stable. Triggers at ~70% of the message budget, keeps the recent ~35% verbatim, snaps the boundary to a user-turn start (so tool-call/result pairs stay intact), and summarizes the rest with the `fast`-slot model. Persisted as a `history.compacted` event and replayed by `reconstructMessages`, so the model context is identical whether freshly computed in a run or rebuilt on load. Compaction scopes the **model context only**: the web client, export, and fork read the full verbatim history, so users keep complete scrollback and forks copy the real turns while the model sees the re-anchored prefix. Event-sourced stores only; best-effort (a summarizer failure falls back to the full history, never failing the turn). Default off — enable per tenant.
- **`nimblebrain-bundle-sdk` Python package — Phase 2b.** Bundle-side wrapper for the `ai.nimblebrain/host-resources` extension. Bundle authors write `await host(ctx).read("files://fl_abc")` instead of hand-rolling the JSON-RPC call. Capability detection from `ClientCapabilities.extensions` with a fallback to the legacy `experimental` slot. Lives in `packages/bundle-sdk-py/`, released independently via `bundle-sdk-py/v*` tags (separate from the platform's `v*` tags). Initial version `0.1.0`. Published to PyPI as `nimblebrain-bundle-sdk`.
- **Host-resources extension — Phase 2a (handlers + resolver).** Bundle subprocesses can now call `ai.nimblebrain/resources/read` and `ai.nimblebrain/resources/list` over their MCP transport and the platform resolves the URIs against the workspace `FileStore` shared with the agent's `files__read`. One chokepoint, one security surface — same scheme allowlist, same workspace isolation. Bundle requests carry only the URI; workspace identity comes from the bundle's session, never the URI, so a workspace can't enumerate another's files. Per-`(workspaceId, bundleId)` token-bucket rate limit (100/sec, 1000 burst; returns `-32004 Rate limited` on exhaustion) prevents a runaway bundle from DoSing the FileStore. Whole-file reads cap at 10 MiB and return `-32005 ResponseTooLarge` above; range reads and write are reserved for a later phase. Threaded through every production bundle-spawn path: lifecycle `installNamed` / `installLocal` / `installRemote`, `installBundleInWorkspace` (agent-facing `manage_app install`), `configureBundle` restart, Composio eager-start, post-credential-change respawn, `ensureSourceRegistered`, and boot reload.
- **Host-resources extension capability — Phase 1 (advertisement + manifest gate).** Platform advertises `ai.nimblebrain/host-resources` in `ClientCapabilities.extensions` on every bundle's `initialize` handshake — the MCP-spec-blessed vendor-extension surface ([overview](https://modelcontextprotocol.io/extensions/overview)). Bundles declare requirements via `_meta["ai.nimblebrain/host"].host_capabilities` (keyed object mirroring the platform-side advertisement); entries with `required: true` cause install to fail loudly if the platform doesn't provide them, no silent runtime degradation. v1 payload: `read.enabled=true`, `list.enabled=true`, `write.enabled=false`, `schemes=["files"]`; `read.maxSize=10 MiB` until v2 ships range reads. Operations are object-shaped (not bare booleans) so future sub-fields slot in without breaking compat. Inbound `ai.nimblebrain/resources/{read,list}` request handlers land in Phase 2. Host-meta schema bumps to `host_version: "1.1"`.
- `auth: composio` third connector auth kind alongside `dcr` and `static`. Discriminator lives in `_meta["ai.nimblebrain/connector"].auth` on `ServerDetail` entries; the install path branches at `handleInstallRemoteOAuth`, eager-starts the source via Composio's session URL (no native MCP OAuth handshake — Composio's static `x-api-key` is the transport credential), and writes a parallel state file at `credentials/composio/<connectorId>/connection.json`. Disconnect deletes the Composio-side account (best-effort) plus the local `connection.json`. Catalog entries declare `composio.toolkit` and an optional `composio.tools` allowlist; the toolkit's `ac_…` id is deployment config, keyed by that same slug.
- `src/connectors/providers/composio/sdk.ts` — single SDK adapter module. Owns every `@composio/core` import: `composio.create` (with `sessionPreset: "direct_tools"` so the toolkit's real tools appear on MCP, not the meta-router), `connectedAccounts.{list,initiate,delete}`, eager `validateComposioConfig` (open-redirect mitigation on `connectors.providers.composio.baseUrl`; multi-tenant `NB_TENANT_ID` enforcement when the bouncer is configured), 10-second timeout wrapper on every SDK call, and the canonical `composioUserId(wsId)` formula that the route and install layers both consume.
- `/v1/composio-auth/{initiate,callback,proxy}` routes. `initiate` adopts an existing ACTIVE Composio connected account when one exists (skips the redirect dance entirely) or kicks off a fresh flow with `allowMultiple: true`. `callback` verifies a sha256-bound nonce cookie + URL params + cid, writes `connection.json`, transitions lifecycle state to `running`. `proxy` is the white-label forwarder for the vendor-side redirect URI.
- Gmail (`com.google/gmail`) and Outlook (`com.microsoft/outlook`) connectors with curated 15-tool allowlists. Without the allowlist Outlook would surface 282 tools and the agent's `nb__search` would dump every match's full description (≈220K tokens) into context — gpt-class models would 400, Claude would burn 400K tokens per turn. The allowlist is per-catalog-entry; adding a new Composio toolkit is one catalog entry + one line of config + one Composio dashboard config.
- Workspace files are now first-class MCP resources at `files://<id>`. The `files` in-process source advertises every registry entry via `resources/list` and serves bytes via `resources/read` (text MIMEs as `text`, others as `blob`), reachable from any MCP client.
- `bun run dev:worktree` — runs the platform from any git worktree against a worktree-local `.nimblebrain-worktree/` workdir on alt ports (27271 API / 27270 web), in dev mode with no auth. For smoke-testing a feature branch without disturbing your primary dev or another worktree's state; suitable for Chrome DevTools E2E. See `AGENTS.md` § Worktree dev.
- `compose__effective_context` debug tool — single-call answer to "what's in the system prompt for this conversation, with provenance per layer." Live mode returns the full traced composition; historical mode (`run_id` set) reads the recorded `skills.loaded` event for that run and verifies each layer-3 skill's `contentHash` against current source, with `_versions/` snapshot recovery on drift. Bundle filter narrows to one app's contributions ([#119](https://github.com/NimbleBrainInc/nimblebrain/issues/119)).

### Changed

- **A conversation is bound to one model for its life.** The model is resolved when the conversation is created and recorded on it; every later turn runs on that model. Changing a model slot — in `nimblebrain.json`, the override file, or via `set_model_config` — therefore applies to conversations started **after** the change, and a conversation already under way keeps running on the model it began on. Previously the slot was re-read on every turn, so an operator changing the default silently retargeted live conversations mid-thread; one production conversation ended up spanning two providers, and because the tool-call ids one provider mints aren't portable to another, it could no longer take a turn on the original provider at all. The binding covers the main chat model only — title generation and compaction still take `fast`, and `nb__delegate` still resolves the slot it names. Conversations created before this carry no binding and resolve from the current slot exactly as before; they are deliberately **not** backfilled, because a binding derived from history can capture a model string that no longer resolves, and a binding cannot be repaired. The consequence is worth stating plainly: **a conversation that already spans two providers is not repaired by this change** and still fails on the provider whose id format it cannot replay — that is fixed by normalizing tool-call ids ([#874](https://github.com/NimbleBrainInc/nimblebrain/issues/874)), not here. Forks inherit the source's binding. No migration. Note there is also currently **no way to re-point a bound conversation**: if the provider or model it names is removed from config, resuming it fails until that config is restored ([#896](https://github.com/NimbleBrainInc/nimblebrain/issues/896)).
- **Skills settings is one composition list.** Every tier shaping the agent — the skills you own here, your personal skills, organization policy, and the built-in system skills — sits in a single list, grouped agency-first with a segment filter to slice by tier. Each row states how it loads at rest (`Always on · every conversation`, `` On tool match `<glob>` ``, `On trigger "<phrase>"`, `Won't auto-load yet`); tiers you don't own here are read-only and link to where they're managed. The workspace, org, and profile tabs are one component: each is a vantage that shows the tiers it has and drops the filter when there's only one. Vocabulary unified on "Skills".
- **Workspace instructions are human-authored; the agent routes "remember this" instead of writing the overlay.** `instructions__write_instructions` is now an internal tool — invoked by the settings UI, never on the model's surface (the write is whole-blob overwrite of always-injected prose, a human-shaped edit made where the author sees the full text they are replacing). The always-on capability briefing teaches the routing: asked to remember a rule or convention, the agent drafts the exact text and points the user to workspace settings; asked to remember a fact or a piece of state, it records it in a memory app when one is installed. `skills__*` stays proxied and named in the briefing (the authoring surface for a capability, reached deliberately). An instruction write from inside an **unattended run is refused** at the source, behind the same wall as the automation-authoring surface.
- **Kernel identity tools are always surfaced directly.** `files__*`, `conversations__*`, and `automations__*` — the kernel identity sources — now join the `nb__` system core in the always-direct tool set, instead of being proxied and discovered via `nb__search` once a workspace exceeds the direct-tool cap. They're hot substrate the model reaches for unprompted, so proxying them forced a `nb__manage_tools` promote on first use — and every promote mutates the tools block ahead of the messages, busting the conversation's cached prefix. Keeping them direct removes those promotes and their cache-writes; the always-direct set is now "kernel tools" (system core ∪ identity sources), not `nb__`-only. Bundle/app tools are unaffected — they still proxy and promote on demand.
- **An automation run requires current membership of its workspace.** An automation fires as its owner, walled to the workspace it was created in. If the owner has since been removed from that workspace, the run is now denied (`executeTask` throws before binding any tools) instead of continuing to act in a workspace they left. The scheduler records the denial as a **skipped** run — it doesn't count as a failure, so it never trips the consecutive-error auto-disable, and the automation resumes automatically if the owner is re-added. Completes the offboarding-revocation story alongside the conversation-resume gate; personal-workspace automations are never affected.
- **Resuming a conversation requires current membership of its workspace.** A conversation is sealed to the workspace it was created in (its tools/skills/apps resolve there), so a member removed from that workspace can no longer **resume** conversations they own in it — continuing would grant that workspace's tools to someone offboarded from it. Both `POST /v1/chat` and `/v1/chat/start` return `403` (`conversation_access_denied`) on such a resume. **Read access is unchanged** — a removed member can still load and read their own authored conversations; only active continuation is gated. Personal-workspace conversations are never affected (sole-member). This replaces the earlier "conversations outlive their workspace context" behavior, a holdover from when conversations were stored outside any workspace. Files and automations share the same offboarding shape and will follow.
- **The chat send endpoints require a workspace.** `POST /v1/chat`, `/v1/chat/stream`, and `/v1/chat/start` now require a valid `X-Workspace-Id` header (`400` if absent, `403` if a non-member) instead of silently defaulting to the caller's personal workspace — a chat turn names the workspace it acts from. The first-party web client already sends it on every request, so there is no user-facing change; embedded `Runtime.chat()`/`startTurn()` callers and dev mode (no identity) still default to the personal workspace. `/cancel` is unchanged (owner-gated, no workspace needed). This also removes a Hono `.use("*")` wildcard that was leaking the chat router's workspace middleware onto `/v1/events` (identity-scoped, never gated on the header by design).
- **The chat panel re-scopes to the focused workspace.** Switching workspaces now clears the open conversation and resets the panel to a fresh draft in the newly-focused workspace, instead of carrying the previous workspace's conversation across. The panel stays open; only the conversation re-scopes. Opening a conversation from within its own workspace is unaffected.
- **Conversation list is always workspace-scoped** — the cross-workspace "All workspaces" view is removed from the conversations app. The list shows the focused workspace's chats, with the workspace name shown ambiently; switch workspaces to see another's. The owner-across-workspaces enumeration remains an internal primitive (skills, usage), never a user surface.
- **Workspace ids are now opaque and name-independent.** A non-personal workspace's id is generated as an opaque token (`ws_<16-hex>`, via `generateWorkspaceId()`) at create time instead of being derived from the name (`ws_<slugify(name)>`). The workspace name is now a freely-editable field: renaming a workspace via `manage_workspaces` no longer changes its id, its on-disk dir, or its URL (`/w/<id>`) — the pre-existing behavior left the URL permanently stamped with the original name. Two workspaces with the same name now coexist with distinct ids (previously a slug conflict). **No migration required and no breaking change for existing deployments**: existing name-derived ids remain valid (they already match the id pattern and `update` already froze the id on rename), so every existing `/w/<slug>` deep link and on-disk dir keeps working untouched; only newly-created workspaces get opaque ids. Personal workspaces are unchanged — they stay deterministic at `ws_user_<userId>` for O(1) lookup. `WorkspaceStore.create(name, slug)` still honors an explicit slug for personal-workspace provisioning and deliberate operator/test overrides.
- **`files__read` text extraction broadens slightly.** `extractText` now treats any `text/*` mime as UTF-8-decodable (previously only an exact-match allowlist of nine mimes). Practical effect: `text/sql`, `text/css`, `text/javascript`, etc. are now extractable from `files__read` instead of returning null. The decode path falls back to null safely if the bytes don't decode. Consolidates a third `isTextMime` duplicate with the agent-side and bundle-side predicates.
- Uploaded images are persisted in conversation JSONL as MCP `resource_link` blocks pointing to `files://<id>` instead of inline `Uint8Array` bytes. The runtime rehydrates them to AI SDK V3 `file` parts at the `model.doStream` boundary, so vision content is now stable across multi-turn agent loops (previously dropped on turn 2+). Existing JSONL files are read forward without migration; legacy `image` blocks are quietly omitted on reconstruction (same as the pre-fix behavior).
- Apps list in the system prompt now surfaces each bundle's `initialize.instructions` inside `<app-instructions>` containment tags, so per-bundle guidance reaches the LLM.
- Iframe bridge uses the MCP transport (`StreamableHTTPClientTransport` against `/mcp`) for `tools/call` and `resources/read`. `INTERNAL_APPS` authz still precedes transport selection. Bridge advertises `hostCapabilities.tasks` to iframes and forwards `notifications/tasks/status` on a per-bridge subscription.
- Inline (non-task) `tools/call` handler on `/mcp` now preserves `structuredContent` (was dropping it).
- Settings nav grouped by scope. "This Workspace" (General / Members / Usage / Apps) and "Organization" (Model / Workspaces / Users) replace the flat tab list. About is the footer. Per-bundle settings panels nest under "Workspace > Apps."
- Settings re-scoped by data ownership. Model → Organization (writes global `nimblebrain.json`, affects every workspace). Usage → This Workspace (uses `runtime.getWorkspaceScopedDir()`). MCP Connection card → Workspace > General.
- Sidebar collapse toggle moved to a half-overflow edge button on the sidebar's right border (Linear pattern).
- `manage_workspaces.list` now returns the requesting user's role within each workspace (`userRole?: "admin" | "member"`) so the web client can gate workspace-admin UI without an extra `list_members` round-trip.
- `POST /v1/chat` validation error wording. Hand-rolled checks (`"metadata must be a JSON object"`, `"allowedTools must be an array of strings"`) replaced with TypeBox path-prefixed errors (`"/metadata: Expected object"`, `"/allowedTools: Expected array"`). HTTP status (400) and `error: "bad_request"` are unchanged. External callers asserting on the exact wording need to update; the field name still appears in the message.
- Skill manifest writes now always include `metadata.keywords` and `metadata.triggers` as arrays (defaulting to `[]` when omitted by the caller). Previously a partial `metadata: { category: "X" }` could write a manifest with no `keywords`/`triggers` keys at all; the loader's domain type required them, so the divergence was a latent type lie. The on-disk JSON shape is now what the type always claimed.
- API responses now carry HSTS (`max-age=31536000; includeSubDomains`) and CSP (`default-src 'none'; frame-ancestors 'none'; base-uri 'none'`) by default so direct-exposure self-hosted deployments aren't naked. Operators terminating TLS at a reverse proxy that already emits these can disable via `NB_HSTS=""` / `NB_CSP=""`, or override to a custom value via env var or middleware option ([#20](https://github.com/NimbleBrainInc/nimblebrain/pull/20)).
- Bridge MCP client session survives workspace switch (Stage 2 / Q3). `setActiveWorkspaceId` no longer fires the bridge-reset hook; reset still fires on logout via `setAuthToken`. Dispatch flows via per-request `X-Workspace-Id`.
- Catalog field `defaultScope` renamed to `defaultBinding` with values `"workspace" | "personal"` (Stage 2 / T008). 19 catalog entries updated.
- Web prop `scope: "user" | "workspace"` renamed to `mode: "personal" | "workspace"` across four UI components (Stage 2 / T009).
- Tool name display in the conversation transcript renders as a workspace badge + friendly tool name (Stage 2 / Q2); raw `ws_<id>/<tool>` stays in JSONL.

### Breaking

- **`skills__update` now requires `body_mode` whenever `body` is given** — `append` to add to the skill, `replace` to overwrite the whole body. It previously replaced unconditionally, so an agent asked to "add a rule" that sent only the new section silently discarded everything else. Neither default is safe (`replace` destroys content, `append` duplicates a full rewrite), so the tool asks rather than guesses; a body with no mode is a clear error and writes nothing. Callers that pass `body` must add `body_mode`. Manifest-only patches are unaffected.
- **The org-wide instructions overlay is removed, and `write_instructions` no longer takes a `scope`.** `instructions://org` is gone; `write_instructions({ body })` writes the workspace overlay and nothing else. Org-wide standing guidance is an **org-tier skill** (`{workDir}/skills/`, authored at Organization → Skills), which is file-backed and org-admin-gated exactly as the overlay was, and additionally carries per-topic granularity, dynamic loading, and triggers — so org content that is only sometimes relevant costs nothing on the turns it isn't. No migration ships: an `{workDir}/org/instructions.md` left on disk is simply no longer read. Copy any such file into an org-tier skill before upgrading. **A caller that still sends `scope` is refused** with a message naming the replacement — the argument is not ignored, because ignoring it would land an org-intended body on the workspace overlay, which is overwrite-only and would lose whatever was there. **Breaking for `/mcp` clients** that call `instructions__write_instructions` with a `scope` argument, and for any that read the `instructions://org` resource.
- **The `reasoning` model slot is removed.** Nothing in the runtime ever read it — `default` serves every chat turn and `fast` serves titles, the briefing and both history folds — so it was a configurable field that implied routing the engine never did. `models.reasoning` in `nimblebrain.json` or `workspace.json` is now ignored (in `nimblebrain.json` it warns as an unknown key and boots; delete it at your convenience), and the Reasoning Model control is gone from settings. **Breaking for agent profiles**: `"model": "reasoning"` no longer resolves to a slot. It falls through to the bare-id fallback, becomes `anthropic:reasoning`, and fails at the provider on the first delegate call. Name the model directly instead — `"model": "anthropic:claude-opus-4-6"` — which is what the slot was standing in for. `"default"` and `"fast"` are unaffected, in both the bare and `alias:` spellings.
- **Top-level `personalWorkspaceId` is removed from the `GET /v1/bootstrap` response — any out-of-tree client reading it should switch to `workspaces[].isPersonal`.** It carries the same fact per entry and is what in-tree callers already use. No migration; no in-tree consumer read the field.
- **Five Composio/Smithery settings env vars are removed; those settings now live in `nimblebrain.json` only.** `COMPOSIO_API_BASE_URL` → `connectors.providers.composio.baseUrl`, `COMPOSIO_MONITOR_ENABLED` → `…composio.monitorEnabled`, `SMITHERY_NAMESPACE` → `connectors.providers.smithery.namespace`, `SMITHERY_API_BASE_URL` → `…smithery.baseUrl`, `SMITHERY_MONITOR_ENABLED` → `…smithery.monitorEnabled`. A deployment that configured Smithery through the documented `SMITHERY_API_KEY` + `SMITHERY_NAMESPACE` pair loses its namespace and the provider unregisters — brokered connectors stop until the namespace is declared; boot logs name the key to set. **The two `*_MONITOR_ENABLED` removals fail silently instead**: a deployment that had the revalidation probe switched off gets it back on with no boot output, and the sweep resumes marking lapsed connectors `reauth_required` — declare `monitorEnabled: false` in the block before upgrading. A removed `COMPOSIO_API_BASE_URL` reverts to the public backend, visible in the `[composio] integration: configured (base=…)` boot line. The broker API keys (`COMPOSIO_API_KEY`, `SMITHERY_API_KEY`) are unchanged and remain the one value with an env fallback, because a secret has a legitimate home in the environment ([#840](https://github.com/NimbleBrainInc/nimblebrain/pull/840), [#839](https://github.com/NimbleBrainInc/nimblebrain/issues/839)).
- **The `ws_<id>-<source>__<tool>` wire form is retired — `/mcp` clients that send it must re-list.** It is rejected rather than routed (`-32602`, `data.reason: "invalid_tool_name"`), which is what makes a second workspace *unnameable* rather than merely denied: no tool name can address a workspace other than the session's own, which comes from the validated `X-Workspace-Id`. A cached `tools/list` is the migration — re-list and use the bare names. Two smaller shape changes ride along: `data.reason: "cross_workspace_reach_denied"` no longer exists (that class is deleted; the retired form is refused earlier), and `data.wsId` on `workspace_access_denied` is now always `""` — its one remaining producer is a session with no workspace to name.
- **Personal connectors are renamed on the wire — `gmail__send` is now `my_gmail__send`.** Affects any caller that hard-codes a connector tool name: `/mcp` clients, and on-disk `allowedTools` / `toolAffinity` globs in skill frontmatter or automations. A glob written against the bare name (`granola__*`) no longer matches that connector and fails closed — degraded surfacing, not a leak. Legacy `ws_<id>-` globs keep working (the pattern is normalized), but a normalized one deliberately cannot reach a `my_`-marked name: it could not have named a personal connector when it was authored, and honouring it would hand a delegated sub-agent the parent's own credentials. No stored state changes — `serverName` is untouched, so credentials, grants, permissions and placements are unaffected.
- **`conversations`, `files`, `automations`, and any `my_`-prefixed name are reserved source names — an already-installed source using one stops starting on upgrade.** With workspace names bare, a workspace bundle named `conversations` is no longer distinguishable from the kernel identity source, and the identity door is consulted first — so such a source is unreachable regardless. The check runs at every boot (`validateServerName`) and on the personal-connector install path (`isReservedServerName`), so it covers **both** workspace bundles and users' own connectors. Failure is contained per-bundle: one dead source and a log line, not a failed tenant start. Before rolling out, check installed workspace `serverName`s **and** `users/<id>/connectors.json` for those four shapes. Only an explicitly-set `serverName` can collide — `slugifyServerName` never emits `_`.
- **Files relocated to workspace-owned storage — run `bun run migrate:files-to-workspace` before deploying.** Files move from identity-owned `users/<userId>/files/` to `workspaces/<wsId>/files/<ownerId>/` (per-owner registry + bytes + sidecars). The `files://<id>` URI stays bare; the workspace is resolved from the ambient request (`RequestContext.fileWorkspaceId`, set on both doors). Two consumer-visible changes: **(1)** the browser serve endpoint is now `GET /v1/files/:id?ws=<wsId>` — bare links (no `?ws=`) get `400 workspace_required`; the web client appends it automatically. **(2)** an external MCP client reading a `files://` over `/mcp` must send `X-Workspace-Id` (was allowed header-less under identity-owned); the iframe bridge already does, so synapse apps are unaffected. The migration is dry-run by default (`--write`), idempotent, holds the `.migration-lock`; files with no `workspaceId` land in the owner's personal workspace. A file referenced from conversations in two different workspaces lands in one workspace (per-owner registry); the other reference won't resolve — rare (files are ~1:1 with their creating conversation).
- **Conversations relocated to workspace-owned storage — run `bun run migrate:conversations-to-workspace` before deploying.** Conversations move from the flat top-level `{workDir}/conversations/<convId>.jsonl` to `workspaces/<wsId>/conversations/<ownerId>/<convId>.jsonl`. The path is now the binding: `Conversation.workspaceId` is fixed at create (the workspace of the first message) and a chat no longer switches workspaces mid-session. The migration is dry-run by default (`--write` to apply), idempotent, and holds the shared `.migration-lock`; records with no `workspaceId` land in the owner's personal workspace. Workspace deletion becomes **archive-then-cascade** — the workspace's subtree is tombstoned to `archived/<wsId>/` (recoverable) rather than hard-deleted, since the workspace now owns its members' private chats.
- **Automations relocated to workspace-owned storage + runs decoupled from conversations — run `bun run migrate:automations-to-workspace` before deploying.** Automations move from identity-owned `users/<userId>/automations/automations.json` (one collection) to per-automation files at `workspaces/<wsId>/automations/<ownerId>/<automationId>.json`; the scheduler now scans `workspaces/*/automations/*/` and keys runs by `${wsId}/${ownerId}/${id}`. A run no longer writes a conversation: it persists a **run result** under `…/automations/<ownerId>/runs/<automationId>/` — an append-only `index.jsonl` of `AutomationRun` summaries (the `conversationId` field is gone) plus a per-run `<runId>.result.json` (full output + activity log + output-file refs). `runtime.executeTask` returns `runId` instead of `conversationId`; the `_runs/<automationId>/` conversation/file partition is removed. The migration is dry-run by default (`--write` to apply), idempotent, holds the shared `.migration-lock`, and resolves each automation's workspace from its `workspaceId` (or the owner's personal workspace when absent). Historical automation-run *conversations* under `_runs/` are no longer read — the run history is the run results going forward.
- **`/mcp` tool access is now walled to one workspace per request.** A `/mcp` session no longer exposes the cross-workspace union. Each request's `X-Workspace-Id` header (membership-validated) bounds it to a single workspace: `tools/list` returns that workspace's tools (namespaced) + your identity tools, and a `tools/call` to any *other* workspace is denied (`-32602 workspace_access_denied`). A request with no (or a non-member) `X-Workspace-Id` is identity-only (conversations/files/automations). The first-party web shell and the synapse iframe bridge both send the header, so the UI and apps are unaffected; **external MCP clients (Claude Code, Cursor) that relied on the old cross-workspace union must now send an `X-Workspace-Id` header to reach workspace tools.** No operator migration.
- **Skill manifest on-disk format change — run `bun run migrate:skill-frontmatter` before deploying.** The skill manifest is now one strict-validated schema: NimbleBrain config nests under `metadata.nimblebrain.*` (`loading-strategy`, `priority`, `status`, `tool-affinity`, `triggers`), `type` is replaced by `loading-strategy` (`always` | `dynamic`), `keywords` fold into `description`, and `requires-bundles` / `overrides` / `derived-from` are removed. The `skills__create` tool now constrains `priority` to 11–99 (0–10 reserved for core skills) — an input-contract narrowing only; the on-disk schema still accepts 0–100. The loader **fails soft** — a skill still in the legacy flat format fails validation and is **silently skipped** (dropped from agent prompts), so an operator who deploys without migrating loses every unmigrated tenant skill. The migration is idempotent, dry-run by default (`--write` to apply), holds the shared `.migration-lock`, writes atomically, validates its own output (a non-conforming legacy name like `My_Skill` is reported as an error, not silently dropped), and folds keywords into the description. Vendored core/builtin skills are already converted; this targets tenant skills under the runtime workDir. As a backstop, the loader now logs a warning naming this migration when it skips a legacy-format skill.
- **Files and automations move to identity-owned storage** (Phase B / C). Operators run two idempotent, dry-run-capable migrations during a maintenance window with the platform stopped: `bun run migrate:files-to-identity` (moves `workspaces/{wsId}/files/` → `users/{ownerId}/files/`) and `bun run migrate:automations-to-identity` (merges instance-level + per-workspace automation stores → `users/{ownerId}/automations/`). Owner resolves to the personal-workspace user or a team workspace's earliest admin; unresolvable ownership and id collisions abort with `[FATAL]`. Wire-contract change: external `/mcp` clients now see bare `files__*` / `automations__*` (identity door), and `files://` reads are identity-scoped (no `X-Workspace-Id` required).
- **Registries unified on upstream MCP `ServerDetail`** ([#195](https://github.com/NimbleBrainInc/nimblebrain/pull/195)). Operator-facing migrations:
  - `RegistryType` values `"curated"` / `"directory"` renamed to `"static"` / `"mcp"`. Any `NB_REGISTRIES` JSON pinning the old strings must be re-typed; `registries.json` is auto-migrated on next read by re-seeding the locked default.
  - The locked seeded registry id `"curated"` is now `"bundled-static"`. Existing `registries.json` rows are preserved; the new id is re-added if missing.
  - Seeded mpak registry rows no longer carry a hardcoded `url` — the mpak SDK owns its default registry host. Operators with a stale `url: "https://mpak.dev"` (the marketing site, not the registry) on a persisted mpak row should drop the field; self-hosted operators set `url` explicitly via the admin UI or `NB_REGISTRIES`.
  - `DirectoryEntry.id` (and `InstalledConnector.catalogId`) is now the reverse-DNS `ServerDetail.name` (e.g. `io.asana/mcp`) instead of bare slugs (`asana`). Catalog-keyed state — `workspace.json#oauthOperatorApps[<id>]` and the matching `<id>.client_secret` credential entries — must be rekeyed to the reverse-DNS form before existing static-auth connectors will resolve.
  - `NB_CATALOG_PATH` removed (was previously deprecated; never deployed). Use `NB_REGISTRIES` with a `static`-type registry pointing at a `ServerDetail[]` YAML/JSON file.
  - `BundleInstance.serverName` for new installs is now the slugified canonical reverse-DNS form (`com-canva-mcp`, `dev-mpak-nimblebraininc-echo`) instead of a short brand slug. Existing installs keep their persisted `serverName` and continue to resolve under the legacy form via `serverNameFromRef`'s fallback. Operators querying by `serverName` (logs, audit, `manage_connectors.uninstall`) need both forms during the transition; new installs of an existing bundle use the new slug.
- **Token-usage shape unified.** The runtime, engine, and conversation events now share a single `TokenUsage` struct (`{ inputTokens, outputTokens, cacheReadTokens?, cacheWriteTokens?, reasoningTokens? }`). Internal layers that exposed flat fields are restructured:
  - `EngineResult.inputTokens` / `outputTokens` → `EngineResult.usage`. `EngineResult` also gains `usage` and `llmMs` (the side-channel `RunMetricsCollector` is gone).
  - `TurnUsage` now extends `TokenUsage`. Top-level `inputTokens` / `outputTokens` / `cacheReadTokens` are still present (via the extension) but `costUsd` is **removed** — cost is computed at the API boundary from `(model, usage)`. Wire-format clients (`done` SSE event, `POST /v1/chat`) still see `usage.costUsd`.
  - `ChatResult` no longer has top-level `inputTokens` / `outputTokens`. Read them from `result.usage.inputTokens` / `result.usage.outputTokens`. The wire format (HTTP response) keeps the top-level fields for backward compatibility.
  - `ChatFnResult` (exported from the automations bundle) drops top-level `inputTokens` / `outputTokens`; `usage` now contains them. External `ChatFn` implementers must update.
- **`Conversation.totalInputTokens` / `totalOutputTokens` / `totalCostUsd` removed.** Totals are derived from events at read time and surfaced on `ConversationSummary`. Stores no longer maintain rolling totals on the line-1 metadata; pre-deploy values written there are ignored.
- **`StoredMessage.metadata.usage` replaces flat `inputTokens` / `outputTokens` / `cacheReadTokens` / `costUsd`.** Pre-deploy assistant messages with the flat shape produce no derived usage (deliberately — see "Old usage data shows zero" below).
- **JSONL `llm.response` event shape changed.** Per-call usage is now nested under `usage` instead of flat `inputTokens` / `outputTokens` / `cacheReadTokens` / `cacheCreationTokens` / `reasoningTokens` siblings. Field rename: `cacheCreationTokens` → `cacheWriteTokens` to match AI SDK V3 vocabulary.
- **SSE `llm.done` event shape changed.** `POST /v1/chat/stream` consumers that subscribe to per-iteration token counts must read `data.usage.inputTokens` / `outputTokens` / `cacheReadTokens` / `cacheWriteTokens` / `reasoningTokens` instead of the previously-flat `data.inputTokens` / `data.outputTokens` / `data.cacheReadTokens` / `data.cacheCreationTokens` / `data.reasoningTokens`. The `done` event's wire shape (`usage.costUsd` etc.) is unchanged.
- **`UsageReport` `cost.cacheCreation` / `tokens.cacheCreation` renamed to `cacheWrite`.** External consumers of `aggregateUsage` output read `undefined` until updated.
- **`UsageReport.tokens.input` is now non-cached input only.** Pre-fix it was the AI SDK V3 grand total (which already includes cache reads and cache writes). Post-fix it's the non-cached portion, so `tokens.input + tokens.cacheRead + tokens.cacheWrite` equals the grand total — same shape as the cost breakdown and the Anthropic dashboard. External consumers will see lower `tokens.input` numbers; switch to summing the three buckets for grand-total input.
- **Old usage data shows zero after deploy.** Conversations created before this release have token totals on disk in the old (flat-field) shape. The new readers do not migrate that data — they skip it and contribute zero. Existing-conversation rows in the conversation list and the usage dashboard show $0 / 0 tokens for activity that predates the deploy. New turns from the deploy onward show correct numbers (now including cache writes, which were under-billed before).
- **Conversations moved to top-level user-owned storage** (Stage 1). Operator action required during a maintenance window with the platform stopped:
  1. `bun run migrate:personal-workspaces` — renames each user's personal workspace to the canonical `ws_user_<userId>` form and stamps `isPersonal` / `ownerUserId`.
  2. `bun run migrate:conversations-to-top-level` — moves every `workspaces/<wsId>/conversations/<convId>.jsonl` to `conversations/<convId>.jsonl` and purges the removed `metadata.visibility` / `metadata.participants` event types from each file. Atomic per-conversation; crash-resumable.
  Both scripts hold a `.migration-lock` PID file at the work-dir root for the duration of the run, so concurrent invocations refuse to start instead of racing. The conversation script also requires `{workDir}/workspaces` and `{workDir}/conversations` to be on the same filesystem (`rename(2)` can't cross mount points) — deployments that split storage across mounts need to consolidate first.
- **Removed `manage_conversation` actions:** `shareConversation`, `unshareConversation`, `addParticipant`, `removeParticipant` are gone. Single-owner semantics; sharing returns in a future stage with policy gates. External callers that previously invoked these actions get an `unknown action` error.
- **`Conversation.visibility` and `Conversation.participants` removed from the schema.** Reads of pre-migration files that still carry these fields skip them at parse time; writes never produce them. `ownerId` is now required on every conversation file — pre-migration files without one fail to load with a clear "run the migration" hint.
- **`/v1/conversations/:id/events` no longer requires `X-Workspace-Id`.** The header is still honored when sent (validated for format + membership); absent → 200, present + malformed → 400, present + non-member → 403. Foreign-owner conversation → 403 `conversation_access_denied`; non-existent → 404 `not_found`. Web clients that already send the header keep working unchanged.
- **Personal workspaces enforce sole-owner-admin membership and freeze `isPersonal` / `ownerUserId` post-create.** `WorkspaceStore.update` / `addMember` / `removeMember` / `updateMemberRole` throw `PersonalWorkspaceInvariantError` on any member or identity-field mutation against a personal workspace; `WorkspaceStore.create` rejects a personal workspace whose initial members aren't exactly `[{ userId: ownerUserId, role: "admin" }]`. Operators with pre-existing multi-admin personal workspaces must run `bun run cleanup:personal-workspace-members --apply` to converge — `bundles`, `name`, `about`, `customInstructions` remain freely mutable.
- **Operator action — run `bun run migrate:user-creds` BEFORE deploying.** Moves `users/<id>/credentials/...` to the user's personal workspace; idempotent, shares `.migration-lock` with Stage 1. Without it the Stage 2 loader throws `LegacyOAuthScopeError`. Runbook: the Stage 2 deploy runbook (Redis registry schema cut per Q4 covered there).
- **`BundleRef.oauthScope: "user"` deleted** (T008). Loader throws `LegacyOAuthScopeError`; catalog field renamed `defaultScope` → `defaultBinding: "workspace" | "personal"`.
- **`installConnector(entry, wsId)`** — `wsId` now required (T010); pre-Stage-2 callers no longer compile.
- **`ToolSource.execute`** — `principalId` argument removed (T008); identity flows via `RequestContext` AsyncLocalStorage. Third-party implementers must drop the parameter.
- **`ChatRequest.workspaceId` / `ChatResult.workspaceId` removed** (T006). Chat is identity-bound; per-turn workspace is determined by the namespaced tool name.
- **`SessionMeta.workspaceId` hard-cut** (T007, Q4). `RedisSessionRegistry` ignores legacy `workspaceId` on read.

### Fixed

- **An automation run no longer looks like a conversation to the code asking.** The run's correlation id was carried in `RequestContext.conversationId`, so one field answered two questions and five of its nine readers took the wrong one: `skills__active_for` reported `Conversation not found: run_…`, the compose tools resolved a conversation that does not exist, `use_skill`'s already-delivered check read one instead of skipping as its comment claimed, the briefing appended usage to a missing path, and a skill an automation created was persisted as `origin: "chat"` with a run id attached. A run now carries `runId`; the two readers that want a correlation id (the usage ledger's `sessionId`, telemetry) read that. **Operator-visible**: task spans carry `run_id` instead of a run id mislabelled as `conversation_id`, and automation-created skills stamp `origin: "admin"`. The usage ledger's `sessionId` is unchanged in shape and still holds either id, separated by `origin` as before, so historical records and their aggregates are untouched. `skills__active_for` also accepts `conversation_id: "current"`, matching the `conversations__*` tools.
- **`conversations__list` reports message counts, not event counts.** The header read counted every line after line 1, which on an event-sourced conversation counts events — so a one-exchange chat listed as 5 messages, and every tool call added two more. The count now mirrors `conversations__get`'s rule (each user message, plus each run that produced a response), so the two surfaces agree about the same conversation. Affects `list`, `search`, `stats`, `export`, and `update`'s response; counts drop for every conversation created since the event format.
- **Entering an app no longer drops the workflow guidance its server publishes.** A bundle that publishes more than one skill lost all but the first on every turn sent from that app's panel — including `always` skills, which are the ones meant to be in context unconditionally. The bundle-skill pool excluded the entered *server*, on the premise that its guidance was recovered through the `<app-guide>` briefing; that briefing carries only the server's primary skill, so the premise held only while a server published exactly one. Deduplication is now per **skill**: the one body `<app-guide>` actually carries is withheld, and every other skill the same server publishes routes by its declared strategy, entered or not. Chats sent from outside the app panel were never affected, which is what made this present as an intermittent flap.
- **Renaming a conversation now takes effect.** `conversations__update` wrote the title to line 1 of the conversation file, but every reader projects it from the last `metadata.title` event — which the auto-titler appends on the first turn of every conversation. From that point on a rename was shadowed: the write landed, every surface kept showing the old title, and the tool reported the requested one back as success. An event-sourced conversation now gets an appended `metadata.title` event; a legacy one keeps the line-1 rewrite, because appending an event to it would switch the reader onto the event parser and hide its messages. The response is read back rather than assembled locally, so it also stops quoting line 1's stale token totals where `conversations__get` reports derived ones.
- **`conversations__update` / `__get` / `__fork` / `__export` can address the conversation you are in.** `id` is now optional on all four and resolves from the request when omitted — the same ambient fallback `skills__active_for` already used. An agent inside a chat is never told its own conversation id, so requiring one made the current conversation the only one these tools could not name; what an agent did instead was invent a placeholder and get `Conversation not found` back. The literal `"current"` is accepted as a spelling of the same thing (it cannot collide with a real id). Outside a chat the tools error and say to pass an id from `conversations__list`, rather than guessing.
- **A fruitless search no longer disables discovery three questions in.** The loop supervisor collapsed every non-advancing result for a tool to one fingerprint, so three `nb__search` calls with three *different* queries tripped it and dropped `nb__search` from the toolset — and since it is the only door to every proxied tool, the rest of the run answered "can this platform do X" with "no". Non-advancing results are now fingerprinted on their normalized input, so re-asking one question (case and whitespace folded) still trips at 3 while genuinely different questions do not. A separate per-tool non-advancing budget — 6 in a run, cleared by any advancing result — keeps the flail bounded.
- **`files__create` no longer saves a corrupted file when the body isn't base64.** `Buffer.from(body, "base64")` discards every character outside the base64 alphabet, so a caller that passed raw text got a successful create and a garbage file, with nothing to indicate it until someone opened it. The body is now validated before decoding and the call fails with what to do instead. `files__create` also takes `encoding: "base64" | "text"` (default `base64`): `"text"` writes the body verbatim as UTF-8, which is what an agent composing markdown, code, or CSV needs — hand-encoding a document to base64 is not something a language model does reliably, so "base64 or nothing" was never a contract it could hold to. **The default path narrows**: only the standard alphabet with `=` padding is accepted, and only line breaks may be interleaved. Unpadded base64, base64url (`-`/`_`), and space-interleaved base64 all decoded before and now error — padding and alphabet are what separate real base64 from prose, which without them passes every check. Re-encode such a body in the padded standard form; do not switch it to `encoding: "text"`, which would store the encoded string rather than the bytes.
- **Composio connectors that ask for a setup value now connect.** Toolkits whose auth config requires a connection-initiation field — WhatsApp's WhatsApp Business Account ID, Zoho's region, Jira's subdomain — failed the Connect click with `Composio rejected the connection initiate.` The redirect flow now runs on Composio's hosted Connect Link, which collects those fields from the connecting user. This also retires our use of a call Composio sunset for its managed OAuth configs on 2026-07-03, which would have broken *every* Composio OAuth connector on enforcement. Operator-visible: the consent dance now passes through a Composio-hosted page, so brand it (Composio dashboard → Project Settings → Auth Screen) and allow `dashboard.composio.dev` alongside `connect.composio.dev` if you filter egress. See the [Composio operator guide](https://docs.nimblebrain.ai/deploy/composio/).
- **The conversation list, search, and stats no longer cross the workspace wall.** Opening or refreshing a workspace could show conversations from another one — the Conversations app sent its workspace as a tool argument, and on the render before the host handshake resolved it had none to send, which the server read as "every workspace". `conversations__list` / `__search` / `__stats` now resolve the workspace from the request itself (`X-Workspace-Id`, already sent on every call) the way `files__*` does, and take no workspace argument at all. On `/mcp` a request with no workspace is refused rather than widened; REST keeps its existing behaviour of falling back to the caller's own personal workspace. Search was never scoped and returned message snippets from other workspaces on every query. **Breaking for `/mcp` clients**: `conversations__list` and `__search` now require an `X-Workspace-Id` header, and the `workspaceId` / `includeUnstamped` arguments are gone — a conversation is in the workspace its directory says, which is also what the locator has always read, so there is no longer an "unstamped" case for a caller to ask about. The workspace's briefing and `home__activity` counted other workspaces' chats and are scoped too, and the system prompt no longer tells the agent these tools search across all workspaces.
- **A chat's agent profiles and model-slot overrides now come from the workspace the chat runs in.** They were read from the caller's personal workspace, so a shared workspace's `agents` / `models` config never applied to chats held in it, and a user's personal overrides followed them everywhere. **Behaviour change for anyone who set either field**: personal-workspace overrides no longer apply to chats in a shared workspace, and a shared workspace's overrides now apply to every member's turns there. No migration — the fields are operator-set in `workspace.json` and have no UI writer.
- **The Context Ledger names skills instead of calling every connector's guidance "SKILL".** A skill published by a connector is a SEP-2640 resource whose id ends in `/SKILL.md`, so surfaces that derived a name from the id labelled all of them identically. `skills.loaded` now records each skill's own `name` and, for connector-published guidance, the `connector` that published it, and the rows read those. Rows also name the publishing connector where they used to print the wire tier `bundle` — connector skills are conventionally named for their job (`usage`, `workflows`), so the publisher is what distinguishes them. Runs recorded before the field existed still render (both read paths resolve a name).
- **"In context" no longer overstates the context window.** The `skills` row measures how much of the *system prompt* the composed skill bodies account for, not a fourth region beside it, so summing all four rows counted them twice (a turn showing 20.7k was really 14.5k). Both surfaces now total the three disjoint regions, state it once, and render skills indented under the system prompt. The `context.assembled` event's recorded `totalTokens` is unchanged; it is telemetry, and `compose__assembled_context` exposes the honest figure as a new `windowTokens` field and documents the overlap in its description. (`compose__effective_context`'s `totalTokens` does change — see below.)
- **`compose__effective_context` reports the prompt size in both modes.** With `run_id`, `totalTokens` returned the run's recorded four-row sum — the whole context window, plus the composed skill bodies a second time — while the same call without `run_id` returned the composed prompt. One field, two questions, so comparing a conversation across the two made the prompt look like it had grown by the size of tool descriptions and history. Historical mode now reads the recorded `system_prompt` row, the analogue of live mode's composed-layer sum. **Agent-visible value change on an existing tool**: a `run_id` call returns a smaller number than on 0.15.x. The tool description and the text summary now name the quantity; `windowTokens` on `compose__assembled_context` answers the other one.
- **History's message count is no longer labelled "turns".** `context.assembled` recorded the windowed *message* count in a field named `turns`, so a 47-message conversation read "47 turns". The field is `messages`; historical events are normalized on read.
- **Reconnecting a provider-minted connector no longer reports a spurious failure.** `startAuth` on a source that connects without an interactive flow (a provider-minted / already-authenticated connector — e.g. hitting "Reconnect" on a platform fleet connector) transitioned the source to `running` but then rejected the auth-URL promise, so the route logged `startAuth failed … already authenticated` and returned 500 even though the connector had reconnected. That headless success now resolves with no URL: the route returns `{ authorizationUrl: null }` and the UI refreshes state in place instead of redirecting to a nonexistent auth page.
- **App tools no longer surface a raw "MCP error … not started" when a remote source idle-closes.** A remote (fleet) MCP source whose long-lived connection idle-closes has its client torn down until the next `HealthMonitor` sweep; during that window a foreground app's tool call or `ui://` read surfaced the raw error (JSON-RPC `-32603`). `execute()` was also asymmetric with `readResource()` — it short-circuited on the `dead` flag, denying a still-live client the `recover()` self-heal that reads already got. `execute()` now dispatches a dead-but-live client (routing any throw through the same connection-down-only recovery), and both `execute()` and the app-surface `ui://` read re-establish a torn-down client on demand — `isStopped()`-gated so a deliberately-stopped source is never revived, and cooldown-floored so a persistently-down upstream isn't restart-hammered.
- **`nb__delegate` no longer hard-fails on an unknown agent profile.** Naming a profile that isn't configured returned an instant error and the delegation never ran — so skill protocols that named a profile the tenant hadn't defined (the model guessing `general`/`worker` → "Available profiles: none") failed outright. An unknown name now falls back to the default sub-agent and notes the fallback in the result; and the `agent` parameter is advertised only when the workspace has profiles configured, so the model isn't prompted to pick one that can't exist.
- **A resumed conversation stays sealed to its own workspace.** Tool, skill, app, and `## Workspace` context resolution followed the client's currently-focused workspace, so resuming a chat born in workspace A while focused on B answered with B's tools and reported B as "the workspace you're in" — a cross-workspace context leak. Resolution now keys off the conversation's authoritative workspace (`convWsId`, from its path) for the whole turn, matching how files already resolve; the focused workspace only chooses where a *new* chat is born.
- **Expected session-expiry no longer reported to Sentry as an error.** `captureLogout` was emitting an `involuntary logout: refresh_rejected` event on every definitive refresh-401 — i.e. every returning user whose refresh token had lapsed and every routine deploy of an environment left open, none of which is an error. `refresh_rejected` is now breadcrumb-only (it still decorates the trail of a real error that fires later); only `retry_401` — a freshly minted token rejected on the very next request, a genuine anomaly — is captured.
- **Multi-org WorkOS users no longer get involuntarily logged out (~hourly `retry_401`).** `WorkosIdentityProvider.refreshToken` minted the new access token without pinning `organizationId`, so WorkOS could refresh against the user's *default* org rather than the one the session was established under. The drifted token then failed `verifyRequest`'s `org_id` gate on the very next request — a refresh that "succeeds" yet yields a token the session rejects, surfacing as `involuntary logout: retry_401`. The refresh now pins the configured org. Additionally, `verifyRequest`'s previously-silent rejection paths now log a structured `reason` (`org_mismatch`, `token_expired`, `malformed_jwt`, …) so an involuntary logout names its cause instead of surfacing as a bare 401.
- **Removed a credential-leaking OAuth debug logger; added redacted connector-health logging in its place.** `NB_DEBUG_OAUTH_EXCHANGE` monkey-patched global `fetch` to log raw token-endpoint requests and responses at `warn` — access tokens, refresh tokens, client secrets, and auth codes in cleartext, bypassing field-level redaction. It was env-gated "temporary" diagnostic code left in `main`, re-armable by one env var. Deleted. In its place, `WorkspaceOAuthProvider` now emits **redacted** signals (booleans + lifetimes only, never token values): a `warn` when a token exchange returns **no refresh_token** (the connection can't refresh and will need a manual reconnect at access-token expiry — usually a missing offline-access param like `token_access_type=offline`), and a `warn` on the `reauth_required` flip. Same diagnostic power for the bug class it was added to chase, with zero secret exposure.
- **Remote OAuth connectors no longer drop to "Reconnect" on a transient blip.** A network error or 5xx from a connector's token endpoint during a mid-session access-token refresh was swallowed by the MCP SDK's `auth()` and converted into a fresh-authorization attempt, which the headless provider signals by throwing `UnauthorizedError` — read by `McpSource` as a dead credential, flipping the connection to `reauth_required` and dropping the connector from the run. A refresh-aware `fetch` on the OAuth transport now retries only the idempotent `grant_type=refresh_token` POST on transient failures (network/5xx/429/`temporarily_unavailable`) with bounded backoff, while a genuine `invalid_grant`/`invalid_client` still passes through to the real reconnect path. The connector-layer analog of the session-refresh fixes in [#434](https://github.com/NimbleBrainInc/nimblebrain/pull/434) / [#459](https://github.com/NimbleBrainInc/nimblebrain/pull/459).
- **Connector OAuth callbacks are public again.** A `requireAuth` `.use("*")` on the logout sub-app leaked onto `/v1/mcp-auth/callback` and `/v1/composio-auth/callback` (Hono flattens a sub-app wildcard onto sub-apps mounted after it), 401-gating their unauthenticated-by-design return leg — so a callback that landed on an origin without the user's session (e.g. the bouncer returning a custom-domain tenant to its branded host) never exchanged its `code` and wedged the connector at "Connecting…". `requireAuth` now attaches per-route to `/v1/auth/logout`.
- **Cache-write TTL is tiered by breakpoint stability.** The engine cached everything at a 1-hour TTL (2× base input), but after the rolling step-anchor the bulk of writes happen within a run — re-read seconds later, where the 1-hour premium (60% over 5-minute) buys nothing. The stable system+tools prefix now uses 1-hour (one write per run, worth keeping warm across a between-runs pause); the rolling history breakpoints use 5-minute. A meaningful cut in write cost on long conversations.
- **Cache-write cost is now priced per-TTL.** The cost model priced writes at the catalog's 1.25× 5-minute rate while the engine billed at the 2× 1-hour rate, under-reporting real cache-write spend by ~1.6× (verified against the live API's `cache_creation.ephemeral_1h_input_tokens`). The per-call 1h/5m split is captured on `TokenUsage` and each portion priced at its true rate; absent splits (legacy events) are treated as all-1h so historical figures stay accurate. Dashboards finally match the bill. **Operator note:** past cache-write spend re-prices ~1.6× higher the moment this deploys (it was genuinely under-reported), so month-over-month dashboards show a one-time step.
- **Final-iteration wrap-up hint no longer busts the system cache.** On a run's last allowed iteration the engine appended a "this is your final step" instruction to the system prompt — mutating the cached system block, which invalidated it and the entire message prefix after it on the final call of every run (a full-prefix re-write each run). The hint now rides a tail message in the volatile cache region instead, leaving the stable system prefix byte-identical so the final call reads it from cache.
- **Prompt cache no longer thrashes on long agentic runs.** The single cache breakpoint sat on the last *user* message, which is fixed for a run — so every iteration's freshly-appended assistant/tool content lived past it, uncached, and the growing prefix was re-sent at full input rate (measured: cache-write/non-cached dominated long-run cost, effective hit rate 14–40%). Cache-control placement moves out of the engine into a provider-scoped seam (`src/model/cache-policy.ts`, mirroring `applyReasoningReplayPolicy`); the Anthropic strategy places a rolling step-anchor breakpoint on each prior step's tail so the whole prior prefix is read back instead of re-written. Validated against the live API: expensive (non-cached + write) tokens drop ~70–100% on the within-run pattern. Other providers pass through (OpenAI caches prefixes automatically; the append-only prefix is all it needs).
- **Reasoning blocks are retained on replay instead of stripped per turn.** The replay policy stripped older Anthropic thinking blocks keyed on "is this the latest assistant message" — so the instant a turn stopped being latest its bytes changed, invalidating the cached prefix from that point. With the rolling step-anchor that bust landed just behind the anchor on every iteration, forcing a full re-write of the growing prefix. Under prompt caching, retained reasoning is written to cache once and read back cheaply, so the strip's token savings were dwarfed by the re-writes it forced. Stripping is only cache-safe beyond a stable frozen boundary (compaction), and compaction summarizes old turns into a reasoning-free block anyway, so the per-turn strip helper is removed rather than kept dormant. OpenAI/Gemini already retained reasoning (correctness); now all providers do.
- User- and workspace-scope `type: skill` skills now load instead of silently doing nothing: the trigger/keyword matcher runs per-request over the merged org+workspace+user pool (it was boot-only and never scanned those tiers), strategy-less skills created via `skills__create` auto-resolve to `loading-strategy: always` written to disk, and `skills__list` flags any skill that would never load. ([#391](https://github.com/NimbleBrainInc/nimblebrain/issues/391))
- Automation field edits no longer fail silently: a rejected update (e.g. an out-of-range `maxIterations`) now surfaces the error in the detail view instead of swallowing it and snapping the field back to its old value.
- Automation `maxIterations` cap raised from 15 to 50 (the engine's absolute ceiling), and the create-form default from 5 to 25. The old 5-step default amputated analytical automations mid-run — they hit the cap, produced no final output, and reported "No output captured." Iterations are a runaway backstop, not a cost budget; `maxInputTokens` and `maxRunDurationMs` bound per-run cost directly.
- **A stalled model stream no longer burns an entire run.** A model call that hung — connecting, prefilling, or mid-stream — used to block the agent loop until the run-level `maxRunDurationMs` fired, so one upstream stall consumed a whole chat/automation budget (and left automations with no deliverable). A per-call watchdog now bounds it in two regimes: a generous first-content deadline (covers connect + prefill, which scales with prompt size) and a tight inter-part idle once tokens are flowing. A stall before any output is retried via `withRetry` (transient, nothing streamed yet); a stall mid-stream fails cleanly rather than re-streaming deltas the client already saw.
- Gmail connector allowlist now exposes `GMAIL_DELETE_DRAFT` so agents can prune stale drafts instead of leaving every revision in the thread. (`GMAIL_DELETE_MESSAGE` deliberately omitted — irreversible permanent delete of arbitrary mail; use the already-exposed `GMAIL_MOVE_TO_TRASH` for reversible removal.) Note: destructive Gmail tools are also gated at the Composio project level — enable them on the gmail `auth_config` in the Composio dashboard and re-install the connector per workspace (the tool filter is baked at session-create time).
- `manage_users delete` is now a **soft delete**: it stamps a `deletedAt` tombstone on the local profile and revokes access (the auth layer denies any request from a deactivated user, both web and `/mcp`) instead of hard-deleting the WorkOS identity. Previously the WorkOS user was destroyed while the local profile and workspace memberships were left behind — so the deleted user still showed in the UI, and re-adding them minted a fresh WorkOS ID that orphaned every prior workspace membership. Deactivated users now stay listed and flagged "Deactivated" in **both** the org Users tab and workspace member lists, and `manage_users restore` re-enables them. The identity ID is preserved across deactivate/restore. The last-owner (org) and last-admin (workspace) guards count only *active* principals, so a deactivated owner/admin can't be mistaken for a live one and let you strand the org/workspace with zero functional admins.
- Heal script for tenants whose legacy personal-workspace slugs use the 16-char truncated form unrecognized by `migrate-personal-workspaces.ts` — run `scripts/heal-truncated-personal-workspaces.ts` after the Stage 1 migrations to rename truncated personal workspaces to the canonical form, stamp identity fields, delete empty canonical stubs, and rewrite conversation `workspaceId` refs.
- `runtime.chat()` now honors an `AbortSignal` end-to-end (`ChatRequest.signal` → `EngineConfig.signal` → iteration loop + every tool call). Callers racing the chat against a deadline (notably the automations executor's per-run budget) now cancel in-flight LLM/tool work instead of orphaning it; HTTP `/v1/chat` and `/v1/chat/stream` also forward `request.signal`, so client disconnect cancels engine work ([#251](https://github.com/NimbleBrainInc/nimblebrain/pull/251)).
- Task-augmented MCP tools no longer report a false `MCP error -32603: Task <id> failed` when the server stored a usable `tasks/result` payload; the engine refetches and surfaces the real content ([#245](https://github.com/NimbleBrainInc/nimblebrain/pull/245)).
- `automations__run` no longer hits `MCP error -32001: Request timed out` on multi-minute automations; `handleRun` caps its sync wait below the SDK's 60 s request timeout and returns a `{ status: "dispatched" }` envelope when the run outlasts the window, with the scheduler tracking it in the background ([#245](https://github.com/NimbleBrainInc/nimblebrain/pull/245)).
- Synthesized automation failure records now carry the real `startedAt` from dispatch time instead of the catch-clause instant, so operators can tell a long hang from a setup crash ([#245](https://github.com/NimbleBrainInc/nimblebrain/pull/245)).
- Timed-out (and cancelled) automation runs now report the real `inputTokens`/`outputTokens`/`toolCalls`/`iterations` and `conversationId` for the work done before the wall clock killed them, instead of `0/0/0/0`. `executeTask` honors its documented contract — returning a result on abort instead of throwing it away — so cost monitoring and token-budget auto-disable see actual usage, and the run links to its conversation for post-mortem.
- Agent runs no longer burn the iteration budget on a stuck MCP tool. Three additions cooperate: outbound args drop no-op optional values (empty strings, nil UUIDs, empty arrays) that some upstream APIs reject as malformed; tool results whose text looks like an upstream error (e.g. `Ran into an error: AxiosError…`) but ship `isError: false` are promoted to `isError: true` so downstream layers see truth; a per-run supervisor watches each tool for identical-fingerprint repeats and, on the 3rd, replaces the result with a stop-directive plus a one-shot system-prompt nudge so the model surfaces the error and ends the run instead of looping to `max_iterations`.
- Vision content is no longer dropped after the first turn of an agentic loop. Uploaded images survived turn 1 (the in-memory message still carried the bytes) but disappeared on turn 2+ — the user-message reconstructor filtered everything except text. Multi-turn flows like "extract from screenshot, then call a CRM tool" now work end-to-end.
- `estimateCost` no longer double-bills reasoning tokens for models with a separate `cost.reasoning` rate. Reasoning is a subset of `outputTokens` per the V3 usage spec; the corrected formula splits rather than adds.
- `estimateCost` no longer double-bills cache tokens. AI SDK V3's `inputTokens.total` is the grand total of all input-side tokens (including cache reads and cache writes); the prior formula charged the grand total at the full input rate AND charged the cache subsets again at their respective rates — a ~3x overcharge on cache-heavy turns. Fix subtracts cache subsets from the input total before applying the input rate. ([#140](https://github.com/NimbleBrainInc/nimblebrain/issues/140), [#151](https://github.com/NimbleBrainInc/nimblebrain/pull/151)).
- Live per-turn `usage.costUsd` (returned via the `done` SSE event and `POST /v1/chat`) now correctly includes cache write and reasoning costs. Previously the runtime layer dropped these fields before computing cost, under-billing cache writes and mis-billing reasoning. Cost is now computed at the API boundary from the canonical `TokenUsage` struct, so the live wire-format value matches what the catalog math produces.
- `EventSourcedConversationStore.fork()` now wraps each forked `llm.response` in synthetic `run.start` / `run.done` bookends. Previously, `history()` on a forked event-format conversation returned only user messages — the reconstructor only emits assistant turns inside an active run scope, and the unbookended events fell through to the "skip events outside a run context" branch. Independent of the cost work; surfaced during PR #151's QA.
- `stopReason` now reflects the model's real finish reason (length, content_filter, error, other) instead of always reporting `complete`; per-call `finishReason` is persisted on `llm.response` events and forwarded over SSE ([#105](https://github.com/NimbleBrainInc/nimblebrain/pull/105)).
- Settings pages now share a unified layout system (`SettingsFormPage` / `ListPage` / `DashboardPage` / `AppPanelPage`) that owns header, width, save bar, and section spacing — replacing per-tab variations of all four. Bundle settings panels render inside settings chrome (back-link, title, "provided by" footer) instead of a chromeless iframe. Org-admin "manage workspace" back button now goes to the right route.
- `maxOutputTokens` is now derived per-call from the synced model catalog (`limits.output`) instead of a static 16,384 default — Opus 4.7 jumps from 16k → 128k, Sonnet 4.6 → 64k. Operator-pinned values still win, clamped to the model's catalog max ([#104](https://github.com/NimbleBrainInc/nimblebrain/pull/104)).
- Default thinking config now works on Claude Opus 4.7. The engine translates `thinking.type=enabled` (which Anthropic rejects for that model) into `adaptive` + `output_config.effort`, gated on a per-model `supportsEnabledThinking()` predicate ([#118](https://github.com/NimbleBrainInc/nimblebrain/pull/118)).
- Skills tool surface honest about its input contract: `skills__list` text emits a row per skill with id+metadata (was counts only); `scopeOfPath` no longer falsely classifies bare ids as `bundle`; path-validation error names the actual roots (`org/workspace/user/bundle`); mutation tools' descriptions point callers at `skills__list` for ids; `bundleNotMutable()` returns the structured `suggested_action` shape from the design doc.
- `skills__active_for` now defaults `conversation_id` to the current conversation when called from inside a chat (the agent doesn't know its own conv id; requiring it forced agents to skip the tool). Explicit ids still win; calls outside a chat scope error with a clear message instead of silently falling back.
- Files-app uploads no longer fail with `Payload too large`. Picker bytes now flow through `POST /v1/resources` (multipart, workspace-scoped) instead of being base64-encoded into a `tools/call` argument; `isAllowedMime` strips Content-Type parameters, fixing a latent miss in the chat ingest path too ([#93](https://github.com/NimbleBrainInc/nimblebrain/pull/93)).
- `nb__read_resource` and `POST /v1/resources/read` resolve `ui://` resources published by platform built-ins (settings, home, automations, conversations, files, usage, nb). Previously the structural type guard couldn't distinguish two divergent `readResource` shapes and silently skipped any platform source ([#90](https://github.com/NimbleBrainInc/nimblebrain/issues/90)).
- `/v1/resources/read` request-context propagation. The route handler wasn't wrapping its source-call in `runWithRequestContext`, so callback-form resource bodies that called `runtime.requireWorkspaceId()` (e.g. `instructions://workspace`) threw and surfaced as 404 "not found." Wrapping matches the existing `handleCallTool` pattern.
- `GET /mcp` returns 405 instead of opening an idle SSE listener. The standalone server→client stream was held open with nothing to write, so Bun's `idleTimeout` (and any L7 proxy: Vite dev, ALB, nginx) silently killed it — surfacing as `[vite] http proxy error: /mcp` + `socket hang up` and exhausting the SDK client's reconnect budget. The MCP SDK treats 405 as "no GET-style listening" and runs POST-only ([#138](https://github.com/NimbleBrainInc/nimblebrain/pull/138)).
- Settings model-picker no longer 404s non-Anthropic models. The dropdown now encodes `provider:` into option values (was `m.id` alone, dropping the provider grouped one level up at `optgroup`); the runtime resolves bare ids in the catalog so existing tenant configs continue to route correctly without re-saving. `getModelSlots()` returns fully-qualified ids so cost aggregation, capability checks, max-output and thinking resolvers, and log lines all see consistent shape — a tenant whose disk had bare `gemini-3.1-pro-preview` was previously routing to the Anthropic API ([#143](https://github.com/NimbleBrainInc/nimblebrain/pull/143)).
- PDF resource_link previews render again in Chromium / Arc. Chat iframe no longer sets `sandbox="allow-scripts"`, which made the frame an opaque origin and caused Chromium to refuse navigation to parent-owned `blob:` URLs (Arc surfaced this as "This page has been blocked by Arc"). PDFium's separate sandboxed renderer process is the actual security boundary for `application/pdf`; iframe `sandbox` is for untrusted HTML ([#144](https://github.com/NimbleBrainInc/nimblebrain/pull/144)).

## [0.3.0] - 2026-04-16

### Security

- **Scope bundle instances and placements by workspace.** When two workspaces had the same bundle installed, `Runtime.getBundleInstancesForWorkspace` returned instances from both (filtering only by `serverName`), causing briefing facets and the apps list to read entity data from other workspaces. `PlacementRegistry.unregister` was also global-per-serverName, so re-seeding in a second workspace silently wiped the first workspace's nav entries. Both paths are now workspace-scoped.

### Breaking (internal API)

Downstream forks or consumers that extend `BundleLifecycleManager` will need to update callsites:

- `installNamed(name, registry, env?)` → `installNamed(name, registry, wsId, env?)`
- `installLocal(bundlePath, registry, env?)` → `installLocal(bundlePath, registry, wsId, env?)`
- `installRemote(url, serverName, registry, transportConfig?, ui?, trustScore?)` → `installRemote(url, serverName, registry, wsId, transportConfig?, ui?, trustScore?)`
- `uninstall(nameOrPath, registry)` → `uninstall(nameOrPath, registry, wsId)`
- `startBundle(serverName, registry)` → `startBundle(serverName, wsId, registry)`
- `stopBundle(serverName, registry)` → `stopBundle(serverName, wsId, registry)`
- `recordCrash(serverName)` / `recordRecovery(serverName)` / `recordDead(serverName)` each gain a required `wsId` second argument.
- `BundleInstance.wsId` is now required (was optional). Every instance belongs to exactly one workspace; global/platform sources are represented as `InlineSource`, not `BundleInstance`.
- `PlacementRegistry.unregister(serverName, wsId?)` now scopes to `(serverName, wsId)` only. Passing no `wsId` removes only global entries; passing a specific `wsId` leaves other workspaces untouched.

### Migration

`installNamed` previously wrote bundle subprocess data to `{workDir}/data/{bundle}`. It now writes to `{workDir}/workspaces/{wsId}/data/{bundle}`, matching `seedInstance`. Self-hosted deployments that installed bundles via the runtime install path (rather than the startup seed path) should move existing data directories to the workspace-scoped layout or accept that old data is orphaned.

### Tooling

- `bun run verify` is now true CI parity. Added `format:check` (previously missed by CI) and split into `verify:static` + `verify:test-unit`; `ci.yml` invokes those subscripts so `package.json` is the single source of truth for "what CI runs."

### Other

- Auto-build bundle UIs during Docker image build and local `dev`.
- Update GitHub Actions workflows to latest major versions.
