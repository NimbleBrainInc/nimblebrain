This guide takes a deployment from the default look to your brand: what to prepare, how to choose colours that the runtime accepts, where the configuration goes, and how to check the result. Every key it uses is described in the [Branding reference](/config/branding/).

## What changes and what doesn't

A `brand` block changes what a person reads and sees:

- **Product name**: the browser tab title, the agent's identity line ("You are a helpful assistant powered by …"), the "Leaving …" dialog before an external link, OAuth success and error pages, and error messages that name the product.
- **Logo, mark and favicon**: the sign-in page, the sidebar, and the browser tab.
- **Palette, typefaces and corner radius**: the shell, and every embedded app, through the theme tokens the shell injects.
- **Default theme**: the colour theme a person starts in until they choose one.
- **OAuth consent screens**: the name, homepage and logo a connector vendor shows when someone connects an account.

It does not change:

- **Wire identifiers.** Tool namespaces (`nb__`), metadata keys (`ai.nimblebrain/*`), the `NB_` environment prefix and the `nimblebrain.json` filename identify the software to other software, not to a person.
- **Your identity provider's hosted sign-in page.** The sign-in page links to your identity provider (WorkOS, or your OIDC provider) for the password or SSO step. Brand that page in the provider's own dashboard.
- **Type scale and shadows.** Sizes, line heights and elevation stay as shipped, so layouts keep their proportions under any typeface.

## Prepare your assets

Publish every file at a stable `https://` URL before you reference it. A URL that returns 404 shows a broken image, not the default artwork.

| Asset | Used for | Notes |
|---|---|---|
| Full logo, light mode (`logo.light`) | Sign-in page, expanded sidebar | SVG or PNG. Dark artwork for a light background. |
| Full logo, dark mode (`logo.dark`) | The same places in dark mode | Light artwork for a dark background. |
| Mark (`logo.mark`) | Collapsed sidebar | Square. One file serves both modes, so use a mark that reads on light and dark. |
| Raster mark (`logo.raster`) | OAuth consent screens at connector vendors | **PNG**, around 128×128. Several identity providers and vendors refuse to render an SVG logo there. |
| Favicon (`favicon`) | Browser tab | PNG or ICO. |
| Fonts | Shell and embedded apps | One `.woff2` file per face (a variable font is one file). |

Set `name`, `logo` and `favicon` together. A brand with a name but no logo keeps the bundled NimbleBrain artwork, with your name as its alt text.

**Fonts must be files you may redistribute.** You serve them to every visitor's browser, so check the licence. Self-host the `.woff2` files; a Google Fonts stylesheet URL (`https://fonts.googleapis.com/css2?…`) is rejected, because embedded apps load faces from the file URL and cannot follow a stylesheet.

**The font host must answer every origin.** Embedded apps run in sandboxed iframes with an opaque origin, so their font requests arrive with `Origin: null`. The only response header that admits them is `Access-Control-Allow-Origin: *`. Check each font URL:

```bash
curl -sI -H "Origin: null" https://static.example.com/brands/acme/fonts/instrument-sans.woff2
```

Look for these lines in the response:

```text
HTTP/2 200
content-type: font/woff2
access-control-allow-origin: *
```

A missing `access-control-allow-origin`, or one that names your domain instead of `*`, is the common failure: the shell renders your font, while every app silently falls back to the next family in its `stack`.

## Choose colours that pass

The runtime checks your palette at startup against every contrast pair the default palette is held to, in light and dark mode, and refuses to start if any pair falls below **4.5:1** (WCAG 2.2 AA for body text). Work through it in this order:

<Steps>

1. **Start from the accent and the backgrounds.** Set `primary` (links, buttons, focus) and the grounds: `background`, `card`, `popover`, `muted`, `sidebar`. Each value is a `[light, dark]` pair of `#rrggbb` colours. Add `foreground` and `muted-foreground` if your grounds are tinted.

2. **Leave the `-foreground` partners out at first.** For any base token you set without its `<x>-foreground`, the runtime derives one per mode: white or black, whichever contrasts more with your base. Set one yourself only when you want a specific colour on that fill.

3. **Start the runtime and read the error.** A failing palette stops startup with a message naming the mode, the pair, the ratio and both colours:

   ```text
   Invalid brand in config: light mode: success on success/10 over background is 4.36:1 (#0f7a4f on #e3eade), below the 4.5:1 WCAG AA minimum
   ```

   Read it as: in light mode, `success` text over a 10% tint of itself on your `background` measures 4.36:1. The first colour is the text and the second the ground it was measured on, after compositing.

4. **Adjust by the smallest step.** Move the token the error names first, and only by as much as it needs: darken text in light mode, lighten it in dark mode. Restart, and repeat until the runtime starts. Small steps keep the colour recognisably yours.

</Steps>

### Worked example

The ACME brand in the [reference example](/config/branding/#example) uses a warm paper background, `#FAF6EE`, and leaves the status colours at their defaults. The runtime refuses it with the error above: the default green, `#0f7a4f`, clears 4.5:1 on white but only 4.36:1 over its own tint on the warmer, darker paper.

The fix is one token, one mode. Darkening the light-mode green to `#0D6B45` brings the same pair to 5.25:1, and dark mode is already fine, so its dark value stays as shipped:

```json
"success": ["#0D6B45", "#3fbf85"]
```

The other status colours stay at their defaults. They carry meaning, so change them only when a pair requires it.

## Write the block

**Self-hosted.** Add a top-level `brand` key to `nimblebrain.json` in the runtime's working directory (`/data` in the container image, so the `workspace` volume under [Docker Compose](/deploy/docker/)). The [reference example](/config/branding/#example) is a complete block to start from. To start everyone in light mode, set `defaultTheme`; a person can still switch, and their choice wins from then on:

```json title="nimblebrain.json"
{
  "brand": {
    "name": "ACME",
    "defaultTheme": "light",
    "logo": { "light": "…", "dark": "…", "mark": "…", "raster": "…" },
    "favicon": "…",
    "colors": { "primary": ["#B53707", "#FF8A4C"] }
  }
}
```

**Helm.** The runtime chart exposes a `tenant.brand` value and renders it verbatim as the `brand` block of `nimblebrain.json`. Put the same object there in your values file.

`brand` is read at startup, so restart the runtime after a change. It is not read from `nimblebrain.overrides.json`.

## Verify

<Steps>

1. **The runtime serves your brand.** It answers without a session:

   ```bash
   curl -s https://agents.example.com/v1/brand
   ```

   You should see your block, with each font role's files listed under `faces`. `{}` means no brand is configured.

2. **The sign-in page, in both modes.** Open the deployment in a private window. The tab title, favicon, logo, colours and typefaces should all be yours. Press **Cmd+Shift+L** (Mac) or **Ctrl+Shift+L** to switch between light and dark mode and check the other logo and palette.

3. **An embedded app.** Sign in and open an app such as Files. Its buttons and links should use your accent, and its text your `sans` typeface. If the shell shows your font but the app does not, recheck the font host's `access-control-allow-origin` header.

</Steps>

## Known limits

- **The default title shows briefly, and in link previews.** The page's static HTML carries the default tab title and favicon. A first visit shows them until the brand arrives, and a later one until the page's script starts, which then paints the brand from the browser's cache. Link previews in chat apps and social cards never run the script, so they always show the default.
- **Apps already open keep the previous look.** An embedded app reads the theme when it loads. After a brand change, an app that was open shows the new look once it is reopened or the page reloads.
- **Vendor consent screens update on reconnect.** A connector vendor stores the name, homepage and logo it received when the connection first registered. Existing connections show the old values until they are disconnected and connected again; new connections use the new ones.
