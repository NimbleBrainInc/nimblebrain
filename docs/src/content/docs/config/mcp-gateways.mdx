An **MCP gateway** is a third party that runs MCP servers so you do not have to. Composio, Smithery, MCP360, and Glama all fit that description, and they market themselves with overlapping words: gateway, aggregator, registry, hub. The words do not tell you how to connect one. The mechanism does.

Gateways divide into two kinds, and the kind decides who configures what.

<Aside type="note" title="This page is about outbound connections">
Here you are pointing NimbleBrain **at** someone else's MCP servers. Pointing an external client such as Claude Desktop **at** NimbleBrain runs the other direction and lives under [Connect via MCP](/connect/external-clients/).
</Aside>

## The two mechanisms

**A brokered provider** holds credentials and mints a session per connection. The platform calls the vendor's API, receives an MCP endpoint scoped to one workspace, and connects to it. Each workspace gets its own connection at the vendor, so the vendor can tell them apart, and revoking one leaves the others alone. You configure the broker once, platform-wide, and workspace admins install connectors that reference it. Composio and Smithery work this way.

**A hosted remote server** publishes an MCP endpoint and one account-wide API key. Every workspace on your instance reaches the same endpoint with the same key. There is no per-workspace connection at the vendor, so the vendor sees one caller no matter how many teams you have. MCP360 and Glama work this way.

The difference is not a quality judgment. A broker earns the extra machinery when the vendor holds a relationship the platform cannot hold itself, such as an OAuth app you lack verification for. A hosted server with a single key is simpler and fine when the tools it exposes need no per-user identity.

## Where each vendor lands

| Gateway | Mechanism | Per-workspace identity | Status |
|---|---|---|---|
| [Composio](https://composio.dev) | Brokered provider | Yes | Supported. See the [Composio guide](/deploy/composio/). |
| [Smithery](https://smithery.ai) | Brokered provider | Yes | Supported. See the [Smithery guide](/deploy/smithery/). |
| [MCP360](https://mcp360.ai) | Hosted remote server, one account key | No | Needs a credential provider. See below. |
| [Glama](https://glama.ai) | Hosted remote server, one account key | No | Needs a credential provider. See below. |

## Adding an account-key gateway

An account-key gateway installs as a normal catalog entry using `auth: provider`. That kind names a **credential provider** which supplies the transport credential server-side, so the endpoint comes from the catalog and the key never touches workspace state.

A catalog entry looks like this:

```yaml
servers:
  - name: ai.example-gateway/search
    title: Example Gateway — Search
    description: What this endpoint gives the agent
    version: "1.0.0"
    remotes:
      - type: streamable-http
        url: https://gateway.example.com/v1/search/mcp
    _meta:
      ai.nimblebrain/connector:
        auth: provider
        providerAuth:
          provider: example-gateway
          config: {}
        tags: [search]
```

The `providerAuth` block is operator-authored and copied verbatim into the connector's transport at install. The install path also re-reads the entry from the operator-published catalog and refuses a `provider`-auth install from any entry it cannot verify, so a workspace admin cannot forge one that spends the platform's credential against an endpoint of their choosing.

What that entry needs from the platform is a credential provider registered under the name it references. The provider resolves the account key and attaches it as a header. Registering one is a small addition beside the built-in credential providers, and `src/connectors/providers/smithery/transport-credential.ts` is the closest model.

<Aside type="caution" title="A gateway is not the fleet rail">
`auth: provider` also carries the platform's own `minted` connectors, which may reach in-cluster `http://` endpoints. A gateway does not inherit that exception. Its URL takes the full SSRF check, so the endpoint must be a public `https` host.
</Aside>

MCP360 and Glama both fit this shape and neither ships a credential provider today, so add one before publishing catalog entries for them.

## Choosing between them

If a vendor offers both a brokered path and a bare endpoint, prefer the broker. Per-workspace connections give you attribution, independent revocation, and a rate limit that one noisy workspace cannot exhaust for everyone. A single account key gives you none of those: the vendor sees one caller, and you cannot tell from their side which team spent the quota.

If no gateway is involved at all, prefer `auth: dcr`. It needs no operator setup and puts no third party in the credential path.
