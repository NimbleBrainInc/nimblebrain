`instance.json` configures **how users authenticate** to a NimbleBrain deployment. It lives at `<workDir>/instance.json` and is the single source of truth for the deployment's auth adapter and org identity.

<Aside type="note">
  Authentication is configured **here**, not through an environment variable. There is no `NB_API_KEY` auth gate.
</Aside>

## The file is required

`serve` does not start without `<workDir>/instance.json`. It exits with an error naming the path and the two ways to write it. A missing file never selects an identity provider, because a deployment that lost its config would otherwise admit every caller as an owner.

The dev launchers (`bun run dev` and its variants, including `dev:worktree`) write the `dev` adapter into a workdir that has no `instance.json`, and leave an existing one alone. With Docker Compose, write the file next to `docker-compose.yml`; it is mounted into the container's workdir.

## Adapters

The `auth.adapter` field selects the identity provider: `dev`, `oidc`, or `workos`.

<Tabs>
  <TabItem label="Dev">
    ```json title="instance.json"
    {
      "auth": {
        "adapter": "dev"
      }
    }
    ```

    No login. Every request authenticates as one built-in identity (`usr_default`, org role `owner`), with no credential checked. It passes the same authorization checks as any other user, as the org owner and an admin of its workspaces. Use it on your own machine only: anyone who can reach the server is that owner.
  </TabItem>
  <TabItem label="OIDC">
    ```json title="instance.json"
    {
      "auth": {
        "adapter": "oidc",
        "issuer": "https://auth.example.com",
        "clientId": "nimblebrain-app",
        "allowedDomains": ["example.com", "acme.com"],
        "jwksUri": "https://auth.example.com/.well-known/jwks.json",
        "owners": ["founder@example.com"]
      },
      "orgName": "Acme",
      "orgId": "org_acme"
    }
    ```

    Verifies incoming Bearer JWTs against the provider's JWKS. Users whose email domain is not in `allowedDomains` are rejected.
  </TabItem>
  <TabItem label="WorkOS">
    ```json title="instance.json"
    {
      "auth": {
        "adapter": "workos",
        "clientId": "client_01ABC...",
        "organizationId": "org_01XYZ...",
        "apiKey": "sk_live_...",
        "authkitDomain": "myapp",
        "adminRoleSlugs": ["org-admin"],
        "firstPartyClientIds": ["client_01DEF..."],
        "owners": ["founder@example.com"]
      },
      "orgName": "Acme",
      "orgId": "org_acme"
    }
    ```

    WorkOS-managed auth with AuthKit. Supports the redirect login flow for the web shell and, when `authkitDomain` is set, Bearer-JWT auth on each workspace's `/mcp/<workspaceId>` for external MCP clients.
  </TabItem>
</Tabs>

## Top-level fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `auth` | `object` | Yes | The auth adapter config. See per-adapter fields below. |
| `orgName` | `string` | No | Human-readable organization name. |
| `orgId` | `string` | No | Stable organization identifier. |
| `integrations` | `object` | No | Free-form integration config bag. |

## OIDC adapter (`auth.adapter: "oidc"`)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `adapter` | `"oidc"` | Yes | Selects the OIDC adapter. |
| `issuer` | `string` | Yes | OIDC issuer URL. |
| `clientId` | `string` | Yes | OAuth client id registered with the provider. |
| `allowedDomains` | `string[]` | Yes | Email domains permitted to sign in. A verified identity whose domain isn't listed is rejected. |
| `jwksUri` | `string` | No | JWKS endpoint override. Discovered from the issuer's `.well-known` when omitted. |
| `owners` | `string[]` | No | Emails of the org's owners. A listed user is an owner on every sign-in (matched case-insensitively), and cannot be demoted or deactivated from the Users page; remove them here first. Since only an owner can make another, this is where the first owner comes from. Each entry must be an email address. See [Owners from `instance.json`](/using/users/#owners-from-instancejson). |

## WorkOS adapter (`auth.adapter: "workos"`)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `adapter` | `"workos"` | Yes | Selects the WorkOS adapter. |
| `clientId` | `string` | Yes | WorkOS Client ID (`client_…`). |
| `organizationId` | `string` | No | WorkOS Organization ID — scopes auth to a specific customer org. Every token, whether from the web login or AuthKit, must be issued for this org (its `org_id` claim), and its user must be a member of it. An empty or whitespace-only value is rejected at startup. Omitting the field admits every user in the AuthKit environment, so omit it only when this instance owns the whole environment. |
| `apiKey` | `string` | No | WorkOS API key. Can also come from the `WORKOS_API_KEY` env var. |
| `authkitDomain` | `string` | No | AuthKit subdomain for MCP OAuth (e.g. `"myapp"` → `myapp.authkit.app`). When set, `/mcp/<workspaceId>` accepts AuthKit-issued Bearer JWTs whose audience is exactly that URL, and exposes `/.well-known/oauth-protected-resource/mcp/<workspaceId>` for MCP client discovery. AuthKit needs a resource indicator covering `<origin>/mcp/*` for each public host, or it ignores the client's `resource` and every token is refused. |
| `adminRoleSlugs` | `string[]` | No | WorkOS membership role slugs that map to the app `admin` role (case-insensitive). Omit to use the defaults `["admin", "owner"]`. An explicit list **replaces** the defaults and must contain at least one non-empty slug — an empty list is rejected at startup. Set this when your WorkOS org's admin role carries a custom slug. |
| `firstPartyClientIds` | `string[]` | No | Client IDs of your own apps that sign users in through AuthKit and call the REST API with the resulting token, such as a chat-channel bridge. See [First-party clients](#first-party-clients). Takes effect only with `authkitDomain` set, since without it no token is recognized as AuthKit-issued. Omitted or empty, no AuthKit token is first-party. |
| `owners` | `string[]` | No | Emails of the org's owners. A listed user is an owner on every sign-in (matched case-insensitively), and cannot be demoted or deactivated from the Users page; remove them here first. Since only an owner can make another, this is where the first owner comes from. Each entry must be an email address. See [Owners from `instance.json`](/using/users/#owners-from-instancejson). |

The sign-in callback is always `<public origin>/v1/auth/callback`, built from the deployment's [public origin](/config/environment/#nb_public_origin). Register that URL as a redirect URI in the WorkOS dashboard; `instance.json` has no field for it.

### First-party clients

An AuthKit token is normally a resource token: valid only at the `/mcp/<workspaceId>` its audience names, and refused on every `/v1/*` route. An app you run yourself that obtains tokens from AuthKit without naming a resource cannot use them anywhere, so list its client ID in `firstPartyClientIds`.

A token whose signed `client_id` claim is listed is first-party, like a web login session: it is admitted on every route, and workspace membership gates what it reaches. Every other AuthKit token is unchanged.

The token's audience never makes it first-party. A token an external MCP client refreshes without a `resource` carries the same audience as your app's token, so only the client it was issued to tells them apart.

The field fails closed: missing, empty, or a client ID that isn't listed, and the token stays a resource token.

<Aside type="caution">
  For WorkOS, prefer the env var `WORKOS_API_KEY` over `auth.apiKey` in production so the secret doesn't sit in a config file that lands in version control or backups.
</Aside>

## Validation

`instance.json` is validated at load:

- Missing or non-object `auth` throws.
- An unknown `adapter` value (anything other than `dev` / `oidc` / `workos`) throws, naming the accepted set.
- Each adapter's required fields are type-checked; a missing or wrong-typed field throws with a field-specific message.
- A malformed file, like a missing one, stops the deployment at startup. An auth misconfiguration fails loud, never open.

The file is written atomically (temp-then-rename) whenever the runtime persists changes to it.
