The **Plugins → Browse plugins** list is built from **catalogs**: [AI Catalog](https://ai-catalog.io/spec/) listings the operator names in [`catalogs`](#catalogs-what-browse-lists). Each listed item is a row, addressed `name@catalog` (`ahrefs@nimblebrain`). Browse reads the listings only; it never opens a plugin archive.

Installing a row installs a **plugin**: the item at the row's address, from that item's own artifact. The runtime fetches the entry's `url` once and installs only bytes that match its `digest` (an entry carrying its artifact inline as `data` is verified over the data's [canonical JSON form](https://www.rfc-editor.org/rfc/rfc8785)). An artifact that does not match is refused and nothing is installed. Each server's record, a [`ServerDetail`](https://github.com/modelcontextprotocol/registry), comes from the archive (`ai.nimblebrain/servers/<key>.json`) and decides the connector: URL, auth, transport, scopes, and authorization parameters; the listing's own fields grant nothing. A plugin that runs a `stdio` server is refused: the runtime connects to remote MCP servers and does not acquire, verify, or execute downloadable code. A connector or a skill listed on its own installs the same way, as a one-item plugin.

The install is recorded on its owner (the workspace, or the person for a [personal install](/using/personal-connectors/)): the address, the digest it was installed at, and exactly the connectors, skills and conversation starters it produced. Uninstalling removes exactly those. A connector two installed plugins use stays until the last of them is removed. A digest that moves in an `available` listing is an update an admin applies (`update_plugin`); a `required` catalog's items are updated by the runtime itself ([Required catalogs](#required-catalogs)). When an update changes how one of the plugin's connectors is reached or signed in to (its URL, scopes or OAuth client), the connector moves to the new settings and has to be connected again. A connector you added yourself is never taken over by a plugin, even one naming the same server at the same URL: the install is refused until you remove it. Adding a server by its URL is a separate capability, available only on a local install (`npx nimblebrain`), and never becomes a plugin.

## Catalogs: what Browse lists

`catalogs` in `nimblebrain.json` lists the catalogs this instance offers, side by side:

```json
{
  "catalogs": [
    { "source": "https://catalog.example-vendor.com/ai-catalog.json",
      "policy": "required", "sha256": "…" },
    { "source": "https://catalog.nimblebrain.ai/.well-known/ai-catalog.json", "policy": "available" },
    { "source": "/etc/nimblebrain/catalogs/local", "policy": "available" }
  ]
}
```

| Field | Meaning |
|---|---|
| `source` | An `https` URL of an AI Catalog document (`http` only to a loopback host), or a path you mount: a file holding one, or a directory holding `ai-catalog.json` or `.well-known/ai-catalog.json`. A relative path resolves against the config file's directory. |
| `policy` | `available` offers the items to install. `required` installs every item into every workspace (see [Required catalogs](#required-catalogs)). |
| `sha256` | Pins the listing's bytes. Bytes that do not match are refused and logged, and the last good copy is kept. A pinned listing is read once and never refreshed. **A `required` catalog must be pinned**: the config is refused at load without one. |
| `name` | The catalog part of an item's address. Default: from the source, the domain label before the last (`nimblebrain` for `catalog.nimblebrain.ai`) or a path's last segment (`local`). Two catalogs that derive one name are refused until one sets `name`. |
| `refreshMinutes` | How often an unpinned listing is read again. Default 15. |

With no `catalogs` key, the instance reads NimbleBrain's catalog at `<NB_PLUGIN_CATALOG_URL>/.well-known/ai-catalog.json` ([catalog.nimblebrain.ai](https://catalog.nimblebrain.ai/.well-known/ai-catalog.json) by default). An empty list reads no listings, so Browse lists nothing. Only the seed config sets it; the override file cannot.

Each listing is:

- **Validated.** A document that is not an AI Catalog this runtime reads (no `specVersion` of major `0`, no `entries`) is refused whole. One bad entry (no `identifier` or `type`, not exactly one of `url` and `data`, a digest weaker than SHA-256, an `extensions["ai.nimblebrain"]` that fails the [catalog-entry extension schema](https://schemas.nimblebrain.ai/catalog-entry-extension/v1/catalog-entry-extension.schema.json), a non-http(s) icon, a name another entry has) is dropped and logged, and the rest load.
- **Cached.** The last good copy is kept in the work directory (`cache/catalogs/`), so a restart needs no network.
- **Refreshed.** An unpinned listing is read again once its interval passes, behind the copy Browse already shows.
- **Never fatal.** When a listing cannot be read, the copy in memory is kept, else the cached copy is read, else that catalog lists nothing and Browse shows the error. A failed read is retried within a minute.

### What a row shows

A row is one listing entry: its `displayName`, `description` and `tags`, and from `extensions["ai.nimblebrain"]` its `iconUrl` and `category`. Its status comes from the auth its server declares in the extension's `servers`:

| Server `auth` | Row |
|---|---|
| `dcr`, `none`, `provider` | Ready to install. |
| `static` | **Set up** until the workspace has the OAuth client the connector needs, which a workspace admin adds. |
| a broker id (`composio`, `smithery`) | Ready when this instance [configures that broker](/config/connector-providers/); hidden otherwise, since it could never install here. |

The same server listed by two catalogs is a row under each, with no precedence between them. To prefer one catalog's item, leave it out of the other.

A row shows the setup its install will ask for, from its listing alone. A connector listed on its own (a bare connector, below) carries its whole server record inline, so its row shows everything the record says: a static entry's OAuth app portal and secret key, a broker's fields, secret headers. A plugin entry's row knows only the auth its server declares in the extension, so it is a row only when that auth needs nothing first (`dcr`, `none`); list a server that needs setup as a bare connector. An entry Browse cannot show (no server or several, or setup its listing cannot describe) is logged once per read; it still installs by its address.

### When an item leaves its catalog

| Catalog | Item removed from it, or the catalog removed from `catalogs` |
|---|---|
| `available` | Stays installed. The plugin list shows it as no longer offered, and it cannot be updated; an admin removes it when they choose. |
| `required` | Uninstalled from every workspace by the required reconcile. |

## Required catalogs

A `required` catalog's items are in every workspace, including each workspace created later, and nobody can remove one there. The runtime keeps that true itself: at startup, when a workspace is created, and every five minutes it installs each item the catalog lists into every workspace that lacks it (a few workspaces at a time), updates one whose digest the pin moved, and uninstalls one the catalog no longer lists. A required catalog that cannot be read changes nothing until it can be. Nothing has to be run by hand, and a pass with nothing to do fetches nothing.

- **Pinned.** A required catalog must carry `sha256`, so what every workspace receives changes only when you move the pin and restart.
- **Workspaces only.** A required item belongs to each workspace. Nobody installs one for themselves, since they already have it in each of their workspaces.
- **Cannot be removed.** Uninstalling a required item, by its address or by one of its connectors, is refused with `REQUIRED`; the plugin page offers no Remove. To take an item away, drop it from the catalog; to keep it but let workspaces remove it, set the catalog's policy to `available`.
- **Sign-in is still each workspace's.** An item whose server signs in with OAuth is installed as a connection awaiting sign-in: it is on the Plugins page with **Connect**, and a workspace admin signs it in for that workspace. Nobody is signed in on another's behalf. An `auth: static` server needs its OAuth client before it can be installed at all, so declare an [instance OAuth client](#an-oauth-client-for-the-whole-instance) for it, or it waits until each workspace sets one up.
- **One failure stays one failure.** An item that cannot be installed in a workspace (a connector added by hand under its name, a missing OAuth client) is logged once and tried again on the next pass; every other item and workspace goes ahead.

## Path catalogs

A `catalogs` entry whose `source` is a path reads an AI Catalog listing from a file or directory you mount, beside every other catalog. It is how a deployment offers servers a public catalog cannot carry: `auth: static` entries that need your OAuth app, brokered toolkits (`composio`, `smithery`), a fleet service, a server you are developing. Unpinned, it is read again every `refreshMinutes`, so an edit to a mounted ConfigMap reaches Browse within that interval without a restart; pinned, it is read once.

### A bare connector

A server listed on its own is an entry of type `application/vnd.nimblebrain.server+json` whose `data` is the server's `ServerDetail` record and whose `digest` is `sha256:` and the hex SHA-256 of that record's [canonical JSON form](https://www.rfc-editor.org/rfc/rfc8785). Install verifies the record against the digest and connects from it, exactly as it connects a plugin's server. A connector installed before plugins existed also reads its record here.

### Converting a connector list

The connector-list format below (`{servers: [...]}` files) is what you author; the runtime reads only AI Catalog listings. Convert a directory or file of them into a listing of bare connectors:

```bash
bun run catalog:convert ./connectors /etc/nimblebrain/catalogs/local --publisher acme.example
# writes /etc/nimblebrain/catalogs/local/ai-catalog.json
```

Each server becomes one entry named by its server name (`io.acme.support/mcp` is `io-acme-support-mcp@local` when the catalog is named `local`), with its title, description, icon, category and tags as the row's display. The conversion is strict: an entry the runtime would drop fails it, every problem is printed, and nothing is written. Mount the written directory and add it to `catalogs`:

```json
{ "source": "/etc/nimblebrain/catalogs/local", "policy": "available" }
```

## Where the connector list lives

The connector list holds the server records an installed connector reads (its display, host UI, OAuth client setup, `adminTools`) when no plugin record of its owner supplies one, such as a connector installed before plugins were. It reads, first per server name: the owner's installed plugins' records, then every configured listing's [bare connectors](#a-bare-connector), then the pinned list below.

**The pinned list: the NimbleBrain plugin catalog's.** The runtime reads the connector list of the catalog at [`NB_PLUGIN_CATALOG_URL`](/config/environment/#connectors-catalog) ([catalog.nimblebrain.ai](https://catalog.nimblebrain.ai)), the same catalog its [connector skills](/using/skills/#connector-skill-overlays) come from. A source checkout, `npx nimblebrain`, and a release image all show the same list.

- **Pinned.** The list is used only when its sha256 is `NB_PLUGIN_CATALOG_CONNECTORS_SHA256`, which each release compiles in. It is asked for at `nimblebrain/connectors/<sha256>.yaml`, a copy a catalog keeps for good, and then at `nimblebrain/connectors.yaml`, the catalog's current build. A list that does not match is refused and logged with both digests.
- **Cached.** A verified list is kept in the work directory (`cache/plugin-catalog/connectors/<sha256>.yaml`), so a restart needs no network.
- **Never fatal.** When the pinned list cannot be fetched or does not match, the runtime reads the newest verified list in its cache and logs a warning naming it. With nothing cached, Browse is empty and the startup log says why. A failed fetch is retried on a later read, at most once a minute, so a runtime that started offline fills Browse once the network is back.
- **Moving forward is bumping the pins.** The list and the index connector skills come from are pinned together; take both from the same catalog build:

  ```bash
  curl -s https://catalog.nimblebrain.ai/nimblebrain/marketplace.json | sha256sum   # NB_PLUGIN_CATALOG_SHA256
  curl -s https://catalog.nimblebrain.ai/nimblebrain/connectors.yaml | sha256sum    # NB_PLUGIN_CATALOG_CONNECTORS_SHA256
  ```

The NimbleBrain catalog's list holds the connectors that install with nothing to configure (`auth: dcr`). To offer your own list, publish a catalog in the same shape and point `NB_PLUGIN_CATALOG_URL` and both pins at it.

## Adding a new OAuth connector

Add the entry to your deployment's connector list and [convert it](#converting-a-connector-list) into the path catalog you mount. The list is a set of upstream `ServerDetail` records; platform-specific fields live under the reverse-DNS extension key `_meta["ai.nimblebrain/connector"]`.

### 1. Pick the auth flow

The kinds and what each asks of a *user* are documented once, in [Connectors → the auth kinds](/using/connectors/#the-auth-kinds). What matters when **authoring** an entry is which to reach for:

- **Prefer `dcr`.** If the vendor exposes `/.well-known/oauth-authorization-server` with `registration_endpoint` set, use it — zero OAuth client setup, no third party in the trust path. (Granola, Notion, Linear, Stripe.) Verify the claim before shipping the entry with the [rot detector](#catalog-rot-detection).
- **Use `static`** when the vendor requires a pre-registered OAuth client. Costs a workspace-admin setup step, per workspace. (Asana, HubSpot, Zoom.)
- **Use a brokered kind** when the vendor's API needs app verification you don't hold — `composio` for OAuth aggregation (Gmail, Outlook), `smithery` for a server already published to the Smithery registry, which brokers the connection *and* hosts the session. Either costs a platform-wide [provider configuration](/config/connector-providers/).
- **`provider`** names a credential provider that supplies the transport credential server-side, with no user or OAuth client. Two things use it: the platform's own connectors, whose credential the runtime mints against the fleet authorizer, and a **gateway** you hold one account key for — see [gateway endpoints](#auth-provider-for-a-gateway-endpoint) below.

<Aside type="caution">
  NimbleBrain's plugin catalog lists **DCR entries only**: connectors that install with nothing to configure, so a fresh install has a full Browse with no setup. Everything else, including `auth: static` and brokered entries, belongs in your own [path catalog](#path-catalogs).
</Aside>

<Aside type="caution" title="A brokered entry must be in your catalog">
  Installing a brokered connector spends your platform's broker credential to
  create a connection on your account. Like every install, it is built from
  **your** catalog's entry for the id, and an id the catalog does not publish is
  refused — which means a brokered connector reaches your users only through
  a catalog you publish or mount.
</Aside>

### 2. Add the YAML entry

```yaml
servers:
  - name: app.linear/mcp
    title: Linear
    description: Issues, projects, and product roadmaps
    version: "1.0.0"
    icons:
      - src: https://static.nimblebrain.ai/icons/linear.png
        sizes: ["any"]
    remotes:
      - type: streamable-http
        url: https://mcp.linear.app/mcp
    _meta:
      ai.nimblebrain/connector:
        defaultScope: workspace
        auth: dcr
        category: "Projects & tasks"
        tags: [tickets, bugs]
```

For `auth: composio`, include a `composio` block with the toolkit slug and (strongly recommended) a curated tool allowlist:

```yaml
servers:
  - name: com.google/gmail
    title: Gmail
    description: Read, send, and draft mail
    version: "1.0.0"
    icons:
      - src: https://static.nimblebrain.ai/logos/gmail/light.svg
        sizes: ["any"]
    remotes:
      - type: streamable-http
        url: https://backend.composio.dev/v3/mcp
    _meta:
      ai.nimblebrain/connector:
        defaultScope: workspace
        auth: composio
        composio:
          toolkit: gmail
          tools:
            - GMAIL_SEND_EMAIL
            - GMAIL_FETCH_EMAILS
            - GMAIL_CREATE_EMAIL_DRAFT
            # ... 10-15 total
        tags: [mail, productivity, composio]
```

The `url` is a fixed placeholder; the actual session URL is minted per install from Composio's session API. `composio.tools` is an allowlist of upstream tool names — without it the connector exposes every tool the toolkit publishes (Outlook ships ~280, enough to blow past Claude's input-token budget on first turn). Curate to a working set.

For `auth: smithery`, include a `smithery` block naming the registry qualified name:

```yaml
servers:
  - name: ai.bassethound/mcp
    title: Bassethound
    description: Company intelligence for AI agents
    version: "1.0.0"
    remotes:
      - type: streamable-http
        url: https://mcp.bassethound.ai/mcp
    _meta:
      ai.nimblebrain/connector:
        auth: smithery
        smithery:
          server: nimblebrain/bassethound
        tags: [intelligence, research]
```

The `url` is a placeholder — the install replaces it with the brokered session URL. A Smithery qualified name is global, so the entry is complete on its own and only the platform-wide `SMITHERY_API_KEY` and the declared `connectors.providers.smithery.namespace` are deployment state. There is no tool allowlist either; the connection exposes the server's own surface.

For `auth: static`, also include `oauthClientSetup`:

```yaml
servers:
  - name: io.asana/mcp
    title: Asana
    description: Tasks, projects, and team workflows
    version: "1.0.0"
    icons:
      - src: https://static.nimblebrain.ai/logos/asana/light.svg
        sizes: ["any"]
    remotes:
      - type: streamable-http
        url: https://mcp.asana.com/v2/mcp
    _meta:
      ai.nimblebrain/connector:
        defaultScope: workspace
        auth: static
        oauthClientSetup:
          portalUrl: https://app.asana.com/0/my-apps
          hint: Create an OAuth client in Asana developer portal, copy client_id + client_secret
          clientSecretKey: asana.client_secret
        tags: [tasks, projects]
```

### Field reference

Top-level fields come from upstream `ServerDetail`:

| Field | Required | Description |
|-------|----------|-------------|
| `name` | yes | Reverse-DNS canonical id (e.g. `io.asana/mcp`). Must match `^[a-zA-Z0-9.-]+/[a-zA-Z0-9._-]+$`. Used as the entry's primary key throughout the platform. |
| `title` | no | Display name on the Browse card. Falls back to `name` when absent. |
| `description` | yes | One-line tagline. ~80 chars. |
| `version` | yes | Semver string. |
| `icons[].src` | yes | Absolute http(s) URL. `javascript:` / `data:` / `file:` are rejected at the directory boundary. |
| `remotes[]` | for OAuth connectors | List of remote transports. First entry drives the install. `type` is `streamable-http` or `sse`. |
| `packages[]` | never | Downloadable distributions. Read for display and scope-matching only — this runtime installs no code, so an entry offering **only** `packages[]` is not installable and is dropped from Browse. |

NimbleBrain-specific fields under `_meta["ai.nimblebrain/connector"]`:

| Field | Required | Description |
|-------|----------|-------------|
| `defaultScope` | recommended | `"workspace"` (shared identity) or `"user"` (per-user account). Defaults to `workspace`. `auth: composio` is workspace-scope only, and `auth: smithery` installs into a workspace only. |
| `auth` | required for `remotes[]` | `"dcr"`, `"static"` or `"provider"` (the runtime-native kinds), or the id of a configured brokered provider — `"composio"` / `"smithery"` today. See [auth kinds](/using/connectors/#the-auth-kinds). Defaults to `dcr`. An entry that names `dcr` or `static` and binds no `secretHeaders` always signs in, even when the server answers discovery and tool listing without a token; one that leaves `auth` out may connect without signing in. A brokered entry carries that provider's config **under a key of the same name** (`composio:`, `smithery:`), which is how the platform hands a provider its own coordinates without knowing their shape. |
| `requiredScopes` | no | OAuth scopes the connection requests. When set, they are exactly the scopes on the authorize request, even where the server advertises more — use it to hold a connector to a narrower grant (read-only, no deletes). Pinning `offline_access` also asks for consent. A `dcr` client is still registered with the scopes the server advertises, so pin only scopes from that set against a server that enforces registered scope. The pin also blocks step-up: a tool the server refuses for insufficient scope fails, and on a connection holding no refresh token it sends the connector to reauthorization, where reconnecting grants the same pin. Omit it to request the scopes the server names in its challenge or advertises; a server that names none gets no `scope` at all. |
| `additionalAuthorizationParams` | no | Extra authorize-URL params (e.g. Google's `access_type: offline`). Reserved keys (`client_id`, `state`, `redirect_uri`, `response_type`, `code_challenge`, `code_challenge_method`, `scope`, etc.) are rejected. |
| `inBandAuthErrors` | no | Text the server puts in a tool error when it rejects the access token without a 401. A matching error is handled like a 401: refresh once and retry, else the connection asks to reconnect. See [Servers that reject a token without a 401](#servers-that-reject-a-token-without-a-401). |
| `oauthClientSetup` | required when `auth: static` | `{ portalUrl, hint, clientSecretKey }`. |
| `secretHeaders` | no, `auth: provider` only | Header name → `{ ref: credential, key, label?, help? }`, for a connection that must present the *workspace's* own secret as well as its own credential. Resolved on every request at that workspace's scope. Only references are accepted — a literal is refused at install, naming the header. The install dialog asks the user for each value, using `label` / `help` when the entry sets them and a label derived from the key's last segment otherwise; both are display-only and never reach the transport. Nothing carries the field on any other auth kind, where it is silently ignored. See [per-workspace credentials](/config/secrets/#when-the-connection-also-has-to-say-who-is-calling). |
| `composio` | required when `auth: composio` | `{ toolkit, tools?, authScheme?, fields? }`. `toolkit` is Composio's slug for the upstream, and doubles as the key your deployment's [`connectors.providers.composio.authConfigs`](/gateways/composio/#3-create-one-auth-config-per-toolkit-in-composio) is looked up under — the catalog itself carries no deployment-specific ids. `tools` is an optional allowlist of upstream tool names — strongly recommended to keep agent context bounded. `authScheme` defaults to `OAUTH2` (the redirect flow); set it to `API_KEY` for toolkits that authenticate by key (see below). `fields` is required for `API_KEY` — the inputs collected from the user at connect. |
| `account` | no | `{ tool, arguments?, field }`. How to ask the service which account a connection is signed in as, when its sign-in does not say. See [Showing the connected account](#showing-the-connected-account). |
| `category` | no | The job the connector does, as the text to show (`"Sales & support"`). Browse offers a filter of the categories your entries name, and shows an entry's category on its page; an entry without one is listed as usual, and a catalog that names fewer than two categories shows no filter. Any text is accepted: the runtime keeps no list of categories. |
| `tags` | no | Search keywords: words a person might type that the title and description do not already contain (`crm`, `wiki`, `invoices`). Browse search matches them, but never shows them. |
| `interactive` | no | Sets the "Interactive" badge. |
| `docsUrl` | no | Connector-specific docs link surfaced on the Configure page. Must be http(s). |
| `personal` | ignored | Accepted so an older catalog still loads, and has no effect. Whether a person can install a connector follows from its `auth` (see below). |

#### Who can install a connector

Any entry installs into a workspace. An entry is also offered for [personal install](/using/personal-connectors/) when its auth can hold a credential that belongs to one person: `dcr`; a brokered provider that runs an interactive sign-in (`composio`); or `static` with an [OAuth client for the whole instance](#an-oauth-client-for-the-whole-instance). `provider`, `smithery`, and `static` with only a workspace's own client sign in with a credential the operator or the workspace holds, so they install into a workspace only. The catalog has no field to restrict a connector to workspace install.

### auth: provider for a gateway endpoint

A **gateway** such as MCP360 publishes MCP endpoints and issues one account-wide API key. There is no per-connection API to call, so nothing is brokered: the entry names the endpoint, and a credential provider attaches the key.

```yaml
servers:
  - name: ai.example-gateway/search
    title: Example Gateway — Search
    description: What this endpoint gives the agent
    version: "1.0.0"
    remotes:
      - type: streamable-http
        url: https://gateway.example.com/v1/search/mcp
    _meta:
      ai.nimblebrain/connector:
        auth: provider
        providerAuth:
          provider: example-gateway
          config: {}
        tags: [search]
```

`providerAuth` is copied verbatim into the connector's transport at install. The install builds the connector from the operator-published catalog's entry for the id, never from the caller's copy, so a workspace admin cannot forge an entry that spends your account key against an endpoint of their choosing.

The provider name must match one registered on the platform. Registering one is a small addition beside the built-in credential providers; `src/connectors/providers/smithery/transport-credential.ts` is the closest model.

<Aside type="caution">
  The platform's own `minted` connectors may reach in-cluster `http://` endpoints. A gateway does not inherit that exception — its URL takes the full SSRF check, so the endpoint must be a public `https` host.
</Aside>

A `minted` connector is the exception to the verbatim copy: it mints with the `providerAuth` its catalog entry declares **now**, re-read every time the connector starts. Editing an entry's `providerAuth` therefore reaches existing installs at their next start. Removing the entry, moving its URL, or a catalog the runtime cannot read leaves those installs in place but unable to start. An install stores no copy of a `minted` entry's `config`; one an older install stored is never used as a fallback.

Every workspace installing such an entry shares the one key, so the gateway sees a single caller. You get no per-workspace attribution and no independent revocation. Where a vendor offers a brokered path as well, prefer it.

### auth: composio with API keys

Some Composio toolkits authenticate by **API key** rather than OAuth. They skip the redirect: the user pastes the key (and any region/host) into a form, the platform hands it to Composio at connect time, and only an opaque account pointer is persisted — never the key.

Set `authScheme: API_KEY` and declare the `fields` to collect:

```yaml
    _meta:
      ai.nimblebrain/connector:
        auth: composio
        composio:
          toolkit: posthog
          authScheme: API_KEY        # default is OAUTH2 (the redirect flow)
          fields:
            - key: generic_api_key   # MUST match Composio's connection field name
              title: Personal API Key
              sensitive: true        # rendered as a password input
              required: true         # required unless explicitly false
            - key: subdomain
              title: Region / subdomain
              required: true
          tools:
            - POSTHOG_CREATE_QUERY_IN_PROJECT_BY_ID
            # ...curated allowlist
```

Each `fields[].key` is sent to Composio verbatim, so it **must** match the toolkit's connection-initiation field name — which is often **not** what the REST tool catalog suggests (e.g. PostHog's key field is `generic_api_key`, not `api_key`). The same namespace caveat applies to `tools` slugs. The operator runbook for creating the `API_KEY` auth config and verifying field keys + tool slugs is in [Composio Aggregator Setup → API-key toolkits](/gateways/composio/#api-key-toolkits-no-oauth).

### Offline access & refresh tokens

Long-running agents and scheduled tasks need a connector to **refresh** its own access token. Most vendors return a `refresh_token` from the authorization-code exchange by default, or when you request the standard `offline_access` scope via `requiredScopes`. A few gate it behind a **non-standard authorize-URL param** — without it the vendor issues only a short-lived access token and **no refresh token**, so the connection dies at every access-token expiry and has to be reconnected by hand (a daily task then fails almost every run).

Set the param via `additionalAuthorizationParams`:

| Vendor | Param |
|--------|-------|
| Dropbox | `token_access_type: offline` |
| Google (native OAuth) | `access_type: offline` + `prompt: consent` |

```yaml
    _meta:
      ai.nimblebrain/connector:
        auth: static
        additionalAuthorizationParams:
          token_access_type: offline
        requiredScopes:
          - files.metadata.read
```

The param is added to the authorize request only, so existing connections do **not** retroactively gain a refresh token — users must **reconnect once** after the catalog change ships.

<Aside type="tip">
  The runtime warns at connect time when a token exchange returns no refresh token: `[oauth] <connector> token exchange returned NO refresh_token …`. If you see that line — or a connector that repeatedly asks to reconnect — it's almost always a missing offline-access param.
</Aside>

### Servers that reject a token without a 401

The MCP authorization spec has a server answer an expired or revoked access token with HTTP 401, and the runtime refreshes on that. Some servers instead answer the tool call normally with an error result whose text says the token was refused. The runtime cannot tell that apart from any other tool error, so the connection keeps its dead token, every call fails, and the connector still reads as connected, with no Reconnect to click.

Declare the server's wording with `inBandAuthErrors`:

```yaml
    _meta:
      ai.nimblebrain/connector:
        auth: static
        inBandAuthErrors:
          - "authentication token has expired or is invalid"
```

Each entry is matched as a case-insensitive substring of the error's text, and must be at least 12 characters so it names one failure rather than many. On a match the runtime refreshes with the stored refresh token and retries the call once. When the refresh is refused, or the server rejects the new token too, the connection moves to **needs reconnect** and the user gets a Reconnect button. A burst of rejected calls spends one refresh. A long-running (task) call whose result arrives later is shown as the server sent it, and the next call refreshes.

The field applies to existing connections without a reinstall: it is read from the catalog each time a connection starts.

### Showing the connected account

A connected connector shows the account it is signed in as ("Connected as alice@example.com"), so nobody has to guess which of their accounts an agent is acting on. The account comes from whoever knows it:

1. **The authorization server**, for an OIDC server. The runtime asks for `openid` and `email` and reads the id_token or the userinfo endpoint at sign-in. Nothing to configure, unless you pin `requiredScopes`: a pin is the whole request, so include `openid` and `email` in it.
2. **The broker**, for `auth: composio`. The runtime reads the account name Composio records for some toolkits, or else the email in the id_token the vendor issued, when the connection lands. For a Google toolkit that means granting `openid` and `https://www.googleapis.com/auth/userinfo.email` on its auth config in Composio, not here.
3. **The service itself**, for everything else: a server that is not OIDC, or a brokered connection with no account recorded. Declare the tool that answers for the signed-in user:

```yaml
    _meta:
      ai.nimblebrain/connector:
        auth: composio
        composio:
          toolkit: zoom
          tools: [ZOOM_GET_USER, ZOOM_LIST_MEETINGS]
        account:
          tool: ZOOM_GET_USER        # the connector's own tool, by its bare name
          arguments: { userId: me }  # optional
          field: data.email          # dotted path into the tool's JSON answer
```

The runtime calls that tool once, the first time the connected connector is listed with no account recorded, and keeps the answer with the connection until the next sign-in replaces it. It asks only a connection that has signed in and is live in the runtime, and only a connector installed from this entry (same URL, or the same brokered id). The listing waits at most five seconds for the answer.

- `tool` must be one the connection can call: for `auth: composio` it has to be in `composio.tools`, and its scope has to be in the grant.
- `field` is a path through objects in the answer (`structuredContent`, or the first text block read as JSON). It must end at a short single-line string. Anything else shows no account, and the runtime logs `account lookup for <connector> named no account` with which half failed.
- Pick a tool that only reads. The call runs with the connection's own credential, outside any agent run and outside the tool permissions a person set for agents.

### 3. Register the OAuth redirect URI

The vendor's OAuth client must allow this exact callback URL:

```
{NB_PUBLIC_ORIGIN}/v1/mcp-auth/callback
```

Where `NB_PUBLIC_ORIGIN` is the canonical public origin of the deployment. For the dev server it defaults to `http://localhost:27247`. **In production this must be set explicitly** (or derived from the chart-forwarded host facts) — see [Environment Variables → Public origin](/config/environment/#public-origin-and-callbacks).

The Set up modal in the UI shows the resolved redirect URI with a Copy button so admins can register it without guessing.

<Aside type="caution">
  A `redirect_uri does not match` error from the vendor at sign-in time means the URL registered with the vendor's OAuth client doesn't match what NimbleBrain sends. Double-check `NB_PUBLIC_ORIGIN` matches the app's actual public origin (not `localhost`, not the internal cluster service name).
</Aside>

### 4. Test it

```bash
bun run dev
```

The new entry appears on **Plugins → Browse plugins**. Walk through the install:

1. Click the new connector, then **Install** at the top of its page.
2. (For static-auth) The first install asks for the OAuth client: paste `client_id` + `client_secret`, then **Save and install**.
3. Complete the vendor's consent flow.
4. Open the connector detail page. The status pill should read **Ready** and the tools list populates.

If anything is off, check the API server logs for `[static-source]` / `[connector-directory]` warnings — invalid entries are dropped with a logged reason.

To replace a static-auth connector's OAuth client, open its detail page and edit the **OAuth client**. A new `client_id` reaches the installed connector at once and signs it out, because the vendor does not accept the old client's tokens from the new one, so click **Connect** again. Saving the same `client_id` with a new `client_secret` keeps the connection signed in.

## Catalog file format

A connector list, the input to [`catalog:convert`](#converting-a-connector-list), is a file or a directory of files, each a YAML or JSON document with one of these shapes:

```yaml
servers:
  - name: io.example/mcp
    description: ...
    # ... full ServerDetail
```

Or a bare JSON array for minimal override files:

```json
[{ "name": "io.example/mcp", "description": "...", "version": "1.0.0" }]
```

Every entry is validated against the upstream `ServerDetail` JSON schema. Invalid entries are dropped with a logged warning naming the file and the entry name; the rest of the file still loads.

### Kubernetes ConfigMap example

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nimblebrain-connectors-catalog
  namespace: nimblebrain
data:
  # bun run catalog:convert acme-catalog.yaml out/ --publisher acme.example
  ai-catalog.json: |
    {
      "specVersion": "0.9",
      "host": { "displayName": "acme.example", "identifier": "acme.example" },
      "entries": [
        {
          "identifier": "urn:air:acme.example:io-acme-support-mcp:server",
          "displayName": "Acme Support",
          "description": "Internal support tooling",
          "type": "application/vnd.nimblebrain.server+json",
          "data": { "name": "io.acme.support/mcp", "title": "Acme Support", "…": "…" },
          "digest": "sha256:…"
        }
      ]
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nimblebrain
spec:
  template:
    spec:
      containers:
        - name: api
          volumeMounts:
            - name: connectors-catalog
              mountPath: /etc/nimblebrain/catalogs/local
              readOnly: true
      volumes:
        - name: connectors-catalog
          configMap:
            name: nimblebrain-connectors-catalog
```

The ConfigMap holds the converted listing under the key `ai-catalog.json` (`bun run catalog:convert` writes it), and `nimblebrain.json` names the mount: `{ "source": "/etc/nimblebrain/catalogs/local", "policy": "available" }`. An unpinned path catalog is read again every `refreshMinutes`, so updating the ConfigMap changes Browse without restarting the pod.

### Validation

Every `ServerDetail` is validated when its file is read and again when the catalog projects it. Invalid entries are dropped with a logged warning naming the file and the entry name. Common rejection reasons:

| Reason | Fix |
|--------|-----|
| `name must match pattern "^[a-zA-Z0-9.-]+/[a-zA-Z0-9._-]+$"` | Use the reverse-DNS form (`io.asana/mcp`), not a bare slug. |
| `icon src must be http(s)` | Drop `data:` / `javascript:` / `file:` schemes. |
| `auth='static' requires oauthClientSetup.{portalUrl,hint,clientSecretKey}` | Add the `oauthClientSetup` block under `_meta["ai.nimblebrain/connector"]`. |
| `inBandAuthErrors entries must be strings of at least 12 characters` | Quote the server's own wording closely enough that it matches only a refused token. |
| `additionalAuthorizationParams cannot include reserved keys` | Remove `client_id`, `redirect_uri`, `state`, `code_challenge`, `code_challenge_method`, `scope`, etc. — these are filled by the OAuth provider. |
| `duplicate name "<id>"` | Each entry's `name` must be unique within a single static source. |
| `refused — its server name "<slug>" is also the server name of "<id>"` | Two names slugify to one server name (`a.b/c` and `a/b.c` are both `a-b-c`), so neither loads. Rename one. Logged as an error. |
| `not installable: needs a \`remotes\` entry` | The entry advertises only `packages[]`. This runtime connects to remote MCP servers; give the entry a `remotes[]` URL. |

An entry's grants — its host UI, `hooks` delivery and its outbox — apply only to an installed connector at the entry's `remotes[0].url` (a brokered connector: the provider and entry its broker recorded); a connector that only shares the entry's server name gets none of them. Its restriction, `adminTools`, applies to every connector under its server name. Changing an entry's URL therefore takes its grants from every existing install until it is reinstalled.

When a file's top-level shape is bad (not a list or `{servers: [...]}`, malformed YAML), that file contributes nothing and the rest still load. The startup logs name the file path and the parse error.

### Checking a catalog before you ship it

A rejected entry is dropped, not fatal — its siblings load normally, so the only symptom is a connector that never appears in Browse. To find that before it reaches a running deployment, point the checker at any `ServerDetail` file or directory:

```bash
bun run scripts/check-catalog-schema.ts <catalog-file-or-dir>
```

It reports every entry that would be dropped — by the source's schema and dedup checks, by the directory boundary's safety scrub, or by being unresolvable to anything installable — and exits non-zero if there are any. A source-stage diagnostic is worded exactly as the runtime logs it, so it doubles as the string to grep for when confirming a fix landed; the directory-boundary ones name the entry and the reason but are not log-line copies.

```
✗ connectors/: 1 problem(s) — these entries would be dropped

  connectors/platform.yaml[4:io.example/mcp] dropped — invalid ServerDetail: /description must NOT have more than 100 characters
```

Offline and deterministic, unlike the DCR probe below, so it is cheap enough to gate every catalog change. `bun run check:catalog-schema` runs it over the plugins demo catalog as part of `bun run verify`; the repo that owns a connector list (a published catalog's, or the one a deployment converts into its path catalog) should run it against that list.

## Catalog rot detection

The platform ships a network-dependent probe that verifies every `auth: dcr` entry in a catalog actually serves the OAuth discovery chain it claims. Point it at any `ServerDetail` file or directory:

```bash
bun run scripts/check-catalog-dcr.ts <catalog-file-or-dir> <redirect-uri>
```

`<redirect-uri>` is the `https` MCP OAuth callback your deployment registers with vendors, such as `https://nb.example.com/v1/mcp-auth/callback`. It is required because vendors check it against their own redirect-host allowlists, so only the real callback gives a truthful result.

Steps 2–4 are the discovery a connector's sign-in runs (the MCP SDK's own, the same calls), and steps 5 and 6 then exercise the flow for real against the vendor, so the check fails only what a real connect would.

1. **Reachability** — `HEAD <remotes[0].url>`. A network error or 5xx fails it, and so does a 404 or 410 that a `GET` confirms: a vendor that retires an endpoint, such as an SSE URL moved to `/mcp`, answers 410 Gone.
2. **RFC 9728** — the protected-resource metadata the server's 401 names in `resource_metadata`, or else its well-known locations, path-aware first. It names the authorization server.
3. **RFC 8414 or OpenID Connect** — that authorization server's metadata, at its path-aware locations first. A vendor that publishes it under the server's path, or only as OpenID Connect discovery, passes as it does at sign-in.
4. **RFC 7591** — that metadata must include `registration_endpoint`.
5. **DCR registration** — POST a synthetic client to the `registration_endpoint` with that redirect URI. Catches vendors that advertise DCR but enforce a redirect-URI host allowlist (Intercom, Vercel).
6. **Authorize** — `GET` the authorization request sign-in would send, built by the same SDK call: that `client_id`, the same redirect URI, PKCE, and the `resource` and scope discovery found. Catches vendors that accept the registration but reject the redirect URI one step later (Canva).

An entry passes only if every step succeeds; step 6 is skipped when the AS advertises no `authorization_endpoint`. When step 6 meets a bot challenge (Cloudflare's `cf-mitigated: challenge`) instead of the vendor's answer, the entry passes marked ⚠ unverified: a script cannot pass the challenge, a person's browser can, and step 5 has already accepted the redirect URI. Steps 5 and 6 are what catch "DCR theater" — a vendor that ships the RFC 7591 endpoints but enforces a parallel host allowlist the spec is meant to make obsolete, which discovery alone reports as healthy.

In this repo it is a **manual CLI** — deliberately, since the catalog it needs to check is deployment config, the connector list a deployment converts into its path catalog, not in the image. The automated gate runs in the deploy repo alongside that real catalog, so a vendor going down or dropping DCR support breaks the catalog's own PR. It is not part of `bun run verify`, which stays offline.

## Where the secrets live

The catalog never contains secrets. For `auth: static` entries, the workspace admin sets `client_id` (which lives in `workspace.json` under `oauthClients[<id>].clientId`) and `client_secret` (which lives in the workspace credential store under the key declared by `oauthClientSetup.clientSecretKey`).

Both are keyed by the connector's reverse-DNS `name` (e.g. `io.asana/mcp`), not a short slug.

Both are set through the UI:

```
Plugins → <connector> → Set up
```

The modal writes the public `client_id` into `workspace.json → oauthClients[<id>].clientId` and stores the `client_secret` in the workspace credential store under `oauthClientSetup.clientSecretKey`. There is no flag-based headless command for an OAuth client secret — use the Set up modal (or the `manage_connectors` tool action it calls).

The two halves go together. Uninstalling the last connector in the workspace that uses the client removes both the `oauthClients` record and the `client_secret`, and the uninstall result lists the secret's key with the connector's other removed secrets. A reinstall then asks for the client id and secret again. While another installed connector still uses the app, uninstalling keeps both.

### An OAuth client for the whole instance

When the vendor relationship belongs to the deployment rather than to each workspace, declare the pre-registered OAuth client once in `nimblebrain.json` instead. Use this when one customer's client serves every workspace on their instance, for example a vendor whose client is tied to that customer's account:

```json title="nimblebrain.json"
{
  "connectors": {
    "oauthClients": {
      "com.example/mcp": {
        "clientId": "abc123",
        "clientSecret": { "ref": "credential", "key": "example.client_secret" }
      }
    }
  }
}
```

The key is the catalog id of an `auth: static` entry. `clientSecret` takes a literal or an [instance-scope reference](/config/secrets/#instance-scope); left out, it is read from `<CATALOG_ID>_CLIENT_SECRET`, the id upper-cased with each run of other characters turned into `_` (`COM_EXAMPLE_MCP_CLIENT_SECRET` here). With an instance OAuth client declared:

- The entry installs in every workspace without asking for an OAuth client, and setting a workspace's own client for it is refused. A workspace's own record for that id is ignored.
- It is offered as a [personal connector](/using/personal-connectors/) too, so each person can sign in with their own account.
- The installed connector names the client and copies neither its id nor its secret, so changing either is a config change and a restart. Connectors already installed with a workspace's own client keep using it.
- The client is used only for the URL the catalog publishes for its id. A connector at any other URL fails to connect rather than send the secret elsewhere.

Startup fails when a declared client has no `clientId` or no secret. An id the catalog does not publish as `auth: static` is logged and unused.

## Migrating from a pre-alignment install

Operators upgrading from a release before the `ServerDetail` alignment landed should be aware of these one-time migrations:

- **`NB_CATALOG_PATH`, `NB_STDIO_CATALOG_PATH` and `NB_CURATED_CATALOG_DIR` removed.** Convert the directory of `ServerDetail` YAML / JSON files with `bun run catalog:convert` and mount the listing it writes as a [path catalog](#path-catalogs).
- **Catalog id format.** A catalog listing's `id` (and `InstalledConnector.catalogId`) is now the reverse-DNS `ServerDetail.name` (`io.asana/mcp`) instead of a bare slug (`asana`). Catalog-keyed state — `workspace.json#oauthClients[<id>]` and the matching `<clientSecretKey>` credential entries — must be rekeyed to the reverse-DNS form before existing static-auth connectors will resolve. There's no auto-migration; rekey workspace by workspace through the admin Connectors UI.
- **Connector `serverName` slug.** A catalog install persists a slugified canonical reverse-DNS form (`com-canva-mcp`), and every connector entry carries its `serverName`.
- **`packages[]`-only entries are not installable.** The runtime does not acquire or spawn a server's code, so a catalog entry advertising only `packages[]` never appears in Browse. Publish the server behind a URL and give the entry a `remotes[]` endpoint.
