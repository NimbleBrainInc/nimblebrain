NimbleBrain reads host metadata from the `_meta["ai.nimblebrain/host"]` key on your server's catalog entry — the upstream MCP registry [`ServerDetail`](https://github.com/modelcontextprotocol/registry) record an operator adds to the [connectors catalog](/config/connectors-catalog/). This is where you declare your app's name, icon, and placements (sidebar items, main views, and settings sections), along with any hooks, notification outbox, and lifecycle tools. The counts your app shows on the workspace overview are not declared here: your server reports them over MCP with the [facets extension](/apps/facets/).

The block has a published JSON Schema at
[`schemas.nimblebrain.ai/v1/nimblebrain-host.schema.json`](https://schemas.nimblebrain.ai/v1/nimblebrain-host.schema.json)
— point your editor's `$schema` at it for completion and validation while authoring.

<Aside type="note">
  The runtime reads this block from the catalog entry, not from a package it
  downloads: it connects to remote MCP servers and never acquires or executes a
  server's code. If you also ship an [MCPB](https://github.com/modelcontextprotocol/mcpb)
  `manifest.json` for other hosts, keep the same `_meta` block there — it is the
  same extension, read from wherever that host reads its metadata.
</Aside>

## Full catalog entry

```yaml title="catalog/my-app.yaml"
servers:
  - name: com.myorg/my-app
    description: My NimbleBrain app
    version: "1.0.0"
    remotes:
      - type: streamable-http
        url: https://my-app.myorg.com/mcp
    _meta:
      ai.nimblebrain/host:
        host_version: "1.0"
        name: My App
        icon: database
        placements:
          - slot: sidebar.apps
            resourceUri: ui://dashboard
            priority: 50
            label: My App
            icon: database
            route: my-app
          - slot: settings
            resourceUri: ui://settings
```

## Host metadata: `_meta["ai.nimblebrain/host"]`

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `host_version` | `string` | Yes | Contract major version. Write `"1.0"`. It changes only on a breaking change: every block on this page is part of `1.0`, and a block is turned on by declaring it, not by the version. The host accepts any `1.x` and skips a catalog connector that declares another major. |
| `name` | `string` | Recommended | Display name shown in the sidebar and app list. Without a `name` the host surfaces no UI for the connector, so it's required in practice for any app with a presence in the shell. |
| `icon` | `string` | No | [Lucide icon](https://lucide.dev/icons) name in kebab-case (e.g., `"database"`, `"message-square"`, `"hand"`). Defaults to `""`. |
| `category` | `string` | No | Reserved, free-form string. Not currently consumed by the host — declare it only as forward-looking metadata. |
| `placements` | `PlacementDeclaration[]` | No | Shell layout placement declarations — sidebar items, main views, and settings sections. See [Placements](/apps/placements). |
| `hooks` | `HookDeclaration[]` | No | Inbound event streams your server accepts from a vendor over plain HTTPS. See [hooks](#hooks-inbound-webhooks) below. |
| `notifications` | `object` | No | The outbox your server exposes — one resource the host polls for facts nobody asked for. See [notifications](#notifications-the-outbox) below and the full guide at [Notifications](/apps/notifications). |
| `lifecycle` | `object` | No | Tools the host calls when your connector becomes reachable in a workspace and just before it is removed. See [lifecycle](#lifecycle-install-and-uninstall-events) below and the full guide at [Lifecycle](/apps/lifecycle). |
| `admin_tools` | `string[]` | No | Tools on your server that only a workspace admin may call. See [admin tools](#admin_tools-tools-only-a-workspace-admin-may-call) below. |

### Settings sections

A settings section is a placement with `slot: "settings"`, not a separate top-level object. It is how your connector behaves in this workspace: changed rarely, and affecting every member. Work people do daily belongs in your app instead.

```json
{
  "slot": "settings",
  "resourceUri": "ui://settings"
}
```

**Where it renders.** On your connector's settings page, **Settings → Connectors → &lt;your connector&gt;**, under a **Settings** heading, after the host's connection sections (status, connection, secrets) and before tool permissions. It claims no navigation: there is no tab, nav entry or route.

**What it may declare.**
- `resourceUri`: the `ui://` page that renders the section, served by your server.
- `priority`: when you declare more than one, the host renders the first by priority and ignores the rest.
- `route` and `label` are ignored; the page already belongs to your connector.

The host sizes the section to its content, so style for a page section, not a full viewport. Every workspace member who can open the page sees it.

**The manage flag.** The host tells the section whether the viewer can manage this connector, in the handshake's host context:

```json
"hostContext": {
  "connector": { "canManage": false }
}
```

`canManage` is `true` for a workspace admin and `false` for everyone else, including an org admin who is not an admin of this workspace. It is the same rule the host's own sections on the page follow. When it changes while the section is open, the host sends it again in `ui/notifications/host-context-changed`. Only the settings section receives the `connector` key; your other placements do not.

Use it to disable or omit controls the viewer cannot use. **The flag reflects controls; it is not the permission.** An iframe can call any tool on its own server regardless of the flag, and so can the agent. A tool that only a workspace admin may call must be declared so the host enforces it. The key that declares it is not available yet.

### `PlacementDeclaration`

Each entry in the `placements` array:

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `slot` | `string` | Yes | — | Shell slot to fill: `"sidebar.apps"` (or any `"sidebar.<group>"`), `"sidebar"`, `"sidebar.bottom"`, `"main"`, or `"settings"`. See [Placements](/apps/placements). |
| `resourceUri` | `string` | Yes | — | `ui://` URI served by this MCP server. |
| `priority` | `number` | No | `100` | Sort order within the slot. Lower values appear first. |
| `label` | `string` | No | — | Human-readable label for sidebar items. Ignored for `"settings"`. |
| `icon` | `string` | No | — | Lucide icon name (kebab-case). Falls back to `CircleDot` if unset or unrecognized. |
| `route` | `string` | No | — | Route path. Registers as `/w/<slug>/app/<route>`. Ignored for `"settings"`. |
| `size` | `"compact" \| "full" \| "auto"` | No | — | Size hint. The shell does not read it. |


## `hooks`: inbound webhooks

A vendor that delivers events to a webhook URL — a payment processor, a campaign
platform, a CRM — cannot carry a NimbleBrain token, so it cannot call your server
directly. Declaring a `hooks` entry asks the host for a URL that it will accept
those deliveries on and forward to you.

```json
"_meta": {
  "ai.nimblebrain/host": {
    "host_version": "1.0",
    "hooks": [
      {
        "vendor": "acme",
        "route": "/ingest/acme",
        "register_tool": "set_webhook_url",
        "description": "Order events: created, paid, refunded"
      }
    ]
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `vendor` | `string` | Yes | Slug for the vendor, lowercase alphanumeric with internal hyphens. Appears in the minted URL. One entry per vendor. |
| `route` | `string` | Yes | Absolute path **on your own server** that deliveries are forwarded to. Must stay on your origin: no `//host`, no `..`, no scheme. |
| `register_tool` | `string` | Yes | A tool on your server that the host calls with `{ vendor, url }` — both strings — to hand you the minted URL. |
| `description` | `string` | No | What the stream carries. Shown to operators; the host never acts on it. |
| `header_renames` | `object` | No | `{ from: to }` header renames applied before the forward. See [signature headers](#signature-headers) below. |

### What happens

1. **At install**, the host mints a URL for exactly one `(workspace, connector, vendor)` and calls your `register_tool` with it. Store it, and register it with the vendor.
2. **On delivery**, the host verifies the URL, then forwards the request to your `route` — **body bytes unchanged**, the vendor's own headers passed through — arriving with the same `x-tenant-id` / `x-workspace-id` identity headers a tool call gets.
3. **Your server answers**, and the host returns your status code to the vendor unchanged. Answer `2xx` once you have durably recorded the delivery; answer `5xx` only when you want the vendor to retry.

The host never parses a delivery body. Signature verification, parsing, idempotency, and state are entirely yours.

### Your `register_tool` must accept `{ vendor, url }`

The host checks this against your advertised `tools/list` **at install time**. If
the tool is missing or does not accept both arguments, **no URL is minted for any
of your streams** and the operator is shown a warning naming the offending
declaration — the connector still installs, and its tools still work. A stream
whose registration tool is wrong would otherwise fail silently, months later, at
a vendor nobody is watching.

The check re-runs every time the connection is (re)established **and** every time
your advertised tool set changes, so fixing the manifest and reconnecting
provisions the streams without a reinstall.

Your tools do not have to be ready the moment the host connects. A server that
advertises nothing yet is not a contract failure — nothing is minted, nothing is
reported wrong, and the streams provision as soon as your tool list appears.

```python
@mcp.tool()
def set_webhook_url(vendor: str, url: str) -> dict:
    ...
```

### Signature headers

Your vendor's own headers reach you — `Stripe-Signature`, `X-Acme-Signature`,
whatever it uses — so you can verify the delivery came from the vendor and not
merely from someone holding the URL. **Verify them.** Possession of the URL
proves only that the host should forward the request to you for this workspace;
it does not prove who sent it.

One class of header does **not** reach you: anything a caller could use to assert
identity — `Authorization`, `X-Api-Key`, `X-Tenant-Id`, `X-Workspace-Id`,
`X-User-Id`, and **everything under the reserved `X-NB-*` prefix**. These are
stripped, because the only identity on a forwarded delivery must be the one the
platform verified. If your vendor signs on one of those headers, declare a
rename. `Cookie` never reaches you either, and cannot be renamed: a browser
posting to the URL from the platform's own origin attaches the user's session
cookie, and no vendor signs with it.

```json
{ "vendor": "acme", "route": "/ingest/acme", "register_tool": "set_webhook_url",
  "header_renames": { "authorization": "x-acme-signature" } }
```

### Limits

| | |
|---|---|
| Body size | 256 KiB; larger deliveries are refused with `413` before reaching you |
| Method | `POST` only |
| Retries | None from the host — a single forward attempt. Your vendor's own retry, plus whatever reconciliation you poll for, is the durability story |
| Rotation | An operator can rotate a URL at any time; the previous one keeps working for 24 hours so in-flight redeliveries land. Your `register_tool` is called again with the new URL |
| Correlation | No key id reaches you — the platform adds no header of its own. An operator correlates a delivery to the URL it arrived on through the platform's own logs, so you do not need to record one |

## `notifications`: the outbox

Your server learns things nobody asked it for — a domain it ordered went active,
a reply landed. Declaring a `notifications` block tells the host which resource
to read for those, on a schedule the host paces.

```json
"_meta": {
  "ai.nimblebrain/host": {
    "host_version": "1.0",
    "notifications": {
      "resource": "acme://notifications",
      "description": "Domain lifecycle, campaign replies, bounce and suppression events."
    }
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `resource` | `string` | Yes | The outbox resource URI. Must carry a scheme; must **not** carry a query string or fragment — the host appends `{?cursor,maxEvents,maxAgeMs}` itself. |
| `description` | `string` | No | What the outbox carries. Operator-facing; the host never acts on it. |

Declaring an outbox grants your server nothing: no URL is minted, no new token
audience exists, and no path to a human is opened — a workspace admin's route
does that. What it costs is a standing poll, which the host bounds with its own
cadence and per-workspace budget.

The resource shape, the poll result, the event envelope, and what the host reads
and never reads are all on the [Notifications](/apps/notifications) page.

## `lifecycle`: install and uninstall events

Some servers need to do something the first time they are installed into a
workspace — mint a tenancy at a vendor, register a sending domain — and undo it
when they are removed. Declaring a `lifecycle` block names two tools on **your
own server** that the host calls at those moments.

```json
"_meta": {
  "ai.nimblebrain/host": {
    "host_version": "1.0",
    "lifecycle": {
      "on_ready": "workspace_ready",
      "on_removing": "workspace_removing"
    }
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `on_ready` | `string` | No | Tool called when your server first becomes reachable in a workspace, with `{ reason: "install" \| "resume" }`. Its text result is shown to the user as a notice on the install. |
| `on_removing` | `string` | No | Tool called with no arguments immediately before the connector is uninstalled, while your server is still reachable. |

Both optional; declare either alone. Both handlers must be callable with **no
required arguments**, must ignore arguments they do not declare (the host sends
`reason` whether or not your schema mentions it), and must be **ordinary inline
tools** — the host awaits them, so a task-augmented handler is refused.
`on_removing` is additionally capped: the uninstall waits a few seconds and then
proceeds without it.

Delivery is **at least once**, and a fresh install delivers **two** `on_ready`
calls in a racy order, so handlers must be idempotent. A failed `on_ready` never
fails the install; a failed `on_removing` never fails the uninstall — which
waits for the call and then proceeds either way — and it may not arrive at all.

There is no `pre_install` and no `post_uninstall`: the call is a tool call on
your server, so before it is reachable and after it is gone there is nothing to
call. The full reasoning, the delivery contract, worked handlers, and the
failure table are on the [Lifecycle](/apps/lifecycle) page.

## `admin_tools`: tools only a workspace admin may call

Your server cannot check who is calling it: the host tells it the workspace, not
the person or their role. When a tool changes how your connector behaves for
everyone in the workspace, name it in `admin_tools` and the host enforces the
role for you.

```json
"_meta": {
  "ai.nimblebrain/host": {
    "host_version": "1.0",
    "admin_tools": ["configure_endpoint"]
  }
}
```

For anyone who is not a **workspace admin** of the workspace the call is bound
to, the host removes these tools from every tool listing (chat, tool search, the
MCP endpoint) and refuses a call to them on every path: chat, your app's UI, the
MCP endpoint, REST, and automations. A refused call never reaches your server.
It returns an error result whose `structuredContent` is
`{ "error": "workspace_admin_required", "connector": "<server>", "tool": "<tool>" }`.

- **Workspace admin** means a member of that workspace whose role is `admin`. An
  organization admin or owner who is not a workspace admin gets no bypass. A call
  with no signed-in user is refused.
- **Catalog only.** The host reads the list from your server's connector catalog
  entry, like [`hooks`](#hooks-inbound-webhooks). A tool's own `_meta`, or
  anything else your running server sends, does not change it.
- **It only narrows.** It removes callers and grants nothing.
- **Enforced by name.** A name your server does not advertise is still refused
  to non-admins, and is a warning on install.
- **A malformed list gates every tool.** If `admin_tools` is present but is not a
  list of at most 64 tool names with no whitespace (`null` included), the host
  cannot tell which tools you meant, so it refuses every tool on your server to
  non-admins and warns on install. An empty list declares nothing.
- **The host's own calls pass.** The host calls your `lifecycle` handlers and
  `hooks` `register_tool` itself; those calls are not checked. Naming one of them
  here is a warning on install.
- **Personal connectors are not gated.** A connector a user connects for
  themselves acts on their own account.
- **Every call is audited.** The host writes an
  [`audit.admin_tool_call`](/config/logging/#event-types) line to the workspace
  log for each call to one of these tools, admitted or refused. It names the
  person and whether the call came from chat, an automation, your app's UI or
  another client, and records the arguments. Mark every secret
  `"writeOnly": true` in the tool's input schema. An argument whose schema
  contains it anywhere (an optional secret's `anyOf` branch, a nested field, a
  `$ref`'d definition) is recorded whole as `"[redacted]"`. Pydantic's
  `SecretStr` emits it for you.

:::caution
`admin_tools` controls **who** can call a tool, not whether a person is
present. A workspace admin's agent acts as that admin and passes the check. An
admin-only tool must still be safe for that agent to call.
:::

## Registering your main view

`placements` is what the shell renders and routes from. To give your app a page with an entry under the workspace's **Apps** heading, declare a `"sidebar.apps"` placement with a `route`:

```json
"placements": [
  {
    "slot": "sidebar.apps",
    "resourceUri": "ui://dashboard",
    "route": "my-app",
    "label": "My App",
    "icon": "database"
  }
]
```

The virtual `primary` resource path resolves to the **first declared placement's** `resourceUri`, so the shell can load your main view without knowing its URI ahead of time. See [UI Resources](/apps/ui-resources) for how `primary` resolves.

The schema also accepts a `primaryView` object for back-compat, but the host does not consume it — placements are the source of truth for what is registered and routed. Declare a placement, not `primaryView`.

<Aside type="tip">
A `"main"` placement registers a route but adds no nav entry. Use it for a page your app navigates to, and a `"sidebar.apps"` placement for the page people open from the sidebar.
</Aside>

## Icons

Icons use [Lucide](https://lucide.dev/icons) names. The resolver accepts both kebab-case and PascalCase:

- `"message-square"` resolves to the `MessageSquare` component
- `"database"` resolves to `Database`
- `"hand"` resolves to `Hand`

If the icon name is not recognized, `CircleDot` is used as the default fallback.

## Minimal example (UI app)

The smallest catalog entry that registers a UI view:

```yaml title="catalog/hello.yaml"
servers:
  - name: com.myorg/hello
    description: Says hello
    version: "0.1.0"
    remotes:
      - type: streamable-http
        url: https://hello.myorg.com/mcp
    _meta:
      ai.nimblebrain/host:
        host_version: "1.0"
        name: Hello
        icon: hand
        placements:
          - slot: sidebar.apps
            resourceUri: ui://index
            route: hello
            label: Hello
```

No `_meta` needed for a tools-only server:
