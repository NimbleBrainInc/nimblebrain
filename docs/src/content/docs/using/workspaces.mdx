Workspaces let you organize your NimbleBrain environment into isolated contexts. Each workspace has its own installed apps, connectors, and members. Use workspaces to separate projects, teams, or environments.

## What is a workspace?

A workspace is an isolated environment within a NimbleBrain instance. It contains:

- **Connectors** — each workspace has its own set of installed connectors, and the app UIs they bring with them
- **Members** — users with assigned roles who can access the workspace

When you send a chat message, it runs in the context of your focused workspace, and the agent's active tool set is scoped to the apps installed there. **Conversations are partitioned by workspace** — each one is stored under the workspace it ran in and authorized by its owner. See [Conversations](/using/conversations) for how ownership and storage work.

<Aside type="note">
Workspace IDs are opaque tokens. Every workspace has a generated ID of the form `ws_<16-hex>` (for example `ws_3f9a1c7e0b2d4856`); you cannot choose one. The ID is assigned once at creation and never derived from the name — renaming a workspace does not change its ID or its URL. Treat it as opaque: never parse it for meaning.

A directory under `workspaces/` whose ID has any other form, such as a name (`ws_<name>`) or a user ID (`ws_user_<id>`), is not served: the server skips it and logs a warning naming it. To serve it, rename it to a generated ID — its directory, the `id` in its `workspace.json`, and every stored reference to it.
</Aside>

## Roles

Every workspace member has one of two roles:

| Role | Capabilities |
|------|-------------|
| **Admin** | Can manage members, apps, and connectors. |
| **Member** | Can chat and use tools. Cannot manage other members. |

## What workspaces isolate

| Scoped to workspace | Identity-level (cross-workspace) |
|---------------------|----------------------------------|
| Installed apps and connectors | Your user account and login |
| Members and roles | Your profile settings (name, theme, timezone) |
| Per-workspace credentials | |
| Conversations, files, and tasks | |
| The notification inbox, its source ceilings and its routes | |

## Creating a workspace

An organization admin creates a workspace from **Organization → Workspaces → New workspace**, or from **New workspace** in the sidebar's workspace switcher. Give it a name; it gets a generated `ws_<16-hex>` ID, and the creator is seated as its admin. The name is a freely editable label: rename it later from the workspace's **Settings → General**.

The agent cannot create workspaces. The `nb__manage_workspaces` tool behind these pages is app-only, so it never appears in the agent's tool list; it takes no ID or slug and refuses one.

## Managing members

Add, remove, and change members from the workspace's **Settings → Members** (`/w/<id>/settings/members`). The page calls the `nb__manage_workspaces` tool with these actions:

| Action | Description |
|--------|-------------|
| `add_member` | Add a user, named by `userId` or `email`, to the workspace with a specified role |
| `remove_member` | Remove a user from the workspace |
| `update_member` | Change a member's role |
| `list_members` | List all members and their roles |

<Aside type="note">
Every member can see who else is in a workspace. Workspace admins and org admins/owners can manage members: add someone in the organization by email, change roles, and remove people, from the workspace's **Settings → Members**. An org admin can manage any workspace's members without joining it. Regular members cannot add or remove other users. The same people can rename the workspace, from **Settings → General**.
</Aside>

## Workspace-scoped apps

Apps and connectors are installed at the workspace level. When a connector is installed in a workspace, only members of that workspace can use its tools.

A workspace admin installs a connector from the workspace's connectors catalog (**Plugins → Browse plugins**). Its tools join that workspace's tool registry; other workspaces are unaffected. The agent can search the catalog with `nb__search` and suggest a connector, but it cannot install one.

## Deleting a workspace

Deleting a workspace takes it away from everyone at once: it leaves every list, every request to it (the web app, `/mcp/<wsId>`, an app inside it) is answered as if it did not exist, its scheduled tasks stop, and its connectors are disconnected. Nothing in it is removed and no app is told, so until its purge time an org admin can restore it as it was from [Organization → Deleted workspaces](/guide/settings/#deleted-workspaces-orgdeleted): members, conversations, tasks, files, connectors and settings.

The purge comes once the retention window has passed (30 days by default, set by the operator with [`workspaces.deletedRetentionDays`](/config/nimblebrain-json/#workspaces); `0` purges inside the delete), or when an admin purges it now. It removes, in order:

1. Each plugin's records for the workspace: its conversations, and its tasks with their runs and batches.
2. Its connectors, each through the same teardown as removing it: the app is told it is being removed (`on_removing`), its OAuth tokens are revoked upstream, a brokered connection is revoked at the broker, and its webhook registrations, notification cursors and tool permissions are dropped.
3. Its secrets, its files and the workspace record.

A purge that stops partway, because a plugin answered an error or the runtime stopped, leaves the workspace deleted and is finished on a later pass; it can no longer be restored once it began. Organization usage keeps the workspace's spend after the purge.

Teardown is best-effort per connector. A vendor that cannot be reached does not block the purge; the connector is reported so you know whose grant may still be live and can revoke it in that vendor's own portal.

<Aside type="caution">
Deleting, restoring and purging a workspace require an org admin. A connector that fails to tear down in a purge is named in an admin's purge result and in the runtime's log — check it, because once the workspace is purged nothing in the product points at that grant any more.
</Aside>

## Switching workspaces

In the web UI, switch workspaces from the workspace navigator at the top of the sidebar. Your session is identity-bound, so switching is instant — there is no per-workspace session to reset.

Each workspace has a stable URL of the form `/w/<id>/...`. The agent's active tools follow your focused workspace; the full set of tools across every workspace you belong to is reachable on demand through `nb__search`.

Switching lands on the workspace's **Overview**. It starts with the chat's own box for asking the agent, where you can attach files and pick a model; sending opens the chat full screen. Below it is a list of your next steps in the workspace, most urgent first: anything that [needs you](/extensions/facets/) (a connector that needs attention, automation runs to review, counts from your apps), then setup still to do (connect a plugin, ask what the agent can do, invite people, each shown only while undone and only if you can do it), then your last conversation, then a few things to try with the plugins installed here, such as "Summarize my unread email" for Gmail, which send that question when you select them. The first five show; **Show more** reveals the rest. The workspace's apps are in the sidebar.

### Where NimbleBrain opens

Opening NimbleBrain at its root address takes you to the workspace you were last in on that browser. On a browser you have not used before, or if you have left that workspace, it opens the first workspace in the switcher's list. The logo at the top of the sidebar takes you to the overview of the workspace you are in.

The workspace switcher lists every workspace you belong to, with a filter, and marks any workspace with unread notifications, on its row and on the switcher itself. If you open a link to a workspace you can't reach, NimbleBrain opens one you can and says so.

## Your first workspace

When you first sign in, NimbleBrain creates a workspace for you, named after you (for example, "Mat's workspace"), with you as its admin. It is an ordinary workspace: add members to share it, rename it, or leave it like any other. Sharing a workspace shares the accounts connected in it with its members.

If you ever belong to no workspace, a new one is created for you the next time you open NimbleBrain.

## Connecting external MCP clients

Each workspace has its own MCP endpoint, `/mcp/<workspaceId>`, shown under **Workspace settings → MCP**. A client connected to it reaches that workspace's tools plus your identity tools, only while you are a member, and no other workspace. Bare `/mcp` is refused. See [Connecting External Clients](/connect/external-clients) for setup.
