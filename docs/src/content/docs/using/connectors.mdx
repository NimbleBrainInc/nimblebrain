Connectors are curated external services you connect to a workspace with point-and-click sign-in — Linear, Stripe, Gmail, Outlook, Notion, and more. Once connected, the service's tools are available to the agent for everyone in that workspace.

A connector is the only kind of thing a workspace installs: every one is a remote MCP server the platform connects to. This page covers connecting one that a workspace shares.

<Aside title="Connecting a service to yourself instead?">
This page is about connectors **shared by a workspace**. To connect a service to **your own identity** — so it follows you across workspaces and you grant it into each one — see [Personal connectors](/using/personal-connectors).
</Aside>

## Where connectors live

The plugins installed in a workspace are on its **Plugins** page, in the sidebar under the workspace's views. Each connector is a plugin there. Skills are on their own page, [Skills](/using/skills/#the-skills-page).

**Workspace | Personal** above the list splits it by whose a plugin is, each with its count:

- **Workspace**: the workspace's own plugins. Everyone's agent here uses them, signed in with the workspace's accounts.
- **Personal**: your own plugins (see [Personal connectors](/using/personal-connectors)), those on in this workspace first, then those that are not (**Off here**). Only your agent uses them.

The search beside it finds a plugin in the selected list by name or account. Each row opens the plugin's page, where every action is (connecting, disconnecting, removing it, its tool permissions). A row shows the plugin's name and, beneath it, what it does. On its right it says the plugin's state in words, never a button: what needs you (**Not signed in**, **Sign-in expired**, **Needs setup**, **Failed to start**), **Off here** for one of yours that is off in this workspace, or else the account it uses (with **on here** for one of yours), **Connected** when it records no account, or a status such as **Connecting…**. Connect, Use here and setup are on the plugin's page.

When something in the selected list needs you, a line above it says so. With one, it names the plugin and what is wrong and carries its action (**Connect**, **Reconnect**, or **Open** for one that failed or needs setup). With more, it counts them, and **Show them** narrows the list to just those (**Show all** brings the rest back). A plugin settling, or a workspace sign-in only an admin can do, needs nothing from a member, so it shows its status on its row and adds nothing to that line.

**Browse plugins**, the page's one action, opens the full directory of available services. It lists what the workspace already has too, in an **Installed** section below the rest, each with a link to its page; **← Plugins** returns. On a narrow screen the action is a **+** button, and the controls and rows stack.

An old link to **Settings → Connectors** opens Plugins (its **Browse** link opens Browse plugins), and an old link to a connector's settings page opens its plugin's page.

A connected service is **shared by everyone in the workspace** — its tools are available to all members. The credentials behind it are stored once, in the workspace.

## Connecting a service

<Steps>
1. Open **Plugins** for your workspace and choose **Browse plugins**. The **+** beside **Apps** in the sidebar opens it too.
2. Find the service you want and click it. Each row shows its name, a short description, and whose account it signs in with; search filters by name, description, or tag. The service's page says whose account it uses, what installing asks for, and the access it requests.
3. Click **Install**, at the top of the page. Every service installs from this one button; anything it needs first opens from it. When the service can sign in with each person's own account, you're asked who it is for: **Just me** (the default) or **Everyone in** the workspace. Choose **Everyone** to share one sign-in with the workspace; **Just me** adds it as one of your [personal connectors](/using/personal-connectors#adding-one-from-plugins) instead. For a service with a sign-in, you're redirected to the vendor's sign-in page. A **provider** or **smithery** connector has none: the button reads **Installed** and you stay on its page. If it installed but failed to start, you're taken to its **Configure** page instead, where the reason is shown.
4. Sign in and approve the requested access. You're returned to **Plugins**, where a notice confirms the connection once the handshake settles and the plugin's row reads **Connected just now**.
</Steps>

Installing or connecting a service for everyone requires the **admin** role in the workspace. A member without it can still install a service for themselves with **Just me**.

A service that signs in only with one account the workspace or platform holds (a **static** client the workspace sets up, **provider**, **smithery**, a service needing a stored credential) can't be installed for one person. Its row says **Uses one account for the workspace**, and **Install** adds it for everyone. A member without the admin role sees **Workspace admin required** on it.

On a workspace plugin's page, the header shows the connector's name and status ("Connected as …" when there is a sign-in), that it uses the workspace's account, and the apps it places, each a link to the app. Its **⋯** menu holds **Documentation**, **Sign out**, **Remove** (for a workspace admin) and the connector's version and tool count. Under the header come its connection settings, then the connector's own **Settings** section when it has one, then the **Skills** the plugin brings, then **Tool permissions**, collapsed to a summary until you choose **Show tools**. Any member can open the page; only a workspace admin can change it.

### Sign out and Remove

A plugin is three things, and each has one action that ends it. The verbs are the same for a workspace plugin and a [personal one](/using/personal-connectors#signing-out-and-removing); who owns the plugin only decides where its account and grants live.

| Thing | Started by | Ended by | What stays |
|---|---|---|---|
| The install | **Install** | **Remove** | Nothing: its account and settings go with it |
| The account it signs in as | **Connect** | **Sign out** | The install, its tool permissions and settings |
| A person's plugin being on in a workspace | **Use here** | **Stop using here** | The install and the account |

**Sign out** appears only for a connection someone signed in to: the **dcr** and **static** kinds, and a brokered connector whose broker can reconnect it, such as an OAuth **composio** toolkit. Signing out is reversible — **Connect** re-runs that sign-in, with the same or another account. A **provider** connector (one of the platform's own services) or one with a stored credential has no sign-in, so there is nothing to sign out of and the menu does not offer it; take it out with **Remove**.

Sign out is shared: it signs the connector out for everyone in the workspace, and asks you to confirm first. The connector stays installed with its tool permissions and settings, and reads **Not signed in** with a **Connect** action — a resting state, not an error. The agent can't use it until someone signs in again. To take it out entirely, use **Remove**, which removes it for everyone in the workspace. A connection that stops working without anyone signing it out (the vendor revoked or expired its access) reads **Reconnect** in amber instead, because someone needs to act on it. **provider** and **smithery** connectors have no interactive sign-in: their credential is held by the platform or the broker, so they reconnect without prompting you.

## The auth kinds

Every connector declares how it authenticates. As a user you rarely need to care — the **Install / Connect** button does the right thing — but it explains what each one asks of you, and who had to set it up first.

| Kind | What it means | What you do | Who sets it up |
|------|---------------|-------------|----------------|
| **dcr** | Dynamic Client Registration. The platform registers an OAuth client with the vendor on the fly. | Click **Install**, sign in. | None |
| **static** | The vendor requires a pre-registered OAuth client. | The first **Install**, by an admin, asks for the OAuth client, then carries on into the install; after that everyone installs with **Install** alone. Removing the last connector that uses the client removes the setup too, so a reinstall asks for it again. When the operator [declares the OAuth client for the whole instance](/config/connectors-catalog/#an-oauth-client-for-the-whole-instance), **Install** never asks for it. | Workspace admin, per workspace; or the operator, once |
| **composio** | Brokered through Composio, a [managed-connector provider](/config/connector-providers/). | Click **Install**. OAuth toolkits send you through the vendor's sign-in; API-key toolkits open a short form for the service's API key. | Operator, platform-wide |
| **smithery** | Brokered through Smithery, a [managed-connector provider](/config/connector-providers/) that also hosts the MCP session. | Click **Install**. A server needing no account connects immediately; one needing sign-in or configuration reports that on the install attempt, with a link to a Smithery-hosted setup page to complete first. | Operator, platform-wide |
| **provider** | A connector whose credential is supplied server-side by a named credential provider — no vendor sign-in, no OAuth client, no per-user secret. Covers both the platform's own connectors, whose credential the runtime mints against the fleet authorizer, and a [hosted gateway](/config/connector-providers/#hosted-mcp-gateways) you hold one account key for. | Click **Install**. Usually there is nothing to enter; an entry marked *Needs a credential* asks for one first (see below). | Operator — the catalog entry, plus the fleet-authorizer environment or the gateway's declared key |

For a **static** connector whose OAuth client isn't set up yet, a non-admin sees **Install** disabled with "Needs an OAuth client" until an admin installs it, which sets the client up.

### Connectors that need a credential only you hold

Some services read something the platform cannot supply for you — your own
database, your own account key. Their Browse row is marked **Needs a
credential**, and **Install** opens a short form before adding anything.

Fill it in and the connector is stored, installed, and connected in one step.
Cancel and nothing is installed, which is the right outcome: the connector could
not have reached anything.

Values are masked, go straight to the workspace credential store, and are never
shown again — not in the UI, not in a log, and never in a conversation. Replace
one later from the connector's plugin page; the next request uses it, with
no restart. See [Secrets](/config/secrets/) for the storage model.

**Remove** takes them with it. The confirmation names each stored credential
the connector owns before removing it — and reinstalling asks for the values
again, so there is nothing to hold back. See
[Uninstalling](/config/secrets/#uninstalling).

The last three rows depend on something configured once for the whole platform rather than anything in this workspace — but on *different* platform machinery: **composio** and **smithery** on a configured [connector provider](/config/connector-providers/), **provider** on the fleet authorizer or a declared gateway. None of them is something a workspace admin can turn on.

## Where your secrets live

Tokens and credentials for a connector are stored in the workspace, at `workspaces/<wsId>/credentials/` on the platform — never echoed back to the UI. For **static**-auth connectors, the admin-configured OAuth client ID is recorded on the workspace; the client secret goes into the same credential store and is never returned in any API response. For **composio** connectors, the platform-wide Composio API key lives in the platform environment, not in the workspace. For an API-key Composio toolkit, the key you paste into the connect form is sent to Composio and **never stored by the platform** — only an opaque account pointer is kept. **smithery** connectors work the same way: the platform-wide Smithery API key lives in the platform environment, and any service credential is held write-only by Smithery — the platform keeps only the connection id.

Because credentials are workspace-scoped, connecting a service in one workspace never exposes it to another. See [Credentials](/config/credentials/) for the full storage model.

## Limiting which connectors a workspace can use

Two workspace settings gate the connector catalog:

- **`connectorsAllowList`** — when set, only the listed connector IDs appear in Browse and can be installed in that workspace. Leave it unset to allow the full catalog.
- **`oauthClients`** — records the per-workspace OAuth client configuration for **static**-auth connectors (the "Set up" step writes here, and removing the last connector that uses it removes it).

See [Workspace configuration](/config/workspace-json) for the field reference.

## What installing does — and does not — do

Installing a connector records the server's URL on the workspace and starts an
authenticated connection to it. Nothing is downloaded, unpacked, or run on your
platform host: the runtime holds a URL and a credential, and the server runs
wherever its operator runs it. A connector that also ships UI surfaces its views
through `ui://` resources read over that same connection.

## Delivering a notification through a connector

A connector's tools are not only for the agent to call. A workspace admin can
write a [notification route](/using/notifications#routes) that calls one on its
own: when a connector reports something — a domain went active, a reply landed
— the route posts it through whichever connector you use to reach people.
Install a Slack, Twilio or mail connector and the route is the whole
integration; there is nothing to build.

Two things follow from a route calling a tool with nobody present:

- **It runs as the admin who wrote it.** Every gate that applies to that person
  in chat applies here — workspace membership, the connector's own permissions,
  the audit trail. If they leave the workspace the route stops rather than
  running as nobody.
- **The connector has to be installed in that workspace.** The route names a
  tool from the workspace's own installed set, and saving one that names
  anything else is refused.

## Usage overlays

When you install a connector, the platform can automatically apply a short **usage overlay** — curated guidance for that connector's tools, surfaced into the conversation the first time the agent calls one of them (never into the system prompt). It's always on and fail-soft; a connector with no curated overlay installs exactly as before (a missing overlay is simply a no-op). See [Connector skill overlays](/using/skills/#connector-skill-overlays) for how it works, and use the connector tool's `list_bound_skills` action to see what's bound in a workspace.

## Listing what a workspace has

The connector tool's `list_plugins` action lists, for the workspace it is called in, every connector installed there and every one of your personal connectors, each as a plugin. A plugin says what it does (`description`, from its catalog entry, when it has one), whose it is (`owner.kind`: `workspace` or `person`), whether it acts in this workspace (`granted`, always true for the workspace's own), each server's status and the account it is signed in as (`account`, or `null` when the connection records none, as with an API key), the skills that come with it, and the views it places in the sidebar (for a personal plugin, only where it is granted, and with no `route`, since a personal view opens from the chat). It never returns a token or other credential.
