NimbleBrain can send anonymous usage data so we can see where installs fail and which features get used. **Nothing is sent until a person says yes.** An install that has not been answered sends nothing, and neither does one with nowhere to send it.

## Who decides

| Install | Who answers | How |
|---|---|---|
| `npx nimblebrain` | You | `init` asks once in your terminal, before it checks your machine. The question shows `[Y/n]`: Enter is yes, `n` is no, and either can be changed later. |
| `npx nimblebrain` run by a coding agent | You, through the agent | The agent passes the question on (below) and runs `npx nimblebrain telemetry on` or `off` with your answer. |
| Any install, still unanswered | An org admin | The web UI asks once, at the foot of the sidebar. |
| A deployment that set it | The operator | `telemetry.enabled` in `nimblebrain.json`, or `DO_NOT_TRACK`. Nobody is asked. |

An agent's unattended `init` installs everything and reports the question instead of answering it:

```json
"telemetry": {
  "state": "undecided",
  "ask": "Help improve NimbleBrain by sending anonymous usage data? No prompts, content, names or keys are sent.",
  "set": "npx nimblebrain telemetry on|off"
}
```

Where nobody can answer (CI, a script), the install stays undecided and sends nothing.

The answer belongs to the install. The CLI, the web UI and the runtime read and change the same one, so `npx nimblebrain telemetry status` shows what the web UI set.

## What is sent

### Installing (`npx nimblebrain`)

| Event | Properties |
|---|---|
| `cli.init_started` | Agent named with `--agent`, whether a person was at the terminal |
| `cli.doctor_failed` | Which check failed (Docker, Compose, architecture, memory, port) and its error code |
| `cli.init_failed` | The error code |
| `cli.agent_connected` | Which coding agent (`claude-code`, `cursor`, `codex`) |
| `cli.init_completed` | Time taken, whether a model key is set, the model provider (`anthropic`, `openai`, …, or `ollama` for a local model, never the model), what runs the agents (`claude`, `codex`, `api`, `local`, or none), and the coding agent connected, if any |

Every CLI event also carries the CLI version, OS, CPU architecture and Node version.

Until someone answers, these events wait in `telemetry-report.jsonl` in the install folder, readable by you only. A yes sends them with the first batch; a no deletes them. Nothing leaves the machine before a yes.

### Using NimbleBrain

| Event | Properties |
|---|---|
| `runtime.started` | Connector count and how long startup took |
| `agent.chat_started` | Number of tools available |
| `agent.chat_completed` | Iterations, tool calls, calls to connector tools, stop reason, model and tool latency, total time, token counts. Model latency is left out for a run on an external agent, which reports no timing for its model calls. |
| `agent.error` | The error's type name only (e.g. `AnthropicError`) |
| `task.created` | Nothing beyond the event |
| `connector.installed` | Whether the connector has a UI |
| `connector.uninstalled` | Nothing beyond the event |
| `web.chat_sent` | Whether the conversation was resumed, whether an app was in focus |
| `web.tour_started` | Whether it was offered on a first visit or replayed from Help |
| `web.tour_finished`, `web.tour_skipped` | The step it ended on, and how many steps it had |

Runtime events also carry the NimbleBrain version, OS, CPU architecture and Bun version. Before a web event leaves the browser, every URL in it loses its query string and fragment, which can name what is on screen.

## What is never sent

- Prompts, messages, conversation or file content
- Names of connectors, tools, skills, workspaces or people
- Tool arguments or results
- File paths, hostnames, IP addresses or email addresses
- Model keys or any other credential
- Error messages or stack traces (only an error's type)
- Model names or cost

## Identity

Each install has one random ID, and nothing else identifies it. `npx nimblebrain init` creates it on its first attempt in an install folder, before checking the machine, and keeps it in `telemetry-id` there, so a retry after a failed check counts as the same install. Making the ID sends nothing; events still wait for your yes. With `DO_NOT_TRACK=1` set, no ID is written. The CLI passes the ID to the runtime as `NB_TELEMETRY_ID` in the install's `.env`, so the CLI's events and the runtime's count as one install. An install started another way keeps its ID in `.telemetry-id` in the work directory. The web client tags its events with the same ID.

To unlink future events from past ones, delete `NB_TELEMETRY_ID` from the install's `.env` (or `.telemetry-id` from the work directory). A new ID is made at the next start.

## Changing your answer

```bash
npx nimblebrain telemetry          # what it is now
npx nimblebrain telemetry off
npx nimblebrain telemetry on
```

Changing it needs NimbleBrain running (`npx nimblebrain up`), since the runtime keeps the answer.

## Turning it off for a deployment

Either of these turns telemetry off and stops anyone from being asked:

- `"telemetry": { "enabled": false }` in `nimblebrain.json`
- `DO_NOT_TRACK=1`

`"telemetry": { "enabled": true }` turns it on without asking anyone. Set it only where you, as the operator, have the right to decide for the people using the install.

## Identified deployments

An operator running NimbleBrain for others, sending to its own PostHog project, can set `identify` beside `enabled: true`:

```json
{ "telemetry": { "enabled": true, "identify": true } }
```

Events then name the person instead of the install, so a person's runtime and web events are one person in that project:

| | Anonymous (default) | Identified |
|---|---|---|
| Who an event is about | The install's random ID | The signed-in person's user ID; the install ID for work no person asked for |
| Person properties | None | Email and display name, sent once per person per runtime start |
| Groups | None | `tenant` (from `NB_TENANT_ID`, when set) and `workspace` (the workspace the request is bound to), with the workspace's name |
| Names of things used | None | Catalog names of connectors, tools, skills and models (below) |
| Pages viewed | None | A web `$pageview` each time the page on screen changes (below) |

An identified deployment also names what was used, by catalog name only. A connector added by URL, and a skill someone wrote, have names people chose, so they are sent as `custom`:

| Event | Adds |
|---|---|
| `tool.called` (one per tool call) | `source` (`kernel`, `app` or `connector`), the app or the connector's catalog id, the tool, whether it succeeded, its duration, and the run's id (`run_id`) |
| `agent.chat_started` | The run's id, the model, and what started the run (`trigger`: `chat` for a person in a chat; `schedule`, `manual` or `event` for a scheduled task's run, by what started it; `api` for a caller driving the runtime directly) |
| `agent.chat_completed` | The run's id, the model, the trigger, the connectors used, the skills used (a catalog connector's skill as `<catalog id>:<skill>`; any other as `custom`), and `cost_usd`: what the run's model calls cost in USD, each priced at its model's rates from the model catalog. A run with any call at a model the catalog has no rates for has no `cost_usd`, since its cost is unknown, not zero |
| `connector.installed` | The connector's catalog id |
| `skill.created` | The skill's scope (`org`, `workspace` or `user`), never its name |

It also sends events for moments in a person's use of the product. None carries a name someone wrote, a prompt, an output or an error message:

| Event | Properties |
|---|---|
| `user.signed_up` | The person (their email and name, as above) |
| `workspace.created` | The workspace |
| `member.added` | The person added, the workspace, and their role |
| `connector.auth_started` / `connector.auth_completed` / `connector.auth_failed` | The connector's catalog id or `custom`, `workspace` or `personal`, and for a failure the state it ended in |
| `connector.auth_lost` | A connected connector that now needs signing in again |
| `automation.created` | Its trigger (`cron`, `interval`, `event`, `once` or `manual`), who made it (`user` or `agent`), `saved` or `oneoff`, and `automation_id` |
| `automation.run_completed` | Its status, trigger (`schedule`, `manual` or `event`), duration, whether it ran in a batch, `run_id`, `automation_id`, and `cost_usd` (the run's recorded cost, priced as on `agent.chat_completed`; left out when any call could not be priced, and for a run that never reached a model). The run's steps are on its `agent.chat_*` and `tool.called` events, which carry the same `run_id`; a run that never started has only this event |

`run_id` is the run's own random id. An automation's own id is its name, so `automation_id` is a hash of where it lives and that id instead: it groups an automation's runs and names nothing. The automation's name is never sent.

On an identified deployment `automation.created` reports every automation, so the anonymous `task.created` (only automations the agent made) is not sent there.

An identified web client sends `$pageview` when the route it shows changes, and nothing when only a value in it changes (another workspace, another conversation). The event names the route template, never the path: `/w/:slug/settings/members`, not the workspace's address. Its `$current_url` is the origin plus that template, and its `$pathname` the template. On an app's page it also carries `app`, the app's server name from the catalog. In every identified web event, a URL naming another page (the referrer, the first page of a session or of a person) keeps only its origin, and a path naming another page is dropped.

Everything else in [What is never sent](#what-is-never-sent) still holds, apart from the email address, the person's name, the catalog names above, and the name of the app on screen. `identify` without `"enabled": true` does nothing: a person's yes in the CLI or the web UI never turns it on. Set it only where your terms with the people using the install allow it, and never with the key `npx nimblebrain` ships, which is the NimbleBrain project for anonymous installs.

<Aside type="tip">
  A runtime with no `POSTHOG_API_KEY` has nowhere to send anything. It asks no one, creates no ID, and makes no request to PostHog.
</Aside>

## Technical details

- **Runtime:** `posthog-node`, batched every 30 seconds or 20 events, GeoIP off.
- **Web client:** `posthog-js` with `ip: false`, `autocapture: false`, `capture_pageview: false`, session recording off. It starts only after the runtime reports a yes. An identified client sends its own `$pageview` (above), so PostHog never reports the URL itself.
- **CLI:** one `POST` to PostHog's batch endpoint at the end of a command, using Node's built-in `fetch`.
- **Destination:** PostHog Cloud (`https://us.i.posthog.com`).
- **Offline:** events are dropped by the runtime and kept by the CLI for its next command. Telemetry never fails a command.
