Skills are markdown files with YAML frontmatter that customize how the agent behaves. A skill can be **always-on** (part of every prompt) or **dynamic** (loaded on demand when it's relevant).

## How a skill loads — `loading-strategy`

Every skill declares one loading strategy:

| Strategy | Behavior |
|----------|----------|
| `always` | Always composed into the system prompt. For identity, voice, and durable cross-cutting rules. Keep it short — it costs context on every turn. Set by a person in settings, never by the agent (see [Who sets how a skill loads](#who-sets-how-a-skill-loads)). |
| `dynamic` | Loaded on demand. For task / domain skills. Enters context through one of the activation signals below. |

A `dynamic` skill activates through any of:

<Steps>

1. **Its `description`** — the model sees every skill's name + description in a catalog and activates the relevant one. This is the default path, so write the description to say *what the skill does and when to use it* (include the words a user would say). Always available — no extra field needed.
2. **`tool-affinity`** — the skill governs the tools its globs match, and reaches the model before the first call to one of them in a conversation. It is never composed into the system prompt, so a turn that calls none of its tools pays nothing for it and the cached prompt prefix stays the same whatever tools a turn starts with. It is delivered into the conversation when the tool is promoted, or, when the model calls the tool first, that call is held: it does not run, the model is told why, the skill follows it, and the model calls the tool again. A held call is not shown in the chat and does not count against a task run. Every source binds this way, so a workspace skill bound to a connector's tool arrives on the same call as the connector's own skill.
3. **`triggers`** — auto-activates on an exact phrase, for deterministic "must-fire" cases (e.g. a compliance rule that must load whenever a regulated action is named).
</Steps>

A dynamic skill with no `tool-affinity` and no `triggers` loads only when the model activates it on its description. Settings and `skills__list` call this loading **on request** (`on_request`).

### The skill catalog

Every conversation's system prompt carries a **Skill Catalog** — one line (name + description) per dynamic skill available in that workspace: authored org/workspace/user skills, skills published by installed apps, and curated connector overlays. Always-on skills don't appear (their full text is already in the prompt), and neither do disabled ones.

When a task matches a listed skill, the model loads it with the `nb__use_skill` tool, which returns the skill's body in the tool result. A skill is delivered at most once per conversation — loading one that's already in context (via `nb__use_skill` or a connector overlay) returns a short "already loaded" note instead of a second copy.

## Skill file format

A skill is a markdown file (`.md`) with YAML frontmatter. Standard fields are top-level; NimbleBrain configuration nests under `metadata.nimblebrain`:

```markdown
---
name: meeting-notes
description: >
  Summarize and search meeting notes from Granola. Use when the user mentions
  meetings, notes, agendas, minutes, or standups.
allowed-tools: granola__search_meetings granola__get_meeting
metadata:
  author: mat
  version: "1.0"
  nimblebrain:
    loading-strategy: dynamic
    priority: 50
    tool-affinity:
      - granola__*
    triggers:
      - summarize my meetings
      - meeting notes
---

You are a meeting notes assistant. Use the Granola tools to search and
summarize meeting transcripts.

When asked about meetings:
1. Search with granola__search_meetings
2. Retrieve transcripts with granola__get_meeting
3. Summarize the key discussion points, decisions, and action items

Format action items as a checklist.
```

### Body length

A skill body is delivered up to **8,000 characters** (frontmatter excluded), however it loads. A longer body is cut from the end, whole sections at a time, so the rules written last are the ones the model never sees.

- `skills__create` refuses a body over the limit, and `skills__update` refuses an edit that would leave the body over the limit and longer than it was. Neither writes anything or takes a snapshot.
- A skill already over the limit can still be edited as long as the edit does not grow it. The result says how far over it still is.
- `skills__read` reports `over-limit-by` for a skill over the limit, with the full stored body.

Keep a skill to one job. When it outgrows the limit, fold each new rule into the section it belongs in rather than appending a dated note, or split the skill into two.

## Frontmatter fields

**Standard (top-level):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | Yes | Lowercase letters, digits, and single hyphens (e.g. `meeting-notes`); ≤64 chars; matches the filename. |
| `description` | string | Yes | What the skill does **and when to use it** — the activation signal for dynamic skills, so include the words a user would say. ≤1024 chars. |
| `license` | string | No | License name or reference to a bundled license file. |
| `allowed-tools` | string | No | Space-separated globs for tools this skill may **call** (e.g. `granola__*`). |
| `metadata.author` / `metadata.version` | string | No | Conventional metadata. |

**NimbleBrain (`metadata.nimblebrain.*`):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `loading-strategy` | `always` \| `dynamic` | Yes | How the skill loads (see above). |
| `priority` | number | No | Selection / ordering priority, 11–99 (0–10 reserved for core). Default 50. |
| `status` | `active` \| `disabled` | No | Default `active`. |
| `tool-affinity` | string[] | No | Globs; a `dynamic` skill reaches the model before the first call to a matching tool (e.g. `granola__*`). |
| `triggers` | string[] | No | Exact phrases; a `dynamic` skill auto-loads on a case-insensitive substring match. |

<Aside type="note">
  `tool-affinity` (when a skill loads) is different from `allowed-tools` (which tools a skill may call).
</Aside>

## Where skills are loaded from

Skills are loaded from multiple locations, in order:

1. **Core skills** (`src/skills/core/`) — shipped with the platform, always loaded
2. **Built-in skills** (`src/skills/builtin/`) — shipped with the package
3. **Global skills** (`<workDir>/skills/`: `~/.nimblebrain/skills/` by default, `/data/skills` in the Docker image) — user-created

Files must have a `.md` extension.

### Platform defaults, and overriding one

Three core skills are always-on for every workspace and need no setup:

| Skill | What it does |
|---|---|
| `soul` | Base identity — use your tools, don't guess, be concise and direct. |
| `customer-communication` | Talk about the customer's goal and the work, not the tool names, IDs, and internal state used to do it. |
| `capabilities` | How to find the tools an app publishes and promote them into the active set. |

All three ship with the platform, so they can't be edited in place — `skills__update` refuses to write a platform-vendored file. Change one by **authoring your own skill with the same name** in a scope that outranks it.

Skills merge by `name`, with later tiers winning: **user > workspace > org (`~/.nimblebrain/skills/`) > platform**. So a file at `~/.nimblebrain/skills/customer-communication.md` replaces the shipped one for the whole org; the same name under a workspace or a single user narrows it further. Writing an org-scoped skill requires the org admin role.

`soul` and `capabilities` are reserved names — `skills__create` refuses them, so an override for those two has to be a file you write yourself. `customer-communication` is not reserved, so either route works.

To turn a default off rather than reword it, give the override `status: disabled` — an always-on skill that isn't `active` is dropped before the prompt is composed. Author it directly as a file, or create the override and toggle it off in the Skills app:

```markdown
---
name: customer-communication
description: Disabled — this deployment wants the machinery visible
metadata:
  nimblebrain:
    loading-strategy: always
    status: disabled
---
```

<Aside type="note">
  An override written through `skills__create` lands at `priority` 11–99, because 0–10 is reserved for the platform's own core skills — so it sits in contained user context rather than raw identity. A file you write yourself takes whatever `priority` its frontmatter declares, the core band included. Either way it applies.
</Aside>

## Guidance for one connector

Guidance a workspace wants the agent to follow when it uses one connector (house rules for a CRM's stages, a brand voice for a document tool) is a **workspace skill bound to the connector's tools**. Create it from **Skills → New skill** (choose **Everyone in** the workspace) and give it a `tool-affinity` matching those tools. The agent can draft it, but the tool patterns are yours to add ([Who sets how a skill loads](#who-sets-how-a-skill-loads)):

```yaml
---
name: crm-house-rules
description: How we use the CRM's stages and fields.
metadata:
  nimblebrain:
    loading-strategy: dynamic
    tool-affinity:
      - crm__*
---
Move a deal to "Qualified" only after a call is logged.
```

It reaches the agent before its first call to one of those tools, on the same call as the connector's own skill, and costs nothing on a turn that never touches the connector. For guidance that must hold before the agent picks any tool, make the skill always on instead.

What a connector's author wants every workspace to know is the server's own guidance: its `instructions` and the [skills it publishes](#skills-published-by-an-mcp-server). The host does not read an `app://instructions` resource; text a server publishes there does not reach the prompt.

## Connector skill overlays

Installing a connector can automatically apply a short **usage overlay** — curated guidance for *that* connector's tools (e.g. "confirm the recipient before sending mail"). Overlays target the connectors you don't author yourself (Composio and other third-party MCP servers). Each one is a skill in that connector's plugin in the [NimbleBrain catalog](https://catalog.nimblebrain.ai): the plugin names its server by registry name (`com.google/gmail`), and the skill names that server under `metadata.nimblebrain.server`. A connector whose server no catalog plugin binds a skill to gets no overlay.

Overlays differ from authored skills in three ways:

- **Surfaced once into the conversation, not the system prompt.** A connector overlay appears in the conversation history exactly once, before the first call to a matching tool runs (that call is held until the overlay has been read, as for any [`tool-affinity`](#how-a-skill-loads--loading-strategy) skill), and then rides the cached, append-only history for the rest of the conversation. It is relevant (only when the connector's tools are used) and cache-friendly (it never re-varies the cached system prefix turn to turn).
- **Bound to the connector's tools.** An overlay is bound to every tool of the connector it is installed for (`<server-name>__*`), or, when its frontmatter declares `metadata.nimblebrain.tool-affinity`, only to the tools it names (or to none, for `[]`), read the same way as for a [skill published by the server](#skills-published-by-an-mcp-server). The block needs nothing else: the other runtime fields are stamped on install, and an overlay always loads `dynamic`.
- **Stored separately.** Materialized overlays live in a `connector-skills/` store, distinct from authored `skills/`. They don't appear in the `skills__list` tool output; list them with the connector tool's `list_bound_skills` action instead, or see them under **Skills** on the connector's plugin page.

Resolution is **always on and fail-soft**. The runtime reads the catalog's NimbleBrain index pinned by its sha256, and each plugin's archive pinned by the sha256 that index lists; a body that does not match its digest is refused. It records the plugin, the pin, the archive digest and the skill's hash on the connector, caches by content, and treats a missing overlay (or any fetch error) as a no-op — a connector install never fails because its optional guidance couldn't be fetched, and there's nothing to enable. At startup the runtime re-binds any installed connector bound at another pin, so moving the pin reaches existing installs. When a connector has a curated overlay, the platform skips synthesizing the server's own `skill://<name>/SKILL.md` guidance so the model sees one set of instructions, not two.

| Env | Default | What it sets |
|---|---|---|
| `NB_PLUGIN_CATALOG_URL` | `https://catalog.nimblebrain.ai` | The catalog to read |
| `NB_PLUGIN_CATALOG_SHA256` | compiled into the release | The pin: `sha256sum` of the catalog's `nimblebrain/marketplace.json`, read from `nimblebrain/marketplace/<sha256>.json` |

Uninstalling the connector removes its materialized overlays.

## Skills published by an MCP server

A server publishes its own guidance as skills through the MCP [Skills Extension](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/seps/2640-skills-extension.md) (`io.modelcontextprotocol/skills`). The platform declares the extension when it connects, and a server that does not declare it publishes no skills: its `skill://` resources are ordinary resources.

To publish skills, a server declares the extension, answers `skills/list` and `skills/get`, and serves each file:

<Tabs syncKey="sdk">
<TabItem label="SDK (Python)">

[`nimblebrain-server-sdk`](/server-sdk/skills/) does all of it in one call for a FastMCP server. A skill is a directory holding a `SKILL.md` and its reference files.

```python title="server.py"
from pathlib import Path

from fastmcp import FastMCP
from nimblebrain_server_sdk import add_skills

mcp = FastMCP("notes")
add_skills(mcp, [Path(__file__).parent / "skills" / "notes"])
```

`add_skills` declares the extension, answers `skills/list` and `skills/get` with each file's digest and size, and serves every file at `skill://<skill-path>/<file-path>`. It checks each skill when the server is built, so a `SKILL.md` with no frontmatter or a name that differs from its directory fails then. Generated skills, the checks and the test helper are in the [Server SDK skills guide](/server-sdk/skills/).

</TabItem>
<TabItem label="Wire (any SDK)">

1. Declare the extension in its capabilities: `"extensions": { "io.modelcontextprotocol/skills": {} }`, alongside the `resources` capability. On a `2026-07-28` connection the platform asks only a server that declares it. On a 2025-era connection it asks every server once per discovery window, because some SDKs (the Python `mcp` SDK among them) leave the declaration out of the legacy `initialize` result; a server that answers `-32601` (method not found) publishes no skills.
2. Implement `skills/list`, returning one entry per skill: the `SKILL.md` URI, its frontmatter verbatim as JSON, and a `resources` manifest of every file in the skill with its SHA-256 `digest` and byte `size` (or `"dynamic"` for generated content).
3. Implement `skills/get`, returning the same entry for one skill URI.
4. Serve each file with `resources/read`.

</TabItem>
</Tabs>

How the platform uses them:

- **Discovery reads the listing only.** The catalog and each skill's loading rules come from the listed frontmatter; no `SKILL.md` is fetched until the skill is needed. An `always` skill is fetched when a turn composes it, a `dynamic` skill when a call to a tool it is bound to, a trigger, or the agent's `nb__use_skill` needs it.
- **Every fetched `SKILL.md` is verified.** Its bytes must match the listed digest and size, and its frontmatter the listed frontmatter, or the skill does not load that turn. A verified body is cached by digest, so an unchanged skill is not fetched again; a server that updates a skill lists the new digest.

The skill's name is its frontmatter `name`. When two skills on one server share a name, each is named by its full skill path instead (`acme/billing/refunds`). The platform reads the **same** `metadata.nimblebrain.*` block documented above off that published frontmatter, so a published skill loads by the rules its author writes rather than a fixed convention:

| Field | Effect on a published skill |
|-------|-----------------------------|
| `loading-strategy` | `always` composes it every turn; `dynamic` (the default when omitted) loads it on demand. |
| `priority` | Ordering, same scale. Defaults to 60. |
| `triggers` | Phrases that load it deterministically, whether or not the server's tools are in the active tool set. |
| `tool-affinity` | The server's own tools the skill governs, as bare names or globs (`draft_email`, `draft_*`). The platform prefixes each with `<server-name>__`. Omitted, the skill is bound to every tool of the server (`<server-name>__*`). A skill bound to every tool of its server does not hold the first call to a tool the server annotates `readOnlyHint`: it is delivered right after that call instead. A skill that names its tools always holds. An explicit empty list (`tool-affinity: []`) binds it to no tool: the skill is listed in the catalog and loads only when the model asks for it, which suits reference material no single tool call needs. A value that is not a list, or a list of only blank entries, counts as omitted. |

Two differences from an on-disk skill:

- **Reading is lenient, not strict.** A malformed or absent `metadata.nimblebrain` block leaves the fields unset and the defaults apply — an unrecognized value never rejects the skill. (An on-disk skill with bad frontmatter is skipped and logged.) Blank trigger phrases are dropped: an empty phrase would match every message.
- **`tool-affinity` is scoped to the publishing server.** A server cannot know the name it is installed under, so it declares its tools bare and the platform binds them to that install. Matching is anchored after the prefix, so a declared pattern can only narrow within the server's own tools: `*` means all of them, and no declared value reaches another connector's tools. A `dynamic` skill is delivered, when a tool is promoted or called, only when a tool it names is involved, so a server that publishes several workflow skills should give each one the tools it governs. A declared pattern that matches none of the tools the connector advertises is logged as a warning (`skills.tool_affinity.unmatched`, naming the connector, the skill, and the patterns); the same check applies to an overlay's patterns. `allowed-tools` is not read from the server.

  ```yaml
  ---
  name: writing
  description: How to draft email in the user's voice. Use when drafting or replying.
  metadata:
    nimblebrain:
      loading-strategy: dynamic
      tool-affinity:
        - draft_email
        - reply_*
  ---
  ```

If a connector has a curated overlay, the platform skips synthesizing its published skills — see the section above.

### Auditing what connectors contribute

A workspace plugin's page has a read-only **Skills** section listing, per server, every skill the runtime loads from it: its published skills and any curated overlay. Each row states how the skill loads (always on, on a tool match, on a trigger, or on the first tool call for an overlay). Opening a row shows the body as the model receives it, with its estimated token cost, priority, triggers, and `skill://` URI. The same data comes from the connector tool's `list_bound_skills` action, and one body from `read_bound_skill` (`serverName` + `skillName`).

## Listing skills

Ask the agent which skills are loaded — it uses the built-in `skills__list` tool to report each skill's name, loading strategy, priority, and source file. To see one skill's full definition, ask the agent for its details.

## The Skills page

**Skills**, in the sidebar after **Plugins**, lists what the agent is taught in a workspace. **Workspace | Personal** splits it by whose a skill is, each with its count, and a search beside it finds one by name or description.

- **Workspace** lists the skills written for this workspace and the organization's (tagged **Org**, read-only there). They apply to everyone here.
- **Personal** lists your own skills, which follow you into every workspace. Each enabled one carries an **On here** switch: switch it off to stop that skill in this workspace only (see below), and the row reads **Off here**. A disabled skill reads **Disabled** and has no switch, since it applies nowhere until you turn it on. Workspace and org skills have no such switch.
- A row says when the skill loads if that is more than the default (loading when the agent asks for it): **Always on**, **On trigger** with its phrases, or **When** a plugin **is used**, naming the plugin whose tools its tool patterns match. The patterns themselves are on the skill's page. **Opening a skill** shows its page. You can edit and delete a workspace skill if you can change the workspace, and your own skills always. An org skill is changed in the organization's settings.
- **From your plugins**, a muted group beneath the list, names the skills that came with the selected list's plugins on here, with the plugin and when each loads. Each opens its plugin's page, where it is read.
- **New skill** asks who it is for: **Just me** (one of your own skills) or **Everyone in** the workspace (a workspace skill, offered only to members who can change the workspace).

An old link to a skill's page under Plugins opens the same page under Skills.

## Your skills in each workspace

Your own skills (scope `user`) apply in every workspace you are in, unless you turn one off in a workspace.

- **Off is per workspace and yours alone.** Turning a skill off in one workspace changes nothing in your other workspaces, and nothing for anyone else. The setting is stored with your account, not in the workspace, and other members never see it.
- **An off skill is gone from that workspace's runs**, chats and tasks alike: it is not composed into the prompt, not listed in the Skill Catalog, not delivered on a tool call, and its trigger phrases do not fire. It takes effect from the next turn.
- **A same-named skill takes over.** Your skill normally wins a name it shares with a workspace or org skill. While yours is off in a workspace, that workspace or org skill applies there instead.
- **Deleting the skill forgets where it was off**, so a new skill with the same name starts on everywhere.

On the Skills page this is the **On here** switch on your skill's row under **Personal** and on its page, offered while the skill is enabled. It flips at once; if the change is refused, it flips back and a notice says why.

Only your own skills turn on and off this way; a workspace or org skill is changed by whoever owns it. The client sets it with `skills__set_here` (`id` from `skills__list`, `on: true | false`), called in the workspace it applies to. The agent cannot call it; to stop a skill for one conversation, it mutes the skill with `skills__deactivate`. `skills__list` with `scope: "user"` reports `onHere` for each of your skills in the workspace it is called in.

## Editing a skill

A skill's page under Skills, and the organization's Skills page in settings, create and edit skills without touching files.

- **Creating** a skill is one explicit action: fill in the name and body, set anything under **Advanced**, and click **Create**. A pasted whole `SKILL.md` works here: its frontmatter sets the fields it declares, and the block isn't stored as text.
- **Editing** an existing skill has no Save button. Each field saves on its own: the loading strategy when you pick one, the priority when you leave it or press Enter, and the body, tool patterns, and trigger phrases when you leave them. A save shows a notice with **Undo**; one the server refuses stays on the field with the reason, **Retry**, and **Revert**.
- On an existing skill, the fields set the manifest and the body is only prose. A body that starts with a `---` header is not applied, because it would overwrite fields saved separately: remove the header, or tick **Keep it as body text**.
- The loading verdict above **Advanced** describes the skill as saved. While an edit hasn't saved yet, it says which one.
- Emptying the tool patterns or trigger phrases removes them from the skill.

The agent edits a skill with `skills__update`, which takes a patch: a field it leaves out keeps its value, and `null` clears one. A cleared list is removed from the file, and a cleared `loading-strategy` or `priority` returns to its default (`dynamic`, 50). `description` is required, so it takes no `null`.

### Who sets how a skill loads

A skill that loads on its own (`always`, `tool-affinity`, or `triggers`) reaches the model in later conversations without that conversation's model choosing it, so a person sets how it loads, from a skill's page or the Skills settings. The skills tools refuse any other caller (the agent in a chat or a task, or an MCP client) a write that would leave a skill loading on its own: a `skills__create`, `skills__update`, or `skills__restore` that sets one of those fields (in `manifest` or in a pasted `SKILL.md`), and any change to a skill that already has one. The refusal has the code `auto_load_set_by_user`.

The agent can still write a skill that loads on request: the Skill Catalog lists it, and the model loads it when the job needs it. When a skill should load on its own, the agent saves it on request and gives you the trigger phrases or tool patterns to add on the skill's page.

## Auditing how skills loaded

`skills__list` says which skills *exist*. To see which ones actually reached the model, and how, replay the skill-load ledger with `skills__loading_log`.

Ask the agent and it reports the summary — how many loads, across how many conversations, broken down by channel. The per-load rows come back in the tool's structured output, so calling it directly (over the API or from an MCP client) is the path for analysis. Each row carries the skill, timestamp, conversation, tokens, and a `loaded_by` channel:

| `loaded_by` | Meaning |
|---|---|
| `always` | Composed into the system prompt because the skill declares `loading-strategy: always`. |
| `tool_affinity` | Appears on older recorded runs only: a bound skill composed into the prompt at turn start. A bound skill loads `before_call` or `tool_use`. |
| `trigger` | Composed in because an exact trigger phrase appeared. |
| `before_call` | A bound skill delivered while the first call to its tool was held. |
| `tool_use` | A bound skill delivered when its tool was promoted, or after a call that ran. |
| `activation` | The model loaded a Skill Catalog entry by name with `nb__use_skill`. |

A row with a `status` is a bound skill that did **not** reach the model on that call: `fetch_failed` (its body could not be fetched, so the call ran without it), `capped` (one delivery carries at most about three skills' worth of guidance, whether it came from a held call or a promotion; the rest arrive later, or the model loads them), or `renamed_unheld` (a policy hook renamed the call after the check). Filter by `conversation_id`, `skill` (name or id), `loaded_by`, or a `since`/`until` window. This is the way to answer questions the catalog alone can't — whether a skill is reaching the model at all, and whether it gets there because the model chose it or because a tool call forced it.

## Creating a custom skill

<Steps>

1. Create a `.md` file in your skills directory:

   ```bash
   mkdir -p ~/.nimblebrain/skills
   ```

2. Write the skill file with frontmatter and body:

   ```bash
   cat > ~/.nimblebrain/skills/code-review.md << 'EOF'
   ---
   name: code-review
   description: >
     Review code for bugs, security issues, and style. Use when the user asks
     to review code, check a diff, or look for bugs.
   allowed-tools: bash__run
   metadata:
     nimblebrain:
       loading-strategy: dynamic
       priority: 50
       triggers:
         - review this code
         - code review
   ---

   You are a code reviewer. When asked to review code:
   1. Read the file using bash tools
   2. Identify bugs, security issues, and style problems
   3. Suggest specific improvements with code examples
   EOF
   ```

3. Restart the server to load the new skill. In development, `bun run dev` reloads on source changes.

4. Verify it loaded by asking the agent which skills are available (it uses the `skills__list` tool).
</Steps>
