`npx nimblebrain` installs NimbleBrain on your machine from the release images, starts it, and connects your coding agent to it. Run it yourself in a terminal, or hand it to a coding agent: the same command works for both.

```bash
npx nimblebrain
```

It checks your machine, starts NimbleBrain in Docker at `http://127.0.0.1:27246`, asks whether NimbleBrain's agents run on a hosted model (your API key) or a local one (see [On a local model](#on-a-local-model)), connects the coding agent you choose to a workspace over MCP, and opens NimbleBrain in your browser (`--no-open` skips that; it never opens one for a coding agent's run). Run it again any time: on a machine that already has NimbleBrain it reports what is there and changes nothing, and after a first start that failed it picks up where that one stopped (see [When the first start fails](#when-the-first-start-fails)).

You need Docker with Compose v2 (Docker's `docker compose` plugin, or the standalone `docker-compose` v2 that Homebrew installs), about 2 GB of memory for Docker, and Node.js 20 or later. It runs on `x86_64` and `arm64`, Apple Silicon included.

<Aside type="caution">
The local instance signs nobody in: anyone who can reach its port is the admin. That is why it is published on `127.0.0.1` only. Do not widen the port, tunnel it, or put a proxy in front of it. To serve other people, set up a real identity provider instead ([instance.json](/config/instance-json/)).
</Aside>

## From a coding agent

Tell your agent:

> Install NimbleBrain with `npx nimblebrain`

An agent runs it with `--yes --agent <its name> --json` and reads the result. When no model is set, everything else still starts, the result is `ok: true` with `model_key: "missing"` and `local_model: null`, and the agent asks you to run `npx nimblebrain key` in your own terminal (so the key never passes through the agent) or `npx nimblebrain local-model` to run a model on this machine.

The agent never decides whether usage data is sent. The result carries `telemetry.state: "undecided"` and the question to ask you; the agent runs `npx nimblebrain telemetry on` or `off` with your answer. See [Telemetry](/using/telemetry/).

## Commands

| Command | Does |
|---|---|
| `init` (the default) | Checks the machine, starts NimbleBrain, connects the agent named by `--agent`, and installs the `nimblebrain` skill for it. |
| `doctor` | Checks Docker, Compose v2, CPU architecture, memory and the port. Installs nothing. |
| `status` | Version, `phase` (`starting` until the first start comes up, then `ready`), health, URL, each workspace's MCP URL, the connected agent, whether a model key is set, and whether this release can reach a server on your machine (`host_loopback`). |
| `open` | Opens NimbleBrain's web UI (the `url` in `status`) in your default browser. Answers `{"ok": true, "url": "...", "opened": true}`; where no browser can be started (no display, an SSH session, or the opener failed), `opened` is `false` and the URL is there to open by hand. A coding agent runs it when you ask it to open NimbleBrain. It never starts NimbleBrain: when it is stopped, it answers `NOT_RUNNING`. |
| `key` | Takes the model key at a hidden prompt and restarts NimbleBrain so it takes effect. A person runs this. |
| `local-model [model]` | Runs NimbleBrain's agents on a model served by Ollama instead of a hosted key: prepares the model (default `gemma4:e4b`) and restarts NimbleBrain. See [On a local model](#on-a-local-model). |
| `up` / `down` | Starts or stops NimbleBrain. Your data survives `down`. `down` also stops an install whose first start failed. |
| `logs` | Recent log lines from the runtime, also after a first start that failed. |
| `update` | Moves to the newest NimbleBrain release, or the one `--runtime` names, keeping your data, then refreshes the connected agent's `nimblebrain` skill. It never moves backwards. |
| `uninstall` | Removes the containers, the images, every conversation, and the files `init` wrote. Asks first. Also removes an install whose first start failed. |
| `telemetry [on\|off\|status]` | Whether this install sends anonymous usage data. Changing it needs NimbleBrain running. See [Telemetry](/using/telemetry/). |
| `mcp add <url>` | Adds an MCP server you run on this machine to a workspace, by its loopback URL. See [Developing a server](#developing-a-server). |
| `mcp list` | The servers in a workspace: name, URL and status. |
| `mcp remove <serverName>` | Removes a server from a workspace. |
| `help` | The commands and flags. With `--json`, every command (with the fields it answers), flag and error code as JSON. See [The CLI describes itself](#the-cli-describes-itself). |

## Flags

| Flag | Meaning |
|---|---|
| `--json` | One JSON object on stdout. Progress goes to stderr. |
| `--yes`, `-y` | Take every default. With no terminal attached, the CLI acts as if this were set and fails rather than wait for input. |
| `--agent <name>` | `claude-code`, `cursor`, `codex` or `none`. |
| `--port <n>` | The local port (default `27246`; for `doctor`, the install's own port). |
| `--provider <name>` | For `key`: `anthropic` (default), `openai`, `google`, `greenpt`, `nebius` or `xai`. The installed release decides which it takes, and `key` lists them. |
| `--local-model <model>` | For `init`: run on this Ollama model instead of a hosted key, without asking. |
| `--home <dir>` | Where the install lives (default `~/.nimblebrain-local`, or `NIMBLEBRAIN_HOME`). Each home is a separate install. See [A second install](#a-second-install). |
| `--runtime <tag>` | For `init` and `update`: the NimbleBrain release to install, such as `v0.74.0`. Default: the newest release. |
| `--no-open` | For `init`: do not open the web UI in your browser when it finishes. `init` opens it only for a person at a terminal, after a new install comes up, and never with `--json` or no terminal. |
| `--telemetry <on\|off>` | For `init`: your answer to sending anonymous usage data. Without it, `init` asks you, or, with no one at the terminal, leaves it undecided and sends nothing. |
| `--name <serverName>` | For `mcp add`: the name to add the server under. Default: the name in its Server Card, else the URL's host and port. |
| `--workspace <id>` | For `mcp`: the workspace to act in. Default: the first workspace `status` lists, the one `init` connected your agent to. |

## Versions

The CLI and NimbleBrain are versioned separately. `nimblebrain --version` is the CLI's own version; `status` reports both, the running NimbleBrain as `version` and the CLI as `cli_version`. The CLI installs the newest NimbleBrain release unless you name one with `--runtime`, and supports releases from `v0.73.0`. A newer NimbleBrain does not need a newer CLI: `npx nimblebrain update` moves you to the newest release.

### Update notices

Once a day at most, the CLI asks npm for its newest version and GitHub for the newest NimbleBrain release, and keeps the answer in `~/.cache/nimblebrain/update-check.json` (under `$XDG_CACHE_HOME` when that is set), shared by every install. The lookup runs alongside the command, and once the command has answered the CLI waits at most a second for it to finish; a slow or failed one changes nothing. When something is newer, a person sees a line on stderr after the command's own output:

```text
nimblebrain 0.4.0 is available (you have 0.3.0): npx nimblebrain@latest
NimbleBrain v0.75.0 is available (you have v0.74.0): npx nimblebrain update
```

The NimbleBrain line appears on `status`, `up` and `init`; the CLI line on any command. The command's answer never waits on the lookup; with `--json`, `status`, `init`, `up` and `update` carry what the last lookup found as `updates`, with each side it knows:

```json
"updates": {"cli": {"current": "0.3.0", "latest": "0.4.0"}, "runtime": {"current": "0.74.0", "latest": "0.75.0"}}
```

It only tells you; nothing updates by itself. It is off when `CI` is set, with `NIMBLEBRAIN_NO_UPDATE_CHECK=1`, and with `DO_NOT_TRACK=1`.

### Updating the skill

`init` installs the `nimblebrain` skill for the agent it connects. `update` refreshes it with `npx skills update nimblebrain -g -y`, also when NimbleBrain is already current, and reports `skill_update`: `updated`, `unchanged`, `failed` (the update still succeeds), or `not_installed` (a skill you removed is not added back; `status` shows how to add it).

## Connecting an agent

`init --agent <name>` registers the workspace's MCP URL, `http://127.0.0.1:27246/mcp/<workspaceId>`, with the agent: through `claude mcp add` for Claude Code, `codex mcp add` for Codex, and `~/.cursor/mcp.json` for Cursor. The local instance needs no login. If the agent's own CLI is not installed, `init` still succeeds and returns `manual`: the exact command or setting to add by hand. An agent loads a new MCP server when its next session starts. `status` reports the skill as the agent has it now, read from the agent's own skills folder, so a skill added later with `npx skills add nimblebraininc/skills --skill nimblebrain --agent <agent> -g` counts. Connecting an agent gives it NimbleBrain's tools; it does not change the model NimbleBrain runs on. NimbleBrain's own agents run on the model key you entered, billed by that provider, or on the local model you chose.

To connect another client by hand, take the MCP URL from `npx nimblebrain status` and follow [Connecting External Clients](/connect/external-clients/).

## Developing a server

The loop for building an MCP server against your local NimbleBrain:

1. Run your server over HTTP on `127.0.0.1`, for example at `http://127.0.0.1:8000/mcp`.
2. Add it, once:

   ```bash
   npx nimblebrain mcp add http://127.0.0.1:8000/mcp
   ```

3. Ask the agent in the workspace to use it. Restart your server as often as you like; NimbleBrain reconnects at the same URL, and the server stays added across `down`, `up` and `update`.

NimbleBrain reads the server's Server Card at `<url>/server-card` for its title, description, icon and sidebar placements ([Host manifest](/host/manifest/)). Without a card, the server is named from its URL unless you pass `--name`, shown under the name it reports when it connects, and gets no placements. The server need not be running when you add it: the answer then carries a `warning`, and it connects once you start it and reconnect it from the Connectors page.

```json
{"ok": true, "serverName": "notes", "url": "http://127.0.0.1:8000/mcp", "dialed": "http://host.docker.internal:8000/mcp", "placements": [], "wsId": "ws_..."}
```

`url` is the URL as you gave it, and `dialed` is where NimbleBrain, inside Docker, connects: the same port and path on `host.docker.internal`, the name Docker gives your machine. Only `localhost`, `127.0.0.1` and `::1` URLs are accepted, and only on an install made by `npx nimblebrain`. An install from before this feature reports `host_loopback: false` in `status`, and `mcp add` answers `UPDATE_REQUIRED` until you run `npx nimblebrain update`.

<Aside type="caution" title="Linux">
On Linux, `host.docker.internal` is the Docker bridge's address, not your machine's loopback, so a server listening on `127.0.0.1` is not reachable from NimbleBrain. Bind it to the bridge address (usually `172.17.0.1`) or to `0.0.0.0`. `0.0.0.0` listens on every interface, so the server can be reached from your network too unless a firewall stops it.
</Aside>

## The JSON

Every command answers `{"ok": true, ...}` or `{"ok": false, "error": "<CODE>", "message": "...", "fix": "..."}`. The exit code is `0` when `ok` is true, `1` when it is false, and `2` for an unknown command or flag. The model key never appears in any output.

| `error` | Means |
|---|---|
| `DOCKER_MISSING`, `DOCKER_NOT_RUNNING`, `DOCKER_PERMISSION`, `COMPOSE_MISSING` | Docker is missing, stopped, not usable by this user, or lacks Compose v2. On a Mac, `fix` names Docker Desktop (through Homebrew when it is there), or `brew install docker-compose` when only Compose is missing, or `colima start` when Colima's default VM is stopped. |
| `ARCH_UNSUPPORTED`, `LOW_MEMORY`, `PORT_IN_USE` | No image for this CPU, less memory than a Docker VM set to 2 GB reports, or the port is taken. `LOW_MEMORY`'s `fix` names Colima's or Docker Desktop's own setting when it is one of those. |
| `NOT_INSTALLED`, `NOT_OURS` | No install here, or the home holds files this CLI did not write (`init` never writes over them). |
| `INSTALL_INCOMPLETE` | The install's first start did not finish, so only `down`, `logs`, `status`, `doctor` and `uninstall` act on it. Run `npx nimblebrain` to finish it, or `uninstall` to remove it. |
| `NETWORK`, `START_FAILED`, `HEALTH_TIMEOUT` | A download failed, Compose could not start it, or it did not become healthy in time. On a first install, read `logs`, then run `npx nimblebrain` again: it finishes the install. |
| `HOME_NOT_SHARED` | Docker cannot read the install's folder, so it cannot mount the install's files: the home is outside the folders Docker shares with its VM. By default Colima shares only your home folder, and Docker Desktop the folders in its file sharing settings. Share the folder with Docker, or move it into a shared one and pass that folder with `--home`; the install keeps its data either way. `uninstall` deletes the install's data, so run it only to install somewhere else. |
| `NEEDS_TERMINAL`, `CANCELLED`, `AGENT_UNSUPPORTED`, `USAGE` | `key` needs a person, the action was declined, an unknown agent, or a bad command or flag. |
| `RUNTIME_UNSUPPORTED` | The release `--runtime` names is older than this CLI supports, or its Compose file cannot be driven. |
| `LOCAL_MODEL_UNREACHABLE`, `LOCAL_MODEL_MISSING`, `LOCAL_MODEL_NO_TOOLS`, `LOCAL_CONTEXT_SMALL` | Ollama does not answer (it is not installed, starting it was declined, or it did not answer after a start; `fix` names the step for this machine), the model is not on it (or its download was declined or failed), the model cannot call tools, or its context window is below the 32k NimbleBrain needs. |
| `INTERRUPTED` | The CLI was stopped (a signal, Ctrl-C) before it finished; `exit_code` says how. Check `status`, then run the command again. |
| `NOT_RUNNING` | The command needs NimbleBrain running (`open`, `telemetry on`/`off`, every `mcp` command); run `npx nimblebrain up`. |
| `TELEMETRY_LOCKED` | `telemetry on` or `off` cannot change the answer here: `DO_NOT_TRACK` is set, this CLI build has nowhere to send, or the running install refuses the change (`message` carries its reason). |
| `UPDATE_REQUIRED` | `mcp add` on a release that cannot reach your machine; run `npx nimblebrain update`. |
| `WORKSPACE_NOT_FOUND`, `SERVER_NOT_FOUND` | No such workspace (the answer lists the ones there are in `workspaces`), or no server by that name in it. |
| `URL_INVALID`, `URL_NOT_LOOPBACK` | The URL is not an `http`/`https` URL NimbleBrain accepts, or is not on this machine. |
| `INVALID_SERVER_NAME`, `NAME_TAKEN`, `NAME_IS_CATALOG_ENTRY` | The name cannot name a server, the workspace already has one by that name, or a catalog connector owns it. Pass another `--name`. |
| `DIRECT_URL_NOT_ALLOWED` | The instance is not a local install with the `dev` sign-in, so it adds servers only from its catalog. |
| `REQUEST_FAILED` | NimbleBrain refused the request for another reason; `message` carries its text. |

Each error's `fix` is the next thing to do.

### The CLI describes itself

`npx nimblebrain help --json` (or `--help --json`) answers the commands, flags and error codes of the CLI version that runs, and the fields of each command's `{"ok": true}` answer, generated from the code it parses, errors and answers with:

```json
{"ok": true, "cli_version": "0.5.0",
 "commands": [{"name": "open", "args": [], "description": "...", "answer": {"url": "...", "opened": "..."}}, {"name": "mcp add", "args": ["<url>"], "description": "...", "answer": {"serverName": "...", "url": "...", "dialed": "..."}}],
 "flags": [{"name": "--port", "takes": "n", "description": "...", "commands": ["init", "doctor"]}, {"name": "--yes", "short": "-y", "takes": null, "description": "..."}],
 "errors": [{"code": "USAGE", "fix": "...", "exit": 2}, {"code": "NOT_INSTALLED", "fix": "...", "exit": 1}]}
```

A flag without `commands` applies to every command. A command's `answer` names every field it can answer besides `ok`; a field present only sometimes says when. An agent reads this rather than a copy of it, so what it knows always matches the CLI it runs.

## On a local model

NimbleBrain's agents can run on a model served by [Ollama](https://ollama.com) on this machine, with no key and no per-call cost. Install Ollama, then answer `local` when `init` asks, or run:

```bash
npx nimblebrain --local-model gemma4:e4b     # a new install
npx nimblebrain local-model gemma4:e4b       # an install that has one already
```

The CLI checks that Ollama answers on `127.0.0.1:11434`. When Ollama is installed but not running, the CLI asks once and starts it the way it was installed: the macOS app (`open -g -a Ollama`), Homebrew's service (`brew services start ollama`, which also starts it at login), or the Linux service (`systemctl start ollama`, without `sudo`; when that needs `sudo`, the fix says so). It never installs Ollama and never runs `ollama serve` itself: when Ollama is missing, the fix names the install step for this machine (`brew install ollama`, or the download page). `--yes` and a run with no terminal take the default, yes, and the answer carries the command it ran in `ollama_started`. It then downloads the model if it is missing (it asks first), refuses a model that cannot call tools, and creates `nimblebrain-<model>` from it: the same model with a 32k context window, so Ollama never picks a smaller one and cuts the prompt. It then writes `NB_LOCAL_MODEL_URL`, `NB_LOCAL_MODEL` and `NB_LOCAL_MODEL_CONTEXT` to `.env`, and the runtime reaches Ollama at `host.docker.internal`. `up` checks Ollama again before starting NimbleBrain, since a reboot can leave it stopped, and offers to start it the same way; if Ollama stays down, NimbleBrain still starts and `up` answers `LOCAL_MODEL_UNREACHABLE`. `doctor` checks all of this again, and starts Ollama only when a person at the terminal says yes. `status` reports `local_model`.

Gemma 4 E4B is the smallest model run end to end on NimbleBrain's tasks (reliable on everyday ones, partial on scheduled tasks); [Local Models](/config/local-models/) lists what has been tested, what failed, and what has not been tried. It needs about 7 GB of memory beside NimbleBrain's 2 GB. On Linux, Ollama listens on `127.0.0.1` by default, which a container cannot reach: set `OLLAMA_HOST=0.0.0.0`. This needs a NimbleBrain release that takes a local model; an older one answers `RUNTIME_UNSUPPORTED`.

## When the first start fails

`init` records the install in `install.json` before it writes anything else, with `phase: "starting"`, and sets it to `ready` once NimbleBrain first answers. When the first start fails (`START_FAILED`, `HOME_NOT_SHARED`, `HEALTH_TIMEOUT`, or the run is cut short), the install stays `starting`: `down` stops what was started, `logs` shows why, `status` reports it with `phase: "starting"`, and `uninstall` removes it. The commands that use NimbleBrain (`up`, `update`, `key`, `local-model`, `telemetry`, `open`, every `mcp` command) answer `INSTALL_INCOMPLETE` until it is finished.

Run `npx nimblebrain` again to finish it. It keeps the install's project, and its port and release unless you pass `--port` or `--runtime`; writes the install's files again; passes the port check when the port is held by this install's own containers; asks for a model only when none is set, and for telemetry only when you have not answered; then starts NimbleBrain and connects your agent, as a new install does.

## A second install

Each home is its own install: its own containers, data volume and port. `init` names the install's Compose project after the home folder plus six random characters, so `~/nb-rc` becomes something like `nimblebrain-nb-rc-3f9a1c`, and no two homes share one, whatever their folders are called. To try a release candidate beside the NimbleBrain you use every day:

```bash
npx nimblebrain init --home ~/nb-rc --port 27300 --runtime vX.Y.Z-rc.N --agent none
npx nimblebrain status --home ~/nb-rc
npx nimblebrain uninstall --home ~/nb-rc --yes
```

Pass the same `--home` to every command for that install. Every command the CLI prints for it, in its text and in `fix` and `telemetry.set`, already carries that `--home`, as it does for a home chosen with `NIMBLEBRAIN_HOME`; the default home's commands carry none. The project is chosen once, at `init`, and kept in `install.json`, so moving the folder later changes nothing. An agent has one `nimblebrain` server, so `--agent` on the second install points that agent at it instead of the first, and that install's `uninstall` removes the registration; `--agent none` leaves your agent on the first.

## What it writes

Everything lives in `~/.nimblebrain-local`: the installed release's `docker-compose.yml`, downloaded from that release, an `instance.json` naming the `dev` sign-in, a `.env` that only your user can read (the release, the port, and your model key or local model), and `install.json`, the install's record: its Compose project, port, release and phase. Your conversations live in the Docker volume `<project>_workspace`, named after that project. `init` never writes into a home that holds any of these files without a readable `install.json`: that is `NOT_OURS`. A key exported in your shell is not used: `.env` is the only source, so the key you entered with `key` is the one that runs.
