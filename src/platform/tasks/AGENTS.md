# Tasks

Scope: the tasks platform app (`src/platform/tasks/`), the unattended primitive of ADR-0045: a definition, its runs, and their assessment. Tool-authoring rules for every platform app are in `src/platform/AGENTS.md`.

## Tasks are workspace-owned

A task lives at `workspaces/<wsId>/tasks/<ownerId>/<taskId>.json`, one file per task. Construct paths ONLY via `src/platform/tasks/paths.ts` (`workspaceTasksDir` and friends); `check:task-paths` rejects the identity-scoped `getIdentityContext(...).getDataPath("tasks")` and hand-built `users/<id>/tasks/` paths.

- **Storage written before the rename moves to `tasks/` at boot** (`migrate-storage.ts`, run by `createTasksSource` before the scheduler is built). It is the only code that names the old directory. In each old owner dir, every record file's old id key is first rewritten to `taskId` (one atomic replace per file); then the owner dir is renamed when the owner has no `tasks/` dir, otherwise merged file by file without overwriting: a file only in the old tree moves, an identical one is dropped, a different one stays and is logged as a conflict, every boot, until someone resolves it. Each step is one rename or unlink, so a crash leaves a state the next boot finishes. `Runtime.start` likewise rewrites any stored `agent` route target to the `task` key once (`migrateAgentTargetKeys`).
- **The workspace comes from `RequestContext.workspaceId`.** Like files, `tasks__*` is an identity-door tool, so it reads the same single bound workspace every other kernel source does.
- **Every run fires as its owner.** Scheduled, Run now, and event runs build the same context: the task's `workspaceId` and `{ id: ownerId }`, with no org role, so Run now tests the scheduled run with its authority, not the clicking person's. The scheduler scans `workspaces/*/tasks/*/` and keys by `${wsId}/${ownerId}/${id}`. The run is an identity-bound session **walled to** the task's provenance `workspaceId` — its tools plus the owner's identity tools, with NO cross-workspace reach.
- **Membership is re-checked per run.** It is stamped from the creator's trusted context at create, and the run-start door (`Runtime.startRun`) then denies any run whose owner is no longer a member of the provenance workspace (`WorkspaceMembershipRevokedError`, thrown before the opening message is written and before any tool binding). It is the same gate, at the same call site, that refuses a conversation resume — only the refusal differs, because the callers' contracts do. The scheduler classifies that denial as **skipped**, not failed: no `consecutiveErrors` bump, no auto-disable. So a removed owner's task stops acting immediately and **self-heals** if they are re-added.
- **A run produces a run result, not a conversation.** Each run leaves a deliverable (final output), an activity log, and refs to any files it wrote (in the workspace file store) under `…/tasks/<ownerId>/runs/<taskId>/` — `TaskRun` summaries in the run index plus a per-run `<runId>.result.json`. `runtime.executeTask` returns a `runId` and the deliverable, and creates no conversation.
- **Run history and results are kept indefinitely; the hot runs dir stays bounded.** `runs/<id>/index.jsonl` holds the newest `MAX_RUN_LINES` summaries, with those runs' `<runId>.result.json` beside it. `appendRun` rolls older lines into `runs/<id>/archive/<YYYY-MM>/index.jsonl` by each run's start month (UTC) and moves each rolled run's sidecar into the same month dir, in that order (archive index, sidecars, then the hot rewrite) so a crash can repeat a line but never lose one. So the hot dir holds only the hot window's sidecars, `index.jsonl`, and `archive/`, and listing it stays bounded. Every hot-path read (appends, `status`, the event fire check, `runs` without `before`) reads only `index.jsonl`. Only `readRunsPage` with `before` reads archive months (`listRunSegmentMonths` lists `archive/`), newest first, stopping once the page is full of runs newer than the next month can hold. `readRunResult` tries the hot dir, then each archive month (a run id carries no date). Nothing here deletes history; `deleteTask` (hard purge) is the only path that removes a runs dir.
- **The schedule is optional, and `enabled` gates only it.** No `schedule` is manual only: `computeNextRunAt` returns null, `isDue` is false, and the timer never arms for it; Run now still runs it. `update` with `schedule: null` deletes the key.
- **A once schedule fires once, then the task is inert.** `{ type: "once", at }` arms `nextRunAt` at `at`. A scheduled run of it, whatever its outcome, calls `retireOnce` in `updateAfterRun`, but only while the stored schedule still names the `at` captured at dispatch (`firedOnceAt`); an `at` edited during the run is a new occurrence and stays armed: `enabled: false`, no `nextRunAt`, and `onceDone: { at, outcome: "ran" }`; the schedule stays for history. `onceDone` is the state every reader uses (`onceRetirement`, list, status, UI); `disabledReason` is display text only. Lateness is judged only in `start()` (`retireOncesMissedWhileDown`): an armed once more than `ONCE_GRACE_MS` past `at` then is recorded skipped and retired with `outcome: "missed"`, because the runtime was down at its time. A tick or `reload()` never judges it, so a once deferred at the slot limit fires whenever a slot frees. Run now and event runs are not the occurrence and leave it armed. Any new `schedule` in an update clears `onceDone`; a new future `at` re-arms a retired once (`updateTask` enables it unless the patch says `enabled: false`); enabling one whose `at` has passed is refused, since within the grace window it would fire again. Validation refuses a past `at` and one without an offset.
- **`kind` is `saved` or `oneoff`; absent reads `saved` (`kindOf`).** `list` filters to `saved` by default. A one-off is kept forever like any task; nothing deletes it. One-offs are tool-only until the tasks UI lands: the panel lists only saved tasks and has no one-off view.
- **A run asked for by `tasks__run` has a ticket and an id minted first.** `prepareRun` (`server.ts`, shared by the inline call and the task path) mints `run_<12 hex>` and hands it to `requestRunNow` as a `RequestedRun`; the scheduler writes `run-tickets/<runId>.json` (status `queued`) before admission, rewrites it `running` when the run starts and with the final record when it ends or is refused, and passes the id to `executeTask` (`TaskRequest.runId`), so the ticket, the index line, the result sidecar, and the runtime's run all share it. The ticket is how a run is found by id alone (`tasks__run_result` with only `runId`, a task lookup). The scheduler's `openRuns` holds the runs this process carries; a ticket open with no entry there was left by a process that stopped, and `settleLostRun` records it (skipped if queued, failure if running) the first time anything reads it.
- **Over the wire, `tasks__run` is a task on the 2026-07-28 leg** (`task-source.ts`, ADR-0045). The task id is the run id, statuses map from the run record (`taskStatusOf`), and ownership is the ticket's path: a lookup reads only under the (workspace, identity) it presents. `tasks/cancel` is `cancelRunById`. A client without the extension, and every 2025-era client, gets the inline answer, which carries `runId`.
- **`tasks__run` takes `input`, an inline definition, and `idempotencyKey`.** Input is any JSON up to `MAX_RUN_INPUT_BYTES`, checked against the task's `inputSchema`, kept on the run record, and rendered by the executor inside `<run-input>` containment (`renderRunInput`, `wrapContained`) ahead of the prompt. Without `name`, the call creates a `kind: "oneoff"` task (`ensureOneoff`) with no schedule and runs it; the definition and the input are checked first, so a refused call creates nothing. The one-off's id is derived from the idempotency key when there is one, so a repeat finds the same one-off; a repeat whose definition differs from the stored one is refused, never run against the old one. A key is recorded at `runs/<id>/keys/<sha256>.json` only once its run is admitted (started or queued), and a repeat returns that run's ticket instead of asking again; a refused run leaves the key free, so a retry runs.
- **`outputSchema` is checked, not judged.** The executor tells the run to answer with matching JSON (`renderOutputSchemaInstruction`), parses and validates the final output (`applyOutputSchema`), keeps the parsed value as the result's `structured`, and records `outputSchemaValid` / `outputSchemaErrors` on the run. It never changes the run's status. Schemas are compiled when written (`assertJsonSchema`), so a schema that does not compile is refused at create, update, or an inline run.
- **Execution and the label are derived on read, never stored** (`assessment.ts`). `executionOf` maps the stored `status`/`stopReason`/deliverable to ADR-0045's execution (a `timeout`, or a `failure` at `max_iterations`/`max_input_tokens`/`spend_limit`/`length`, with a deliverable is `incomplete`); `labelOf` maps execution plus assessment to the one label. The stored `status` keeps its meaning, so error streaks, backoff, budgets and `nb_task_runs_total` are unchanged; an `incomplete` run counts toward the streak exactly as its status did. `unrecoveredToolFailures` is recorded by the executor whatever the status. Run surfaces return `toRunView(run)`.
- **Assessment runs after the record, never inside it.** `dispatchRun` records the run, frees the slot, then `assessRecorded` calls `SchedulerConfig.assess` (`judge.ts::assessRun`) for a run with a deliverable and writes the assessment with `updateRun` (index line, hot or archived, and ticket; a person's verdict is kept). A Run now's promise settles once assessed, so `tasks__run` and `runEnded` carry it; scheduled and event dispatches settle at record time, so the timer and an event batch never wait on a judge. Assessment never touches `status`. Order is cheapest first: the recorded schema validity (invalid is `fail`, no judge call), then one judge call.
- **The runtime names no judge.** `findJudgeServer`: a judge server is a workspace source exposing `judge` and `list_judges`; `judge.server` picks one, else the only one; none or several unnamed is `not_assessed` with the reason. Nothing connects one: connecting is the workspace's consent to send the state. The call goes through `runtime.dispatchUnattended` as the owner, in the task's workspace (`createJudgePort`), so the wall and the owner's tool policy apply. The state is capped (`MAX_JUDGE_STATE_CHARS`) with truncation markers. `rate_limited`/`upstream_unavailable`/`upstream_timeout` (and the door's timeout) retry on `JUDGE_RETRY_DELAYS_MS`; anything else is `not_assessed` with the code. The judge applies no pass rule: `decideCriterion` and `verdictOf` do, reading probability mass for score and choice when given.
- **`onPoorResult` acts on `fail` only** (`afterAssessed`): `record`; `notify` (default) appends `task.run.poor_result` to the workspace inbox (source `tasks`, idempotent per run; the inbox has no owner partition, so members can read it); `retry_once` asks `requestRunNow` for one run with `retryOf` and the failed criteria as a preamble (`retryGuidance`, the judge's text inside `<judge-feedback>` containment), and notifies instead when the run is itself a retry or the retry is refused. `uncertain` sets off nothing; a re-assessment sets off nothing.
- **`tasks__assess` sets a person's verdict or re-judges** (`handleAssess`). `human.via` is `ui` when `RequestContext.shellCall` is set (the REST tool call, or an app view's `/mcp` call under a first-party credential), else `remote`; it is attribution, never authority. It is not in `TASK_RUN_SAFE_TOOLS`, so a run cannot mark its own result passed.
- **A task's `allowedTools` is enforced at the run's tool router, not only in surfacing.** For an unattended run, `IdentityToolRouter` drops tools outside the list from the run's reachable set, so `nb__manage_tools` cannot activate them, and refuses a call to one, so the list is a boundary rather than a display filter. `nb__search` reads `listDiscoverableTools`, not the router, so it can still list them. A chat's `allowedTools` stays a turn-start filter whose hidden tools remain promotable. Only `nb__search` and `nb__manage_tools` pass regardless, since finding and activating the listed tools is all a run needs; every other `nb__` tool must match the list, so an owner lists `nb__use_skill` for the skill catalog (a run without it gets none) and `nb__read_resource` for connector resources. The run's tool list is filtered by the same predicate (`isToolAllowedForRun`), so the model is never shown a tool the router refuses. An empty list means no narrowing, matching the form's "all"; the executor sends none.

## Run admission

Slots, the queue, and fair share belong to the runtime's run admission at the run-start door (`src/runtime/admission.ts`, guide `src/runtime/AGENTS.md`), not to the scheduler: every unattended run takes a slot there, whatever source started it. The scheduler is handed `runtime.getRunAdmission()`, asks it for a slot, and renders its answers as run records. Config is `src/config/tasks.ts` (`tasks.maxConcurrentRuns` / `maxQueuedRuns`; it lives in `config/` because `runtime/types.ts` may not import `platform/`).

- **The scheduler holds the slot, then hands it to the door.** A run is admitted before the executor is called, and the lease rides `TaskRequest.admission` into `executeTask`, which runs under it rather than acquiring a second slot. `dispatchRun` releases it in its `finally` too (release is idempotent), which admits the next queued run. Admission keys are `task:<wsId>/<ownerId>/<id>`, so `stop()` and `dropWorkspace` withdraw only this scheduler's queued runs.
- **Run now and event runs queue at the limit; scheduled runs defer.** `requestRunNow` and `runFromEvent` ask admission with a waiter, so at the limit the run joins the runtime's queue (bounded by `tasks.maxQueuedRuns`; beyond it a skipped record). Admission hands a freed slot to a waiting run at once, so a queued run never waits for the timer and takes it ahead of a deferred scheduled run. `considerForDispatch` asks without a waiter, so a scheduled run never enters the queue: its persisted `nextRunAt` holds its place across restarts, which the in-memory queue cannot.
- **One run per task.** A Run now or event run for a task already in flight or queued is a skipped record (the admission key's duplicate check). A refused Run now or event run does not move `nextRunAt`; only a skipped scheduled occurrence does.
- **A run that never started is reported as not started.** Its record carries no `trigger` (`recordSkipped` does not write one), so the event fire ceiling (`countsAsEventFire`) counts only runs that ran. `runFromEvent` answers `{ skipped }` for a queued run that leaves the queue without starting (cancelled, disabled, dropped), so the event trigger never settles that batch `delivered`. Run now and event runs are refused once `stop()` has run, since nothing would drain the queue.
- **The queue is in memory.** `stop()` records every queued run of this scheduler as skipped; a killed process loses them with no record. `cancelRun` removes a queued run and records it `cancelled`. `dropWorkspace` resolves the workspace's queued runs without writing. Each happens in `leftQueue`, which admission calls synchronously, so the record is written before the call returns.
- **Run now returns a ticket, not a promise of a run.** `RunNowTicket` says at once whether the run started, queued (with its position), or was refused, so `handleRun` can answer a queued run immediately with the `queued` envelope. `runNow` is the awaited form.
- **The token budget is enforced before each model call, as spend accounts.** The executor names one token-unit account per cap (`budgetSpendAccounts`): an id built from the task's key, the window, and the unit, holding the cap minus the window's counters. The run-start door clamps each model call's output to what is left and stops the run with stopReason `spend_limit` when too little is left for another call (`src/runtime/AGENTS.md`), so a run spends close to the budget and not past it. The ids mean nothing to the door; only this app builds or reads them.
- **The token budget counts every run**, enabled or not, Run now included (`applyTokenBudget`). An enabled task is disabled when its counters pass a cap or when a run was stopped at `spend_limit` by one of the budget's own accounts (the run's `spendAccountId` starts with `task-budget:`); the counters then stop just short of the cap. A stop by any other account leaves the task enabled. A disabled one whose counters passed a cap is refused by Run now, as a skipped record, until the window resets (`runNowBudgetRefusal`, checked at request and again when it leaves the queue); one disabled by a `spend_limit` stop below the cap may still Run now, and the door stops that run before it passes the cap.
- **Per-run caps are clamped at execution, not at write.** `createDirectExecutor` sends every run `effectiveRunLimits`: the definition's `maxIterations` / `maxInputTokens` / `maxRunDurationMs` lowered to `tasks.maxRun*`, with unset iterations and duration taking the runtime default held to the ceiling, so stored definitions written by any path are bounded. Input tokens have no runtime default: `tasks.maxRunInputTokens` is unset unless the operator sets it, and an unset per-run cap then means no cap, because large tasks legitimately spend many millions of input tokens per run. Create and update keep the value the caller set and report `effectiveLimits`, naming any cap that was lowered. A run stopped at its input cap says whether its own cap or the operator ceiling applied.
- **`NB_TIMEZONE` is validated once, in `createTasksSource`** (`resolveDefaultTimezone`): an unknown name falls back with a warning, because a throw while recording a run leaves it unrecorded and due.
