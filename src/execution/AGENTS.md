# Execution

Scope: `src/execution/`, the agent runtimes a run executes on. The door that decides a run is `Runtime.startRun` (`src/runtime/AGENTS.md`); why the two are split is ADR-0056.

## The seam

- **The door decides; a runtime executes.** `AgentRuntime.execute(run, io)` receives a `ResolvedRun` (prompt, history, tools, model, limits, signal, and whether it may fold mid-turn) and a `RunIO` (the run's walled `ToolRouter`, its `EventSink`, and `billSummary` for a fold's summary). A runtime never resolves tools, skills, models, identity or history itself, and may narrow what a run allows, never widen it.
- **The seam carries NimbleBrain types only.** No ACP or other vendor type appears in `types.ts`, `registry.ts` or anything `src/runtime/` imports. A protocol is translated at its runtime's own edge.
- **One event vocabulary.** Every runtime emits `EngineEventPayloads` events stamped with `ResolvedRun.runId`, and each run emits one `execution.bound` naming the runtime (and its own session id, when it has one). The conversation log and the browser stream read nothing else, which is why a conversation can move between runtimes.
- **No agent runs as a child of the runtime.** A runtime reaches its agent outside the installation over a remote transport, never by spawning one: a child shares the runtime's uid, network and secrets, and an agent with its own loop is the riskiest extension there is. `biome-plugins/no-agent-process.grit` and a `node:child_process` import ban enforce it here. An external runtime is a worker dialed over Streamable HTTP (`acp/http-connection.ts`); the stdio connection that runs nimblebrain-agent as a child lives in `test/helpers/acp/` for tests and the live eval only.
- **The native runtime is built in; every other one is a worker the runtime dials.** `registry.ts` builds each `execution.runtimes` entry (`src/config/execution.ts`) at boot, plus any `RuntimeConfig.agentRuntimes` an embedder or a test hands in. A misconfiguration fails the boot: a configured runtime is a shared worker pool, so its driver must declare `toolSurface: "projection"` (an agent with tools of its own gets a sandbox per session, ADR-0057); outside the `dev` identity provider external runtimes need the run key (to sign the connection credential the worker checks on every request) and `execution.modelGateway`, one per installation (ADR-0057: the gateway is the only model endpoint an installation's agents call).
- **The door mints the turn's model credential** (`ResolvedRun.modelCredential`) when the runtime declares `modelCredential: "session"` and the installation has a run key. It goes to the agent beside the gateway only, never alone (by `providers/set` when the agent takes it, else by its driver): without a gateway the worker calls its own provider with its own key. Credentials stay in memory; never log or persist one.
- **The gateway serves each provider at `<modelGateway>/<provider>`** (`modelGatewayBaseURL` in `src/model/registry.ts`): the driver hands the worker every provider's path (`modelEndpoints`, with the session model's as `modelEndpoint` for an older worker), and with a gateway every native provider is built against the same path (which ones it serves is the gateway's answer to `GET /providers`, `src/runtime/model-gateway-providers.ts`), with `modelGatewayFetch` (`src/runtime/model-gateway-fetch.ts`) minting a credential per call from `RequestContext.credentialSubject` (the door's run id for every run, chat included).
- **A credentialed run is bounded by its credential** (`src/runtime/run-deadline.ts`). The credential expires at the run's own limit (`RunBudget.maxRunDurationMs`, a task's cap, which its executor enforces), held to `tasks.maxRunDurationMs`, plus the gateway's leeway. A run with no limit of its own, a chat turn, is held by the door to `tasks.maxRunDurationMs` and ends with `RunDeadlineExceededError`. A native run carries no credential and gets no limit from the door.
- **Capabilities are declared, and the door refuses mismatches.** A runtime states what it holds (`RuntimeCapabilities`; an ACP runtime takes its driver's); `Runtime.agentRuntimeFor` refuses a run it cannot hold (spend accounts or an input-token cap on a runtime with no spend gate). Never branch on a runtime's id anywhere outside `registry.ts`: what the door needs to know about a runtime is a capability.
- **Usage is recorded whichever runtime ran the turn.** Each model call is an `llm.done` the usage ledger prices, and each fold's summary goes through `billSummary`. The door stamps the id of a runtime whose agent reports its own usage (`RuntimeCapabilities.usage: "reported"`) on the run's request context, so its ledger lines name it (`UsageLedgerEntry.runtime`): the count is the agent's own (ADR-0056).
- **Layering:** `execution/` must not import `runtime/`, `tools/` or `platform/` (biome `noRestrictedImports`). It reaches the platform only through `RunIO`.

## ACP (`acp/`)

- **A runtime is a connection and a driver.** The connection (`AcpConnection`) is how the agent is reached, the same for every agent on that transport: it opens a fresh stream per run and owns the working directory. The driver (`AcpDriver`) is what one agent takes beyond ACP. Never put transport in a driver or an agent's dialect in a connection.
- **The generic runtime names no agent.** `acp-runtime.ts` knows ACP v1; everything one agent needs beyond it is its driver (`driver.ts`): what it holds a run to and which model credential it takes (`capabilities`), whether its tools are the projection alone (`toolSurface`), its `session/new` `_meta` (given the session's MCP servers, for an agent that restates them in its own terms), its own session preparation, its prompt, and what the agent reported about its turn beyond ACP (`outcome`: its own stop reason and each model call's usage, from its response `_meta`). The generic runtime reads no agent's `_meta` key itself. A new ACP agent is a new driver. If a driver needs a hook the interface lacks, change the interface for every driver, not the runtime for one.
- **ACP's standard fields are the runtime's, not a driver's** (`acp/standard-fields.ts`). For any agent that advertises them, the runtime sends the door's system prompt as `systemPrompt` on `session/new` (override when taken, else append), and, with a gateway and a credential, routes every provider the agent lists that the gateway serves, in a protocol the agent supports, to its gateway path with that protocol and the credential as its one header (`providers/set`), turns off the rest, and refuses a run whose agent requires one the gateway cannot serve. What went this way reaches the driver as `AcpSessionPlan.delivered`, so it leaves those out of its `_meta`. Both fields are unstable in the spec; a driver keeps its own delivery only for an agent that does not advertise them.
- **One run, one connection, one session.** The door owns the conversation, so every execution opens a fresh session from the history it is handed. No agent-side session is the record of anything.
- **Tools reach the agent through the tool projection only** (`tool-projection.ts`), an MCP server over the run's router, closed with the run. An agent that advertises `mcpCapabilities.acp` gets it on its own ACP connection (`acp/mcp-over-acp.ts`, ADR-0057): the runtime declares an `acp` MCP server under a random id bound to the run before `session/new`, answers each `mcp/message` for that id through the projection, and refuses any other id, so nothing listens. An agent that takes no `acp` server is refused before its session: it runs behind the bridge (ADR-0057), and the projection never listens. It applies the engine's call checks, the hold for bound-skill guidance, and the run's `beforeToolCall` / `afterToolCall` hooks, and it emits `tool.start` / `tool.done`. The agent's own `tool_call` updates are logged, never recorded. Never point an agent at `/mcp/<wsId>`: that is a person's attended surface, not a run's bound.
- **Bound skills are delivered by the engine's own module** (`src/engine/skill-delivery.ts`), never a copy of its rules. The first call to a bound tool is held and its guidance returned in the held result; a call that runs first carries the guidance after its output. The persisted record is the engine's: `tool.done` holds the held result alone (its `modelOutput`), and each body is a `connector.skill.injected`, which replay places after the call's iteration as for a native turn.
- **The client advertises no `fs` and no `terminal`.** A permission request is allowed when the driver declares `toolSurface: "projection"` (the agent has no tool of its own, and the projection re-checks the call), and otherwise only when its title names a projected tool. ACP has no field that names a tool reliably, so never widen the title match.
- **An agent's own session id is meaningful to that runtime only.** With a fresh store per run it can repeat across runs; never key anything on it.
- **Reasoning streams, it does not persist.** `agent_thought_chunk` becomes `reasoning.delta`, which the conversation store does not keep.
- **Per-call usage arrives with the response.** Segments are emitted as the turn runs, before any usage is known, as `transcriptOnly` `llm.done` events that usage consumers neither count nor price, so each loop call is recorded at the end as an `llm.done` with empty content and finish `stop`, which replays as nothing; the last call carries the turn's closing text. Without reported calls, ACP's turn total rides the last segment.

## What an agent needs to run as a worker

An ACP agent runs as an installation's worker with no more than a short driver when it:

1. **Serves ACP over Streamable HTTP and admits only the runtime's connection credential**: `Authorization: Bearer`, an EdDSA JWT with audience `acp-worker`, checked against the runtime's run-key set.
2. **Takes the run's tools on its ACP connection** (`mcpCapabilities.acp`) and has no tools of its own, or lets a session turn them off, so its driver can declare `toolSurface: "projection"`.
3. **Takes model access per session or per connection**: a credential and a base URL per provider, each one the installation's gateway, so its driver can declare `modelCredential: "session"`.

An agent short of 2 needs the bridge beside it (ADR-0057); one short of 3 runs chat only, on a credential per pool. nimblebrain-agent meets all three, and its driver is the reference. Prefer ACP's standard fields to a driver's `_meta` wherever the spec has one, so the next agent needs less driver.

## Tests

- **`test/integration/execution/runtime-parity.test.ts` holds the generic ACP runtime to the native record.** Its ACP side is a scripted agent (`test/helpers/acp/scripted-agent.ts`) that plays the echo model's script over plain ACP, so a change to the runtime, the recorder or the projection is checked with no model and no external agent. A new behaviour of either runtime joins it.
- **nimblebrain-agent is pinned to a commit as a dev dependency**, which the image's `--production` install leaves out, and nothing in `src/` may import it (`noRestrictedImports` in every `src/` override of `biome.json`; `test/unit/biome-plugins.test.ts` proves it fires). `test/integration/execution/nimblebrain-agent.test.ts` runs that pin and the native runtime against one fake Anthropic endpoint (`test/helpers/fake-anthropic.ts`) on every merge, with no network and no key. Bump the pin with `bun add -d nimblebrain-agent@github:NimbleBrainInc/nimblebrain-agent#<sha>` (Renovate proposes digest bumps).
- **Real agents are held to it by the live eval** (`test/eval/runtime-parity.eval.test.ts`): native and nimblebrain-agent on the same runs. Add an agent to it with its driver. nimblebrain-agent's session options are its own documented contract, which its driver speaks without importing it; the stdio connection in `test/helpers/acp/nimblebrain-agent-driver.ts` runs the pinned binary unless `NB_AGENT_BIN` names another.
