# MCP App Bridge

Scope: `web/src/bridge/`, the host side of the MCP Apps protocol between the web shell and sandboxed app iframes. Shell-side rules (SlotRenderer, chat context, auth-token lifecycle) are in `web/AGENTS.md`.

## MCP App Bridge Rules

These cause production bugs if violated:

- **A tool's own failure is a result; a JSON-RPC error means no result came back.** `tools/call` answers the `CallToolResult` verbatim, `isError` and `structuredContent` included (MCP; ext-apps `callServerTool` returns a tool error rather than throwing), so a view reads a structured refusal. Answer a JSON-RPC error only when there is no result: the bridge's own refusals (another server's tool, no active workspace), a server's refusal (`McpError`, forwarded with its `code` and `data`), or a transport failure (`-32000`). Never document a JSON-RPC error as "the call never ran": a timeout (the SDK's `-32001`) or a connection closed mid-call loses the answer to a call that may have run. A pushed `ui/notifications/tool-result` carries the same `CallToolResult`, `isError` included. Never unwrap or rebuild either.
- **An iframe reaches its own server and no other.** `tools/call`, `resources/read`, `resources/list`, `resources/templates/list` and `tasks/get`, `tasks/result`, `tasks/cancel` go to the server that rendered the view, whatever the app names: a qualified tool name for another server is refused, a read names the app's server on the wire so `/mcp` never resolves the URI across the workspace, and a `tools/call` names it so `/mcp` refuses a tool whose `_meta.ui.visibility` lacks `"app"` (MCP Apps). Never add a parameter, `_meta` key or name form that picks a different server.
- **Nothing reaches an app before `ui/notifications/initialized` except answers to its own requests.** The first frame an app receives is the `ui/initialize` response. `createBridge`'s `postToIframe` is the one gate: it holds every notification (host context, tool input and result, `notifications/tasks/status`, relayed server notifications) until the handshake completes, then delivers in order. Post to an app only through its bridge: `BridgeHandle` methods, or `postToApp(iframe, message)` (`web/src/bridge/app-channel.ts`) for code that finds iframes in the DOM. Never call `iframe.contentWindow.postMessage` directly, and never send a load-time notification.
- **A write reaches an app's views only when the app's server announces it**, with a notification the host relays (`RELAYED_SERVER_NOTIFICATIONS` in `src/tools/server-notifications.ts`, today `notifications/resources/list_changed`). This holds wherever the write happened (the agent, an iframe, a webhook, a schedule). The relay forwards, it never interprets: never infer a change from a tool call, on the agent's door or a UI door (a UI door's traffic is mostly reads, and a read that broadcasts loops). A method added to the allowlist must also get its `ui/initialize` capability (`web/src/bridge/relayed-notifications.ts`); a test pins the two. Every notification has one owner, and delivery follows it:
  - **Workspace relay.** A workspace source's notification is stamped with that workspace by its registry and reaches the workspace's members as `server.notification` (`createServerNotificationRelay`). The web shell drops one stamped with a workspace other than the one on screen.
  - **Per-person relay.** A kernel identity source (`IDENTITY_SOURCES`) is shared by every user and sits in no registry, so the host names the owner when it announces (`announceResourceListChangedFor(userId, source)`) and the event reaches only that person, whichever workspace is on screen (`createIdentityServerNotificationRelay`). A notification that names no one is dropped, never broadcast.
  - Both are coalesced per (owner, server, method), and the web shell posts each verbatim to the server's iframes (`useServerNotificationRelay`).
- **Serving a method and declaring it are one edit.** `@nimblebrain/synapse` checks the host's `ui/initialize` declaration before it sends, so a method the bridge serves but does not declare is one no app can reach — and it fails silently, in the app, at the call site. `buildHostCapabilities(appName)` (`web/src/bridge/host-capabilities.ts`) is the whole declaration, built per app (see `upload-files` below); `test/unit/bridge/host-capabilities.test.ts` pins it against the methods the validator accepts. Add a `case` to the bridge, add its capability there.
- **The NimbleBrain extensions are `ai.nimblebrain/action`, `ai.nimblebrain/notify`, `ai.nimblebrain/request-file`, `ai.nimblebrain/upload-files`, `ai.nimblebrain/keydown` and `ai.nimblebrain/location`**, named once in `web/src/bridge/extensions.ts` and declared in `hostCapabilities.experimental` under those same identifiers. The name is both the wire method and the capability id. Never spell one as a literal; import the constant. `ai.nimblebrain/navigate` is host → app, the answer to a location the app sent, so it is named there too but not declared. It is sent only after that app's first location report, never on the handshake alone: an app subscribes to `navigate` only once it has rendered, and drops what arrives earlier (`SlotRenderer` holds an `openApp` target until the report).
- **An app's location is a snapshot, never a history the host keeps.** `ai.nimblebrain/location` carries the app's whole trail and replaces the last one; the top bar derives title and breadcrumb from it alone (`AppLocationContext`, cleared when the app view unmounts). Do not add push/pop messages or a host-side stack: a missed message, a reload or a deep link would leave the host's copy wrong, where a snapshot corrects itself on the next send.
- **`experimental` is where a non-spec capability goes, keyed by its identifier** — the MCP tasks capability at `io.modelcontextprotocol/tasks`, ours under `ai.nimblebrain/`. The official ext-apps `App` parses the handshake result against the spec schema, which names no such field and strips anything outside it; `experimental` is the one slot whose contents survive (ext-apps 1.7.5+). A top-level sibling reaches nothing, so don't add one back.
- **Host fonts travel as the spec's `hostContext.styles.css.fonts`**, built by `buildHostStyles` (`web/src/bridge/host-extensions.ts`) and read once at the handshake. Never as a `styles.variables` key — that field is a strict enum of CSS var names, and one key outside it makes a spec client reject the whole host context.
- **An app's notice (`ai.nimblebrain/notify`) is labelled by the host, never by the app.** The bridge checks level and lengths and answers a bad value `-32602` with the reason (a schema failure is dropped unanswered, which would leave the app's request waiting), limits each app to a burst of 5 in 10 seconds, and passes the notice to `onNotify` without any label. The caller adds the app's name from the bundle's manifest (`SlotRenderer`: the placement's label; `InlineAppView`: the server name), never from the message, so a request cannot name its own source. An app's `notifications/message` stays a console log line: the spec defines it for debugging, and core MCP deprecates it.
- **`ai.nimblebrain/upload-files` is offered and served only to the apps in `UPLOAD_FILES_APPS` (the Files app).** A pick has a step the user takes; this stores whatever the app hands over, so it is an iframe reaching the file store, not its own server. Every other app is not declared it (`extensionsFor`) and is refused `-32601`. Never widen the set without a user-visible step in its place.
- Picker uploads (`ai.nimblebrain/request-file`) and held-file uploads (`ai.nimblebrain/upload-files`) MUST persist via `POST /v1/workspaces/<wsId>/resources` (multipart) and answer `{ files: FileEntry[] }`, with `{ files: [] }` when the user cancels. Never a bare array, never bytes: base64-in-`tools/call` arguments hits the 1 MB JSON cap and silently breaks for any binary above ~750 KB.
- **A picker answers a result only when every picked file was stored.** If any was refused (over `maxSize`, or refused by the server for type or size), it answers JSON-RPC error `-32602` with `data: { files: FileEntry[], errors: string[] }`: `errors` names each refused file and why, `files` holds the entries stored anyway. A rejection does not mean nothing was stored, so an app reads `error.data.files`. It is an error and not a result field because `@nimblebrain/synapse`'s `pickFiles` returns `result.files` alone, so an extra result field never reaches the app. The oversize check runs before upload and stores nothing; the server stores the files that pass. A set over the instance's total is refused before upload with a plain error naming the limit, since no one file is at fault.
- **The picker's limits are the instance's `files` config**, handed to the bridge by `getUploadLimits` and published to apps as `hostContext.uploads`. An app's `maxSize` can lower the per-file limit, never raise it.
- Bridge must guard listeners with `destroyed` flag (React StrictMode double-mounts)
