# packages/cli: the `nimblebrain` CLI

> Read by agents. Terse, imperative. Scope and contract: issue #2028.

Published to npm as `nimblebrain`; run as `npx nimblebrain`. It installs, starts, updates and removes a local NimbleBrain from the release images, connects a coding agent to a workspace, adds an MCP server in development to that workspace (`mcp add | list | remove`, ADR-0065), and runs the install's agents on the person's own Claude Code or Codex subscription through an agent worker on this machine (`use`, `src/subscription/`). Not to be confused with `src/cli/`, the server's own entry point inside the container.

## Rules

- **Setup and running, plus a thin client of the local instance's API for developing against it** (ADR-0065). Setup commands cover checking the machine, installing, starting, stopping, logs, what the agents run on (`use`, `key`, `local-model`), updating and removing. The developing commands (`mcp`) call a tool action the web shell already calls (`manage_connectors`) through `/v1/workspaces/<wsId>/tools/call` and print its answer; the runtime owns what it stores, so they store nothing, restart nothing, and never write a file in the volume. Nothing else inside a running instance (apps, tasks, chat, catalog connectors) gets a subcommand: it belongs to the web UI and `/mcp/<workspaceId>`.
- **A client command sends no `Origin` and no credential.** The `/v1` tool-call doors refuse an untrusted browser origin and pass a request with none; the `dev` adapter signs nobody in. It acts in `--workspace`, else the first workspace in bootstrap, which is the one `init` connects. The runtime's coded refusals (`structuredContent.error`) become CLI codes of the same name; an uncoded one is `REQUEST_FAILED` with the runtime's text.
- **The published package is one self-contained file on Node 20+.** `npx` must start fast on a clean machine, so it installs nothing beside the file and runs nothing at install: `dependencies` stays empty, no install scripts, no native code, no `Bun.*` at run time, and the file stays small (about 260 KB minified). Code the build bundles is fine when it is pure JavaScript with no dependencies of its own and no native code (the ACP SDK and zod, for the agent worker): list it in `devDependencies` at the version the repo root pins, since the build resolves it from the root install (`test/package.test.ts`). A command never evaluates bundled code it does not use: the worker is loaded by a dynamic `import()` in `bin.ts` only. `bun build --target=node --minify` writes the file. Bun is the dev and test toolchain, as everywhere in this repo. `import.meta.main` is Node 24+, so the entry point is `src/bin.ts`, not a guard.
- **Every run answers exactly once.** `bin.ts` writes the answer synchronously; an `exit` hook (and SIGINT/SIGTERM/SIGHUP, routed through `process.exit`) writes `INTERRUPTED` with the exit code if the process ends first. Never write the answer any other way, or end the process before it is written. The one process that never answers is the agent worker (`WORKER_COMMAND`, below), which is not a command: it is absent from `COMMAND_SPECS` and help.
- **One source for the contract: `help --json` is generated from the code.** Commands, flags and error codes live once, in `COMMAND_SPECS` / `MCP_SUBCOMMANDS` / `FLAG_SPECS` (`src/args.ts`) and `ERRORS`; the parser, `--help` and `help --json` (`src/help.ts`) all read them. Never hand-write a list of them anywhere else; `test/help.test.ts` fails when a command, flag or raised code is missing.
- **Each command's answer fields are described once, in `ANSWER_FIELDS` (`src/answers.ts`), and the type-check holds them to the builders.** `AnswerFieldsMatch` fails `tsc` when a builder answers a field not described there, or one is described that no builder answers. So a builder keeps its inferred return type (`ok: true as const`), never the loose `Ok`, which answers every key and fails the check. A new command adds its builder to `Builders` there.
- **`--provider`'s values are the installed release's, not the CLI's.** `key` reads them from the installed Compose file (`providers`), so help cannot list them statically; `key` names them at its prompt and in its `USAGE` error.
- **Every command answers the same shape.** `{ok: true, ...}` or a thrown `CliError`, which `main.ts` turns into `{ok: false, error, message, fix}`. Exit 0 / 1 / 2 (usage). An error code is a published contract once released: add codes freely, never rename one. Each code's `fix` lives once, in `ERRORS` in `src/result.ts`.
- **The model key never appears in arguments, output or logs.** Only `key` takes it, at a hidden prompt, and writes it to `<home>/.env` with mode 600. `status` reports `model_key: set | missing` from the install's `.env` (names only), never from the runtime: bootstrap's `configuredProviders` lists the providers the config allows, key or no key.
- **The web port is published on `127.0.0.1` only.** The local instance uses the `dev` adapter, which signs nobody in.
- **Never touch an install the CLI did not make.** `install.json` (`InstallState`, `src/status.ts`) is the one ownership mark: a home with a readable record is ours; a home without one that holds any file `init` writes (`paths`) is `NOT_OURS`, because `uninstall` would delete it. A corrupt record reads as none. Never infer ownership from `.env`, Docker or anything else: a second mark can disagree with the first.
- **The record is written first, at the claim.** `init` writes `install.json` (`phase: "starting"`) before the Compose file, `instance.json` and `.env`, so a run cut short at any point leaves no CLI file without an owner, and `down`, `logs`, `uninstall` can still act. `phase` turns `ready` after the first healthy start, before the agent is connected.
- **One home, one install, one project.** At the claim the project is `newProject` (`src/compose.ts`): the folder's name plus six random hex digits, so two homes never share one whatever their folders are called (a hash of the path would change when the folder moves). It is stored in the record; every command reads it from there and never derives it again, so a moved home keeps its data. `.env` carries `COMPOSE_PROJECT_NAME` only because Compose reads it there, so no command passes `-p`; the CLI never reads it back.
- **A default port moves; a chosen one never does** (`movePort`, `src/ports.ts`). `init` on a new install (no record) with no `--port`, and `use claude|codex` with no `--port`, take the default (27246; 27290, 27291 for the worker), else the first free port `PORT_STEP` (100) on within `PORT_TRIES`, skipping any port another install this CLI can see recorded (the default home's and `NIMBLEBRAIN_HOME`'s `install.json`, `agent-worker.json` and `.env`, read leniently and never acted on), since a stopped install still owns its port. The move is said (`movedLine`: what holds it, an install by its home, a NimbleBrain web UI by its page title, else "another program") and answered in `port_moved`; the port is recorded (`install.json`; the worker record, `NB_AGENT_RUNTIME_URL` and the login item), so every later command follows it and nothing recomputes it. A port named with `--port`, and a resume's recorded port, are never moved: busy is `PORT_IN_USE`, as is no free port within the tries. A second install beside the first is the case this serves: `--home` already says so, and a refusal would only make the person pick a number. `doctor` in a home with no install reports the port `init` would take.
- **Each install registers under its own server name** (`chooseServerName`, `src/agents.ts`). The default home is `nimblebrain` (`SERVER_NAME`); any other home `nimblebrain-<slug>`, the slug from its folder's name, or its project when the slug is empty or another visible install has it. Chosen at the claim and stored as `serverName` in `install.json`; connect, the `manual` text, `status.agent.server` and `uninstall` read it from there (`serverNameOf`; an older record with none registered `nimblebrain`). A non-default name never replaces a registration this install did not make: when the agent already has one by that name (`claude mcp get`, `codex mcp get`, `~/.cursor/mcp.json`), the install takes its project's name instead. `uninstall` removes only its own name, from Cursor's file too. The `nimblebrain` skill is one, shared and generic, for every install.
- **The phase gates the commands** (`requireInstall` / `requireReady`, `src/status.ts`; every command goes through one). Any phase: `down`, `logs`, `uninstall`, `status`, `doctor`. `ready` only: everything that uses the install (`up`, `update`, `key`, `local-model`, `use`, `telemetry`, `open`, `mcp`), else `INSTALL_INCOMPLETE`, because they assume the agent connection and skill a finished `init` adds. `init` on a `starting` record resumes: same project, the record's port and release unless `--port` / `--runtime`, every install file written again, the port check passed when this project's own containers run (`runningHere`, which `doctor` uses too), and no question already answered in `.env` (model, telemetry) asked again.
- **Every command the CLI prints runs against the install this run acted on.** Build it from `invocation(deps, home)` (`src/deps.ts`), never a literal `npx nimblebrain`: another home is another install, so a bare command would act on the default one, and the printed command may run in a shell without the flag or `NIMBLEBRAIN_HOME`. `ERRORS` keeps the bare text; `main.ts` points a failure's `fix` at the install (`forInstall`). The default home, with no `NIMBLEBRAIN_HOME` elsewhere, prints bare.
- **The CLI is versioned on its own; the runtime is chosen when it runs** (ADR-0064). `--runtime`, then `NIMBLEBRAIN_TAG`, then the newest plain `vX.Y.Z` release; anything below `MIN_RUNTIME` (`src/release.ts`) is `RUNTIME_UNSUPPORTED`. Never tie a CLI version to a runtime version.
- **The Compose file is the chosen release's own,** fetched from its tag (`fetchCompose`) before anything is written. Never write a second Compose file here. Model-key variable names, `key`'s provider list, and `status.host_loopback` (`NB_HOST_LOOPBACK`, without which `mcp add` is `UPDATE_REQUIRED`) are read from the installed file, not restated. A Compose file that does not take `NIMBLEBRAIN_TAG` and `NIMBLEBRAIN_WEB_PORT` from `.env` is refused.
- **Compose runs without the shell's keys, `NIMBLEBRAIN_TAG`, `NIMBLEBRAIN_WEB_PORT` or `COMPOSE_PROJECT_NAME`** (`composeEnv`), so `<home>/.env` is the one source: a key exported in the shell would otherwise silently win over the one entered with `key`.
- **Every Compose call goes through `composeExec` (`src/compose.ts`), never `docker compose` directly.** `findCompose` picks Docker's plugin, else the standalone `docker-compose` v2 (the same program; Homebrew's, as on a Colima machine), once per run, so `doctor` and the commands after it run the same program. Compose v1 is a different program and is never used; with no v2 the call goes to the plugin and its failure says why.
- **`up -d --no-build`, always.** The root Compose file keeps `build:` for source checkouts; the install folder has no source, so a missing image must fail as a pull, never fall back to a build.
- **Update notices are cached, never block, and never update anything** (`src/updates.ts`). One lookup a day (npm `latest`, and the newest runtime through `newestRuntime`), cached in the per-user cache folder, not a home: it describes the world, not one install, and a home holds only what `init` wrote. It starts with the command, and the answer never waits on it: `bin.ts` writes the answer, then gives a lookup still running up to `NOTICE_WAIT_MS` (so a short `--json` run still refreshes the cache), then ends the process, so an abandoned lookup cannot hold it open. A slow or failed lookup leaves the old cache. People get stderr lines after the answer; agents get `updates`, from the cache, on answers carrying an install's state. Off under `CI`, `NIMBLEBRAIN_NO_UPDATE_CHECK=1` and `DO_NOT_TRACK=1` (`doNotTrack`).
- **`update` refreshes everything the CLI installed: the runtime and the skill.** The skill is refreshed (`refreshSkill`) on the `already` path too, reported as `skill_update`, and never fails `update`; a skill a person removed is not added back.
- **Connecting an agent and installing the skill never fail `init`.** The instance is usable either way; a failed connection returns `manual`, the exact settings to add by hand.
- **The agent is asked like the source, but never refused** (`pickAgent`, `detectAgents`, `src/agent-picker.ts`). At a terminal without `--agent`, `init` shows one numbered list once NimbleBrain is up: agents found here first, by what connecting relies on (`claude` and `codex` on `PATH`, the `~/.cursor` folder; `Deps.which` and `Deps.exists`, nothing run), then the rest, then None. Enter takes the default: the agent that is also the source `.env` names (`claude` → Claude Code, `codex` → Codex) when found, else the first found, else None. A number, a name or an alias is taken; anything else is asked again, and after three the default is taken and said, never refused, because it is asked after the start and connecting never fails `init`. Under `--yes`, `--json` or no terminal, only `--agent` connects one. No `agent.ask` in the answer: nothing answers it after `init` (a ready install's `init` connects nothing), and the agent driving `init` names itself with `--agent`.
- **Telemetry waits for a person's answer (`src/telemetry.ts`).** `init` takes it from `--telemetry`, else asks a person at the terminal before anything else, so a failed check after a yes is sent (a busy default port moves rather than failing, so it needs no exception to this order) (`[Y/n]`: Enter is yes, an answer starting with n is no, and the answer is printed back with how to change it), else leaves it `undecided` and returns the question in `telemetry.ask` for an agent to pass on. Never turn it on where no person saw the question: `--yes`, `--json` and a run with no terminal never answer it. Until a yes, events wait in `telemetry-report.jsonl` (mode 600); a yes sends them, a no deletes them. The install's anonymous id is chosen before the checks and kept in `<home>/telemetry-id` (mode 600; `installId`), so every attempt on one home is one install; `.env` gets it as `NB_TELEMETRY_ID`. Never write it into a home holding files the CLI did not write, or while telemetry is locked off. Once the runtime runs, it owns the answer (`nb__set_telemetry`, the same tool the web UI uses); the CLI holds it in `.env` (`NB_TELEMETRY_CONSENT`) only for the runtime's first start. No key or `DO_NOT_TRACK=1`: ask no one, write nothing, send nothing. Only the release build (`build:release`, run by `release-cli.yml`) has a destination, so a development or CI build never sends; the version cannot tell them apart, since it is committed. The runtime gets the key only when its Compose file passes `NB_TELEMETRY_CONSENT` through (`asksConsent`), because an older runtime sends by default once it has a key. Telemetry never fails a command. `TELEMETRY_KEY` is the "NimbleBrain Self-hosted" project's write-only key, public by design; never point it at a project that holds customer data.
- **A local model is set up over Ollama's HTTP API, never its binary** (`src/local-model.ts`): check `/api/version`, pull a missing model only after a person agrees (`--yes` or no terminal agrees), refuse one whose `/api/show` capabilities lack `tools`, and `/api/create` a `nimblebrain-<model>` copy with `num_ctx` fixed, because Ollama otherwise picks a window from GPU memory and silently cuts a longer prompt. The runtime reads it from `.env` (`NB_LOCAL_MODEL_URL`, `NB_LOCAL_MODEL`, `NB_LOCAL_MODEL_CONTEXT`) only when the release's Compose file passes them (`takesLocalModel`); an older release is `RUNTIME_UNSUPPORTED`. `status.local_model` and `doctor`'s Ollama checks read the same `.env`.
- **The CLI may start a dependency the person installed, never install one** (`ensureOllama`, `src/local-model.ts`). It starts a down Ollama only by that install's own mechanism (`open -g -a Ollama`, `brew services start ollama`, `systemctl start --no-ask-password ollama`; never `sudo`, never a spawned `ollama serve`, which would die with the session), after one `[Y/n]` question naming the command, then waits for `/api/version`. Commands that set up or start NimbleBrain (`init`, `local-model`, `up`) take yes when no person can answer; `doctor` starts only on a person's yes. A missing or unstartable Ollama is `LOCAL_MODEL_UNREACHABLE` with that machine's fix from `FIX_VARIANTS`; an answer says what was started in `ollama_started`.
- **A browser opens for a person, or when asked** (`src/open.ts`). `open` always tries, under `--json` and with no terminal too, since an agent asked to open NimbleBrain runs it; where none can start it answers `opened: false` with the URL, never an error. `init` opens one only after a fresh install comes up, for a person at a terminal without `--json` or `--no-open`. The opener is the platform's own (`open`, `xdg-open`) through `Deps.launch`, the URL its own argument, never a shell string. None on Linux without a display (`xdg-open` would fall back to a text browser in the terminal), in an SSH session (it would open on the remote screen), or on Windows, which the CLI does not support. `up` never opens one: it is a restart, often the fix before another command.
- **A code's fix varies only within `FIX_VARIANTS` (`src/result.ts`),** a closed set beside `ERRORS`, chosen by `CliError`'s `variant`. Rebuild an error with `err.with(...)`, never `new CliError(err.code, …)`, which drops the variant.
- **All I/O goes through `Deps` (`src/deps.ts`).** Tests pass a fake and stay unit tests: no Docker, no ports, no network. The agent worker's own process (`src/subscription/`) is the exception: it is a long-running server that does its own I/O (its port, the vendor CLI's processes, its log on stderr). Everything a command does to it (checking the sign-in, installing and removing its login item through `launchctl`, checking `/healthz`) goes through `Deps`, in `src/agent-worker.ts`.
- **What runs NimbleBrain's agents is one question with four answers** (`SOURCES` in `src/args.ts`; `src/source.ts`): `claude` (the Claude subscription through Claude Code), `codex` (the ChatGPT plan through Codex), `api` (a hosted provider's key), `local` (Ollama). `init` asks it and `use` answers it afterwards; `key` and `local-model` change the key or the model within a source and never stop a subscription's worker (a local model set while on a key does become the source, since `sourceOf` ranks it above a key, as the runtime does). The source is read from `.env` alone (`sourceOf`): `NB_AGENT_RUNTIME` first, since the runtime makes that worker the default for every turn, then `NB_LOCAL_MODEL`, then a key. `use claude|codex` keeps a saved key and local model, because a run with a spend budget runs on the native engine and needs one; `use api` empties the agent runtime and the local model; `use local` empties the agent runtime and keeps the key. `status.model_source` names it with a label a person reads, and reads nothing but files and the worker's `/healthz` (for its plan), so it stays fast.
- **The picker never chooses for a person** (`pickSource`, `detectSources`). At a terminal, `init` and a bare `use` show one numbered list: available sources first, each labelled with what was found (the vendor CLI signed in to a subscription by the worker's own parser, `preflight`; a key in `.env`; Ollama answering on 127.0.0.1), the subscriptions offered on macOS only and listed under "Not here" elsewhere, so a Linux user learns they exist without a choice that would fail. Enter takes the default: a signed-in Claude subscription, else a signed-in ChatGPT plan, else `api`. Under `--yes`, `--json` or no terminal, without `init --use` (or `--local-model`, which is `--use local`), `init` chooses nothing and returns the question in `model_source` (`ask`, `options`, `default`, `set`), as `telemetry.ask` does, and a bare `use` is `USAGE`. `init --use claude|codex` starts the worker and writes `.env` before the first `compose up`, so there is no second recreate.
- **`use` runs the install's agents on the person's own subscription** (`src/use.ts`, `src/agent-worker.ts`). `claude` or `codex` checks the vendor CLI's sign-in first (`preflight`: the same parser the worker uses, `claudeAccount` / `codexAccount`), so a CLI that is missing, signed out or signed in with an API key is a coded error whose fix names that CLI's exact command (`FIX_VARIANTS`), then starts the worker, waits until it answers `/healthz`, writes `NB_AGENT_RUNTIME` and `NB_AGENT_RUNTIME_URL` to `.env` (mode 600), and recreates the container with `up -d`, the only way it reads `.env` again. `api` and `local` stop the worker, empty both variables and recreate it; `api` with no key in `.env` asks for one at the hidden prompt (`enterKey`) at a terminal, else refuses with `MODEL_KEY_MISSING` before anything changes. A release whose Compose file does not pass them (`takesAgentRuntime`) is `RUNTIME_UNSUPPORTED`. On Linux it is `HOST_LOOPBACK_UNREACHABLE`: `host-gateway` there is the bridge, not the host's loopback, and the worker never listens anywhere but 127.0.0.1. Anywhere else but macOS it is `PLATFORM_UNSUPPORTED`: the worker runs as a launchd login item.
- **The agent worker is a macOS login item running a copy of this CLI** (`src/agent-worker.ts`, `src/login-item.ts`). `use claude|codex` copies the running file into `<home>/bin/nimblebrain.mjs` (mode 600; npx's cache is cleaned, so the item never points there). `Deps.self.script` is the entry's real path (`entryScript`: npx starts the CLI through a `.bin/nimblebrain` link), and anything but a source checkout's `.ts` entry is copied; only that one runs in place, writes a per-user LaunchAgent, `~/Library/LaunchAgents/ai.nimblebrain.agent-worker.<project>.plist` (`RunAtLoad`; `KeepAlive` on an unsuccessful exit, so a crash restarts it and a clean stop does not; `ThrottleInterval` 10; its output to `<home>/agent-worker.log`, created mode 600 first), with this Node (`process.execPath`), `WORKER_COMMAND`, `--port` and `--log`, and loads it with `launchctl bootstrap gui/<uid>` (`Deps.uid`; never `sudo`, never a LaunchDaemon). launchd owns the process; the CLI never spawns it. The plist passes `PATH`, `HOME`, `LANG`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` from the shell that ran `use` (launchd's own `PATH` finds no `claude`), never a key; its `PATH` puts the folder of the `claude` or `codex` that `use` found (`Deps.which`) first and drops npx's cache (`_npx`), whose entries stop resolving once npx cleans it. Its record, `<home>/agent-worker.json` (mode 600), holds `{port, agent, plan, label, model}`. A worker counts as running when it answers `/healthz` on its port, never by pid; `status` takes the pid from `launchctl print`. Ports: claude 27290, codex 27291, moved when busy (above), `--port` overrides; the runtime dials `http://host.docker.internal:<port>/acp`. `up` and `update` reinstall the item when the Node path, the CLI file or the plist changed, or the worker does not answer, and leave a current, answering one alone. Every stop that a start follows goes through `replaceWorker`: `launchctl bootout` returns while the old worker still drains and holds its port, so it waits (up to `WORKER_RELEASE_MS`, launchd's 20 s kill deadline) for this install's own port to be free before any port is judged, and never reads it as taken (nor moves `use`'s default for it). A port still taken after the wait is `PORT_IN_USE` (fix variant `worker`), and the old plist and record go back and are loaded again, since nothing new was written yet: a failed refresh never leaves the install without its worker; a worker that cannot start still lets NimbleBrain start and fails the command with the worker's code. `down` removes the item, because Docker does not restart a downed NimbleBrain at login either, and keeps `.env`, so `up` installs it again; `use api|local` and `uninstall` remove it (`uninstall` also the record, the log and `<home>/bin`). A worker that exits before answering is unloaded and removed, and `AGENT_WORKER_FAILED` carries its log's last line. Answers name the item in `agent_runtime.worker.login_item`, and `use`'s text says the worker starts at login.
- **The turn model is chosen at `use`, never in the chat** (`DEFAULT_TURN_MODELS`, `src/subscription/command.ts`). `use claude|codex --model <id>` (and `init --use claude|codex --model`) names it; Claude Code defaults to `sonnet`, because a chat turn on it answers faster than on Opus, and Codex to its own default (no `-m`), since the models it offers change with the plan and no small one is documented for every ChatGPT plan. `--model` on any other source is `USAGE`. The model goes to the worker as `--model` in the login item's arguments, into its record, and into `.env` as `NB_AGENT_WORKER_MODEL`, which only this CLI reads: `down` removes the record and the item, and `.env` is what `up` and `update` start it from again. `model_source.model` and its label ("… through Claude Code (Sonnet)") report it.
- **An internal session is cheap** (`SESSION_META_KEY`, `src/subscription/agent.ts`). `session/new` with `_meta["nimblebrain-subscription/session"]: {purpose: "internal"}` is the door's own model work (a title, a history summary): the worker binds no bridge and the backend attaches no MCP server (Claude Code: `--mcp-config '{"mcpServers":{}}'` with `--strict-mcp-config` and `--tools ""`, no `--allowedTools`; Codex: no `mcp_servers` entry), and Claude Code runs it on `INTERNAL_MODEL` (`haiku`), whatever the turn model. Codex keeps the turn model, for the same reason it has no default. Absent or anything else is a normal turn, which still needs its `acp` server.
- **The worker tells the runtime about itself and about every failed turn** (`src/subscription/agent.ts`, `backends/failure.ts`). `initialize` answers `_meta["nimblebrain-subscription/plan"]`, the plan the start-up sign-in check read (`Claude Max`, `ChatGPT`), and `_meta["nimblebrain-subscription/model"]`, the turn model as a person reads it (`Sonnet`, `Opus`, `Haiku`, or the id; absent on the CLI's own default), which the runtime shows in the composer. A failed `session/prompt` is `RequestError.internalError({"nimblebrain-subscription/failure": {code, message}})`: `signed_out`, `plan_limit` (with the reset time when the CLI gives one), `api_key`, `cli_missing` (the binary is not found at spawn) or `cli_failed` (anything else: the exit, the CLI's last output line, and `--log`'s path). `code` matches `^[a-z_]{1,32}$` and is a contract with the runtime's driver (`agent_<code>` in chat): add codes, never rename one. `message` is shown in chat as written, so it names the fix and never carries a credential (`redact`). Classify from what the CLIs print, checked against their real output: Claude Code's assistant `error` field (`authentication_failed`, `rate_limit`, `billing_error`) and its `is_error` result text; Codex's `turn.failed` text (a 401 is signed out). A Codex turn that completes after a retried `error` event succeeded.
- **Every turn and internal run logs one `timeline` line when it ends** (`startTimeline`, `src/subscription/backends/timeline.ts`; `CLAUDE_MARKS`, `CODEX_MARKS`): seconds from spawn to each mark (`-` when never reached), then `events` (retries, errors, other system lines), then `rate_limit`. It is built from event names, counts, codes and the CLIs' own short error text (`redact`ed, 80 characters), never a prompt, an answer, a tool's arguments or output, or a credential. Claude Code's retry is `{"type":"system","subtype":"api_retry",attempt,max_retries,retry_delay_ms,error_status,error,no_response?}` (`error`: `overloaded`, `rate_limit`, `authentication_failed`, `server_error`, `unknown`); its plan window is `rate_limit_event.rate_limit_info` (utilization under `unifiedWindows[<type>]`). Codex's retry is `{"type":"error","message":"Reconnecting... n/m (reason)"}`, and a transport fallback an `item.completed` of type `error`. Check a new event against the CLI's real output before timing it.
- **A turn that shows nothing for `WAIT_NOTE_MS` (15 s) is told it is waiting** as an `agent_thought_chunk` (the runtime streams it as reasoning and does not keep it), again each interval, naming the latest retry when the stream reported one, until the first text, thinking or tool call; never after output starts, never for an internal run, which no one watches. The interval is the backend's `noteMs`, for tests.
- **The worker's safety checks are what make a turn bill the subscription** (`src/subscription/backends/`). Every API key variable is removed from the vendor CLI's environment (`subscriptionEnv`); it refuses to start unless the sign-in names a subscription; a Claude turn whose `init` line names any `apiKeySource` but `none` is stopped; never `claude --bare`, which reads only `ANTHROPIC_API_KEY`. Claude Code runs with `--tools ""`, `--strict-mcp-config` and `--setting-sources ""`; Codex with `--ignore-user-config`. Both in an empty working directory. The worker binds 127.0.0.1 only, answers only a Host of `127.0.0.1`, `localhost` or `host.docker.internal` with no `Origin` (a browser page rebinding its hostname to loopback is refused), and each session's MCP bridge is a random path that lives as long as the session. Never relax one of these to make a turn work.

## Releasing

Its own `cli/v*` tags and `.github/workflows/release-cli.yml` (RELEASING.md, "Releasing the CLI"), like `packages/server-sdk-py`. The version lives in this `package.json`; bump it in the PR that ships the change, and the tag must match it. A release is staged on npm and goes public only when a maintainer approves it with 2FA. `cli-e2e` runs the whole lifecycle on `ubuntu-latest` and `ubuntu-24.04-arm` against the newest runtime release.

## Verify

- `bun run test:cli`: unit tests (in `verify:test-unit`).
- `bun run check:cli`: type-check, build, and run the built file under Node (in `verify:static`).
- `node packages/cli/dist/nimblebrain.js doctor` after a build tries it against this machine.
