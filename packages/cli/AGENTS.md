# packages/cli: the `nimblebrain` CLI

> Read by agents. Terse, imperative. Scope and contract: issue #2028.

Published to npm as `nimblebrain`; run as `npx nimblebrain`. It installs, starts, updates and removes a local NimbleBrain from the release images, connects a coding agent to a workspace, and adds an MCP server in development to that workspace (`mcp add | list | remove`, ADR-0065). Not to be confused with `src/cli/`, the server's own entry point inside the container.

## Rules

- **Setup and running, plus a thin client of the local instance's API for developing against it** (ADR-0065). Setup commands cover checking the machine, installing, starting, stopping, logs, the model key, updating and removing. The developing commands (`mcp`) call a tool action the web shell already calls (`manage_connectors`) through `/v1/workspaces/<wsId>/tools/call` and print its answer; the runtime owns what it stores, so they store nothing, restart nothing, and never write a file in the volume. Nothing else inside a running instance (apps, tasks, chat, catalog connectors) gets a subcommand: it belongs to the web UI and `/mcp/<workspaceId>`.
- **A client command sends no `Origin` and no credential.** The `/v1` tool-call doors refuse an untrusted browser origin and pass a request with none; the `dev` adapter signs nobody in. It acts in `--workspace`, else the first workspace in bootstrap, which is the one `init` connects. The runtime's coded refusals (`structuredContent.error`) become CLI codes of the same name; an uncoded one is `REQUEST_FAILED` with the runtime's text.
- **Node 20+, no Bun at run time, no dependencies.** `npx` must start fast on a clean machine. Use `node:` built-ins only; `bun build --target=node` bundles to one file. Bun is the dev and test toolchain, as everywhere in this repo. `import.meta.main` is Node 24+, so the entry point is `src/bin.ts`, not a guard.
- **Every run answers exactly once.** `bin.ts` writes the answer synchronously; an `exit` hook (and SIGINT/SIGTERM/SIGHUP, routed through `process.exit`) writes `INTERRUPTED` with the exit code if the process ends first. Never write the answer any other way, or end the process before it is written.
- **One source for the contract: `help --json` is generated from the code.** Commands, flags and error codes live once, in `COMMAND_SPECS` / `MCP_SUBCOMMANDS` / `FLAG_SPECS` (`src/args.ts`) and `ERRORS`; the parser, `--help` and `help --json` (`src/help.ts`) all read them. Never hand-write a list of them anywhere else; `test/help.test.ts` fails when a command, flag or raised code is missing.
- **Every command answers the same shape.** `{ok: true, ...}` or a thrown `CliError`, which `main.ts` turns into `{ok: false, error, message, fix}`. Exit 0 / 1 / 2 (usage). An error code is a published contract once released: add codes freely, never rename one. Each code's `fix` lives once, in `ERRORS` in `src/result.ts`.
- **The model key never appears in arguments, output or logs.** Only `key` takes it, at a hidden prompt, and writes it to `<home>/.env` with mode 600. `status` reports `model_key: set | missing` from the install's `.env` (names only), never from the runtime: bootstrap's `configuredProviders` lists the providers the config allows, key or no key.
- **The web port is published on `127.0.0.1` only.** The local instance uses the `dev` adapter, which signs nobody in.
- **Never touch an install the CLI did not make.** The Compose project name in `install.json` marks containers and the data volume as ours; anything else is `NOT_OURS`.
- **One home, one install.** `init` names the Compose project after the home folder (`projectFor`; the default home keeps `nimblebrain-local`, the name every older install has) and writes it to `install.json` and `.env`. Every later command takes it from there and never derives it again, so a moved home keeps its data. Compose reads it from `<home>/.env`, so no command passes `-p`.
- **Every command the CLI prints runs against the install this run acted on.** Build it from `invocation(deps, home)` (`src/deps.ts`), never a literal `npx nimblebrain`: another home is another install, so a bare command would act on the default one, and the printed command may run in a shell without the flag or `NIMBLEBRAIN_HOME`. `ERRORS` keeps the bare text; `main.ts` points a failure's `fix` at the install (`forInstall`). The default home, with no `NIMBLEBRAIN_HOME` elsewhere, prints bare.
- **The CLI is versioned on its own; the runtime is chosen when it runs** (ADR-0064). `--runtime`, then `NIMBLEBRAIN_TAG`, then the newest plain `vX.Y.Z` release; anything below `MIN_RUNTIME` (`src/release.ts`) is `RUNTIME_UNSUPPORTED`. Never tie a CLI version to a runtime version.
- **The Compose file is the chosen release's own,** fetched from its tag (`fetchCompose`) before anything is written. Never write a second Compose file here. Model-key variable names, `key`'s provider list, and `status.host_loopback` (`NB_HOST_LOOPBACK`, without which `mcp add` is `UPDATE_REQUIRED`) are read from the installed file, not restated. A Compose file that does not take `NIMBLEBRAIN_TAG` and `NIMBLEBRAIN_WEB_PORT` from `.env` is refused.
- **Compose runs without the shell's keys, `NIMBLEBRAIN_TAG`, `NIMBLEBRAIN_WEB_PORT` or `COMPOSE_PROJECT_NAME`** (`composeEnv`), so `<home>/.env` is the one source: a key exported in the shell would otherwise silently win over the one entered with `key`.
- **`up -d --no-build`, always.** The root Compose file keeps `build:` for source checkouts; the install folder has no source, so a missing image must fail as a pull, never fall back to a build.
- **Update notices are cached, never block, and never update anything** (`src/updates.ts`). One lookup a day (npm `latest`, and the newest runtime through `newestRuntime`), cached in the per-user cache folder, not a home: it describes the world, not one install, and a home holds only what `init` wrote. It starts with the command, and the answer never waits on it: `bin.ts` writes the answer, then gives a lookup still running up to `NOTICE_WAIT_MS` (so a short `--json` run still refreshes the cache), then ends the process, so an abandoned lookup cannot hold it open. A slow or failed lookup leaves the old cache. People get stderr lines after the answer; agents get `updates`, from the cache, on answers carrying an install's state. Off under `CI`, `NIMBLEBRAIN_NO_UPDATE_CHECK=1` and `DO_NOT_TRACK=1` (`doNotTrack`).
- **`update` refreshes everything the CLI installed: the runtime and the skill.** The skill is refreshed (`refreshSkill`) on the `already` path too, reported as `skill_update`, and never fails `update`; a skill a person removed is not added back.
- **Connecting an agent and installing the skill never fail `init`.** The instance is usable either way; a failed connection returns `manual`, the exact settings to add by hand.
- **Telemetry waits for a person's answer (`src/telemetry.ts`).** `init` takes it from `--telemetry`, else asks a person at the terminal before anything else, so a failed check after a yes is sent (`[Y/n]`: Enter is yes, an answer starting with n is no, and the answer is printed back with how to change it), else leaves it `undecided` and returns the question in `telemetry.ask` for an agent to pass on. Never turn it on where no person saw the question: `--yes`, `--json` and a run with no terminal never answer it. Until a yes, events wait in `telemetry-report.jsonl` (mode 600); a yes sends them, a no deletes them. Once the runtime runs, it owns the answer (`nb__set_telemetry`, the same tool the web UI uses); the CLI holds it in `.env` (`NB_TELEMETRY_CONSENT`) only for the runtime's first start. No key or `DO_NOT_TRACK=1`: ask no one, write nothing, send nothing. Only the release build (`build:release`, run by `release-cli.yml`) has a destination, so a development or CI build never sends; the version cannot tell them apart, since it is committed. The runtime gets the key only when its Compose file passes `NB_TELEMETRY_CONSENT` through (`asksConsent`), because an older runtime sends by default once it has a key. Telemetry never fails a command. `TELEMETRY_KEY` is the "NimbleBrain Self-hosted" project's write-only key, public by design; never point it at a project that holds customer data.
- **A local model is set up over Ollama's HTTP API, never its binary** (`src/local-model.ts`): check `/api/version`, pull a missing model only after a person agrees (`--yes` or no terminal agrees), refuse one whose `/api/show` capabilities lack `tools`, and `/api/create` a `nimblebrain-<model>` copy with `num_ctx` fixed, because Ollama otherwise picks a window from GPU memory and silently cuts a longer prompt. The runtime reads it from `.env` (`NB_LOCAL_MODEL_URL`, `NB_LOCAL_MODEL`, `NB_LOCAL_MODEL_CONTEXT`) only when the release's Compose file passes them (`takesLocalModel`); an older release is `RUNTIME_UNSUPPORTED`. `status.local_model` and `doctor`'s Ollama checks read the same `.env`.
- **The CLI may start a dependency the person installed, never install one** (`ensureOllama`, `src/local-model.ts`). It starts a down Ollama only by that install's own mechanism (`open -g -a Ollama`, `brew services start ollama`, `systemctl start --no-ask-password ollama`; never `sudo`, never a spawned `ollama serve`, which would die with the session), after one `[Y/n]` question naming the command, then waits for `/api/version`. Commands that set up or start NimbleBrain (`init`, `local-model`, `up`) take yes when no person can answer; `doctor` starts only on a person's yes. A missing or unstartable Ollama is `LOCAL_MODEL_UNREACHABLE` with that machine's fix from `FIX_VARIANTS`; an answer says what was started in `ollama_started`.
- **A browser opens for a person, or when asked** (`src/open.ts`). `open` always tries, under `--json` and with no terminal too, since an agent asked to open NimbleBrain runs it; where none can start it answers `opened: false` with the URL, never an error. `init` opens one only after a fresh install comes up, for a person at a terminal without `--json` or `--no-open`. The opener is the platform's own (`open`, `xdg-open`) through `Deps.launch`, the URL its own argument, never a shell string. None on Linux without a display (`xdg-open` would fall back to a text browser in the terminal), in an SSH session (it would open on the remote screen), or on Windows, which the CLI does not support. `up` never opens one: it is a restart, often the fix before another command.
- **A code's fix varies only within `FIX_VARIANTS` (`src/result.ts`),** a closed set beside `ERRORS`, chosen by `CliError`'s `variant`. Rebuild an error with `err.with(...)`, never `new CliError(err.code, …)`, which drops the variant.
- **All I/O goes through `Deps` (`src/deps.ts`).** Tests pass a fake and stay unit tests: no Docker, no ports, no network.

## Not here yet

- **A skill matched to the release.** `installSkill` takes the `nimblebrain` skill from the skills repo's default branch; that repo has no release tags to pin to yet.

## Releasing

Its own `cli/v*` tags and `.github/workflows/release-cli.yml` (RELEASING.md, "Releasing the CLI"), like `packages/server-sdk-py`. The version lives in this `package.json`; bump it in the PR that ships the change, and the tag must match it. A release is staged on npm and goes public only when a maintainer approves it with 2FA. `cli-e2e` runs the whole lifecycle on `ubuntu-latest` and `ubuntu-24.04-arm` against the newest runtime release.

## Verify

- `bun run test:cli`: unit tests (in `verify:test-unit`).
- `bun run check:cli`: type-check, build, and run the built file under Node (in `verify:static`).
- `node packages/cli/dist/nimblebrain.js doctor` after a build tries it against this machine.

## The skill side

The `nimblebrain` skill in `NimbleBrainInc/skills` drives this CLI and documents its commands, fields and error codes in `skills/nimblebrain/references/cli.md`. Change both together. The skill is moving to read `npx nimblebrain help --json` from the CLI that runs instead of keeping that copy, keeping only what the code cannot say (when to run what, what a person must do themselves).
